# 음성 에이전트(Voice Agent) — 개념·기술·산업 도입 사례 리서치

조사일: 2026-09-24 (KST)

- 백로그: `_research/ax-topic-backlog-100.md` 087번을 ‘반복 전화 업무의 AX’로 확장.
- 독자: AI·AX에 관심 있는 경영진, 물류·고객지원·서비스 운영 책임자.
- 범위: 실시간 음성 대화, 업무 시스템 실행, 사람 인계, 실제 산업 도입, 품질·비용·운영 기준.
- 자료 구분: 도입 기업 공식 발표, 공급사 고객 사례, 공식 기술 문서, 자체 설계 제안.
- 공개 자료조사이며 실제 전화 발신·제품 구축·통화 실험·고객 인터뷰는 수행하지 않았다.

## 1. 핵심 결론과 편집 방향

**음성 에이전트는 음성으로 요청을 주고받으며 필요한 정보를 조회하고, 허용된 업무를 실행하거나 사람에게 넘기도록 구성한 시스템이다.** 음성 인식이나 말하는 챗봇은 구성 요소가 될 수 있지만 그것만으로 예약 변경·주문 접수·운송 상태 갱신이 끝나지는 않는다.

이번 포스트는 목소리가 사람과 얼마나 비슷한지보다 **전화로 확인한 내용이 실제 업무에 반영되는가**에 초점을 맞추는 편이 좋다. DHL의 일정·운송 확인, Five Guys의 전화 주문, MUSC Health의 예약 지원을 묶어 산업별 적용을 설명할 수 있다. [S1–S4]

중심 질문:

> 직원이 하루 종일 통화하면서 같은 정보를 여러 사람과 시스템에 옮기고 있다면, 그중 어디까지 AI에게 맡길 수 있을까?

음성 에이전트 전체를 LLM 기반 제품으로만 정의하지 않는다. 기존 대화형 음성 시스템도 업무 실행 기능을 가질 수 있으며 최근 제품에서는 언어 모델과 실시간 음성 모델을 조합하는 선택지가 늘었다. 기능과 실행 범위로 구분한다.

## 2. 혼동하기 쉬운 개념

| 개념 | 역할 | 음성 에이전트와의 관계 |
|---|---|---|
| ARS·IVR | 전화 메뉴, 안내, 입력 수집, 연결 | 버튼 입력뿐 아니라 음성 인식·시스템 조회를 지원하는 구성도 있음 |
| STT·ASR | 음성을 텍스트로 인식 | 들은 말을 기록하는 단계. 실제 의도·업무 완료와 구분 |
| TTS | 텍스트를 음성으로 합성 | 말하는 기능. 그 말이 사실인지·권한 안의 약속인지는 별도 문제 |
| 음성 챗봇 | 음성으로 질문·응답 | 업무 도구와 연결하면 실행 범위를 확장할 수 있음 |
| 상담원 보조 | 사람이 통화하고 AI가 검색·요약·추천 | 고객과 직접 통화하는 자동 에이전트와 운영 주체가 다름 |
| 음성 에이전트 | 대화 상태와 업무 도구를 사용해 과업 수행 | 확인·실행·인계·결과 대조까지 설계 |
| 음성 복제 | 특정 목소리의 특징을 재현 | 선택적 음성 제작 기능. 에이전트 도입의 필수 조건이 아님 |

설명을 위한 기능 구분이다. ‘기존 ARS는 아무것도 실행하지 못한다’거나 ‘음성이 자연스러우면 자율 에이전트다’라고 단순화하지 않는다.

인바운드는 고객이 건 전화에 응대하는 일, 아웃바운드는 시스템이 상대방에게 먼저 전화하는 일이다. 미응답·재발신·수신 거부·발신 목적과 권한은 아웃바운드에서 별도로 다뤄야 한다.

## 3. 산업 현장의 실제 도입 사례

### 3.1 DHL — 전화로 확인하고 운영 시스템을 갱신

DHL은 2025-11-11 공식 발표에서 HappyRobot의 AI 에이전트를 여러 지역의 일정 예약, 운전자 후속 전화, 우선순위가 높은 창고 업무 조율에 활용한다고 밝혔다. 전화·이메일과 내부 시스템 연결을 함께 다룬다. 연간 수십만 이메일과 수백만 음성 분량을 대상으로 한다고 설명하지만 이는 절감 시간이나 자동 해결 건수와 다르다. [S1]

HappyRobot의 상세 고객 사례는 운송사에 전화해 집하·배송 예상 도착 시간을 수집하고 DHL의 운송관리시스템(TMS)을 갱신하는 흐름을 설명한다. 공급사 자료에는 청구 후속 연락, 온도 경보에 따른 연락·단계별 인계 등도 나온다. [S2]

**활용 관점:** 전화 대신 받는 기능보다 ‘확인 전화 → 도착 시간 기록 → 예외 전달’을 설명하기에 적합하다. 상세 구현은 HappyRobot 발표, 도입 자체와 주요 업무는 DHL 공식 발표로 출처를 구분한다. 발표에 없는 절감률이나 인원 감소를 만들지 않는다.

### 3.2 Five Guys — 바쁜 매장의 전화 주문

SoundHound의 2026-06-29 고객 사례는 Five Guys가 전화 주문을 받고 주방에 전달하는 음성 AI를 사용한다고 설명한다. 공개 수치는 첫해 184,000건 이상의 전화 주문, 2025년 AI가 접수한 전화 주문의 완료율 92%다. [S3]

자료는 모든 전화를 받는다고도 표현하지만 응답과 주문 완료는 서로 다른 단계다. 수치를 전체 브랜드의 모든 매장 성과로 확대하지 않는다. 도입 매장 범위·분모·측정 방법의 상세 내용은 해당 페이지에서 충분히 확인되지 않았다. 스페인어 지원은 본문과 확대 계획의 표현이 섞여 있어 전 매장 완료 기능으로 쓰지 않는다.

**활용 관점:** 직원이 현장 주문을 처리하는 동안 놓치는 전화 주문이라는 경영진의 관심사를 다룬다. 음성 대화 뒤 메뉴·옵션·주방 전달의 정확성이 중요하다는 논점으로 연결한다.

### 3.3 MUSC Health — 예약 확인·취소·일정 변경

SoundHound의 2026-05-21 사례에 따르면 MUSC Health의 Emily는 Epic과 연결해 예약 확인·취소·일정 변경, 일반 문의 등을 지원한다. 연간 220만 상호작용이라는 규모는 **음성과 채팅을 합친 범위**다. 2026년에는 처방 재조제 요청·상태 확인·약국 연결로 확장했다고 설명한다. [S4]

본문에서는 예약 지원과 시스템 연결을 중심으로 사용하고 진단·처방 판단을 자율 수행한다고 쓰지 않는다. 계획 중인 HR·IT 기능이나 단계적 파일럿인 시설 업무도 운영 완료 사례와 구분한다.

자료 품질 메모: 원문에 ‘4.3/5 NPS’라고 적혀 있으나 일반적인 NPS 척도와 맞지 않는다. 이를 임의로 CSAT로 바꿔 인용하지 않고 본문에서 제외한다. 인력 부족을 설명하는 문맥의 ‘30 FTE underutilized’도 해석이 불분명해 수치 인용을 보류한다.

**활용 관점:** 예약을 묻는 전화가 담당자 연결에서 끝나지 않고 실제 예약 시스템의 상태 변경으로 이어지는 구조를 설명한다. 의료 업무 자체의 판단과 행정 지원을 섞지 않는다.

### 3.4 참고 후보 — Taco Bell 드라이브스루

2024-07-31 공식 발표는 당시 미국 13개 주의 100개 이상 드라이브스루에서 음성 AI를 운영하며 연말까지 수백 매장으로 확대할 계획이라고 설명했다. [S5]

이는 당시 도입·확대 발표다. 현재 운영 규모나 전체 확대의 성공 여부를 확인하는 근거로 사용하지 않는다. 이번 글에는 위 세 사례만으로도 산업 범위가 충분하며, 이 사례를 본문에 쓰려면 후속 운영 결과를 추가 조사하는 편이 좋다.

## 4. 기술 구조: 음성을 처리하는 두 경로

LiveKit 공식 문서는 STT–LLM–TTS 조합과 직접 음성을 주고받는 실시간 모델을 구분한다. [S6]

| 구성 | 흐름 | 설계 시 고려점 |
|---|---|---|
| 단계별 파이프라인 | 음성 → STT → 언어 모델·도구 → TTS → 음성 | 인식·판단·발화를 따로 조정·검토하기 쉬움. 단계 사이 지연과 인식 오류 전파 관리 |
| 실시간 음성 모델 | 음성 입력 → 실시간 모델·도구 → 음성 출력 | 음성 맥락과 빠른 상호작용 활용. 재생·중단·기록·도구 실행의 동기화 확인 |
| 혼합 구성 | 실시간 대화와 별도 전사·검증·업무 엔진 조합 | 중복 호출 비용, 서로 다른 기록의 불일치, 어느 결과가 기준인지 관리 |

비교표의 운영 고려점은 자체 설계 정리다. 직접 음성 모델에도 내부 처리 단계가 존재할 수 있으며 ‘텍스트를 전혀 사용하지 않는다’고 일반화하지 않는다.

Gemini Live API 공식 설명에는 음성 대화, 중간 발화 끼어들기, 도구 호출, 입력·출력 전사 기능이 있다. [S7] 실시간 음성 모델을 사용해도 전화망 연결, 고객 인증, 예약 권한과 실행 검증은 별도로 구성한다. 모델 ID·가격·지원 언어 목록은 변동 가능성이 커 이번 문서에서 비교 순위를 만들지 않는다.

### 4.1 전화망과 애플리케이션 사이

일반 전화망(PSTN), 기업 전화 연결에 쓰는 SIP, 웹·앱 실시간 미디어에 쓰는 WebRTC는 연결 방식이다. 업무 판단 모델과 구분해서 설명한다. 전화번호를 연결했다고 AI에게 예약 변경 권한까지 생기는 것은 아니다.

Twilio Media Streams는 WebSocket으로 음성 데이터를 전달하며 문서의 해당 오디오 형식은 μ-law, 8kHz, 모노다. [S8] 이를 모든 전화 서비스의 고정 사양으로 일반화하지 않는다. 모델 입력 형식과 다르면 변환이 필요하며, 실제 전화 품질에서 인식 성능을 시험해야 한다.

Twilio ConversationRelay는 STT·TTS 처리를 서비스 쪽에 맡기고 애플리케이션과 텍스트·이벤트를 주고받는 구성을 지원한다. [S9][S10] 음성 스트림을 직접 다루는 경로와 운영 책임이 다르다.

## 5. 말이 끝났는지와 잠깐 멈췄는지는 다릅니다

핵심 용어:

- **VAD:** 음성이 있는 구간을 탐지한다. 문장의 의미가 완성됐는지 판단하는 것과 다르다.
- **Endpointing·Turn detection:** 상대의 발화 차례가 끝났는지 판단한다.
- **Barge-in:** 상대가 AI의 말 도중 끼어들면 재생을 멈추고 새 발화를 처리한다.
- **Backchannel:** “네”, “음” 같은 맞장구. 항상 새로운 요청이나 실행 동의인 것은 아니다.

LiveKit은 음성 활동·문맥을 활용한 발화 종료 판단, 중단, 잘못 감지한 끼어들기 등을 설명한다. [S11] Twilio도 발화 종료 대기 시간과 음성 재생 중단 여부를 설정할 수 있다. [S9]

가상 예시:

> 고객: “금요일 오후 세 시로… 아니요, 네 시로 바꿔주세요.”

‘세 시’ 뒤의 짧은 침묵을 완료로 판단해 예약 변경을 실행하면 고객의 정정을 놓친다. 반대로 매번 지나치게 기다리면 고객이 끊겼다고 생각하고 말을 반복할 수 있다.

권장 설계는 최종 후보를 확인한 뒤 실행하는 것이다. “이번 금요일 오후 네 시로 변경할까요?”라고 구체적으로 확인하고, 고객이 동의하면 예약 도구를 호출한다. 핵심 슬롯인 날짜·시간·대상·수량은 인식된 문장과 별도로 관리한다.

### 5.1 지연은 전체 통화 경로로 본다

자체 관측 설계:

`발화 종료 판단 → 인식 결과 → 모델 판단·도구 조회 → 음성 생성 → 네트워크 전송·재생`

단계들이 스트리밍으로 겹칠 수 있으므로 단순 합산만으로 실제 체감 지연을 설명하지 않는다. 고객 발화 종료부터 AI의 첫 음성이 들리기까지, 조회가 끝나기까지, 업무를 완료하기까지를 따로 측정한다. 평균 외에 느린 통화 구간과 p95도 확인한다.

첫 음성이 “잠시만요”였다는 이유로 업무 응답이 빨라졌다고 평가하지 않는다. 도구 조회가 지연되면 실제 처리 상태에 맞는 안내를 하고 시간 한도를 넘었을 때 인계할 방법을 정한다. 모든 업무에 같은 지연 목표를 임의로 제시하지 않는다.

## 6. 생성한 문장·재생한 말·실행한 업무를 구분한다

AI가 “예약이 변경됐습니다”라는 문장을 만들었어도 고객이 중간에 말을 끊으면 전체 내용을 듣지 못했을 수 있다. 더구나 예약 도구 호출은 아직 처리 중일 수 있다.

Twilio ConversationRelay는 끼어들기 시점까지의 발화와 시간을 이벤트로 전달한다. Media Streams에는 재생 버퍼를 관리하는 mark·clear 메시지가 있다. [S10][S8] 이는 오디오 처리 상태를 관리하는 신호이며 고객의 이해나 동의까지 증명하지 않는다.

자체 설계 제안:

| 기록 | 용도 |
|---|---|
| 인식한 요청과 정정 | 마지막으로 확인한 날짜·수량·대상 파악 |
| 생성한 답변 | AI가 어떤 안내를 계획했는지 확인 |
| 재생 진행·중단 이벤트 | 실제 전달을 시도한 범위와 잘린 안내 확인 |
| 확인 질문과 고객 응답 | 어떤 조건에 동의했는지 대조 |
| 도구 요청·결과·거래 ID | 실제 예약·주문·상태 갱신 확인 |
| 다음 조치와 인계 상태 | 통화가 끊겨도 업무 누락 방지 |

말을 끊었다고 이미 실행한 예약 변경이 자동으로 취소되는 것은 아니다. 실행 전 취소, 실행 중 결과 확인, 실행 후 취소·변경을 분리해야 한다. [기존 Durable Execution 글](../content/posts/geoff-20-durable-execution/index.md)의 중복 실행 방지와 연결할 수 있다.

## 7. 사람에게 연결할 때는 설명도 넘긴다

LiveKit의 warm transfer는 고객을 대기시키고 담당자에게 먼저 맥락을 전달한 뒤 연결하는 절차다. 담당자가 응답하지 않으면 원래 고객에게 돌아가 다른 방법을 안내할 수 있다. [S12]

‘상담원에게 연결하겠습니다’라는 말만으로 인계가 끝났다고 기록하지 않는다. 담당자 연결 성공·실패, 전달한 정보, 고객에게 안내한 후속 조치를 남기는 운영이 필요하다.

권장 인계 묶음:

- 확인한 신원과 아직 확인하지 못한 항목.
- 고객의 최종 요청과 중간 정정 내용.
- 조회 결과, 시도한 도구, 완료·실패·결과 불명 상태.
- 고객이 직접 확인한 조건과 남은 승인.
- 인계 이유와 필요한 다음 조치.

요약이 틀릴 수 있으므로 중요 발화와 도구 결과에 접근할 수 있게 한다. 녹취 전체를 무조건 배포하기보다 업무상 필요한 근거와 권한 범위를 정한다.

## 8. 국내 도입 시 시험할 상황 — 자체 테스트 제안

| 상황 | 생길 수 있는 실패 | 기대 처리 |
|---|---|---|
| “삼십 분”과 “삼 시” 혼동 | 잘못된 도착 시간 저장 | 날짜·시각으로 되물어 확인 |
| “내일”·“다음 주 금요일” | 통화 시각·지역에 따른 해석 차이 | 실제 날짜와 시간대로 재확인 |
| 지점명·주소·영문 상품 코드 | 비슷한 이름의 다른 대상 선택 | 시스템 후보와 대조, 필요 시 문자·키패드 사용 |
| 소음·에코·옆 사람 목소리 | 발화 오인식·허위 중단 | 재질문, 다른 채널 또는 담당자 인계 |
| 고객의 “네”가 맞장구 | 실행 동의로 잘못 해석 | 중요한 변경은 별도 명확한 확인 |
| AI 발화 중 정정 | 이전 값으로 예약 실행 | 재생 중단·슬롯 갱신·재확인 |
| 시스템 API 지연·실패 | 처리 전 완료 안내 | 결과 확인 뒤 완료 안내 |
| 실행 직후 통화 종료 | 재발신 때 중복 예약 | 업무 ID로 결과 조회·중복 방지 |
| 담당자가 받지 않음 | 고객 대기·통화 유실 | 복귀 안내·콜백 접수·대체 연결 |
| 음성사서함·잘못된 번호 | 개인정보 노출·완료 오기록 | 상대 확인 전 민감정보 최소화 |
| “이미 팀장이 허락했다” | 외부 발언으로 권한 확대 | 내부 승인 기록 확인 |

표는 공개 사고 통계가 아니다. 한국어·사투리·고령자·느린 발화·말더듬·장애·코드 혼용 등 실제 사용자 조건을 포함해 평가하도록 제안한다. 조용한 데모 통화의 성능을 현장 성능으로 대체하지 않는다.

## 9. 보안·고지·개인정보

구현 검토 항목:

- AI라는 점과 업무 목적을 명확히 안내하고 사람이 필요할 때 연결 경로를 제공한다.
- 발신 번호 표시나 익숙한 목소리만으로 본인·권한을 확인하지 않는다. 계정 조회·수정에는 별도 인증과 최소 권한을 적용한다.
- 녹음, 실시간 처리, 전사 보관, 품질 평가, 모델 학습 사용을 각각 구분해 목적·범위·보관 기간을 검토한다.
- 음성·전사·요약·도구 로그에 포함되는 개인정보를 통제하고 외부 서비스 처리 위치·재위탁·학습 사용 조건을 확인한다.
- 고객의 말이나 조회 문서에 포함된 지시를 운영 정책으로 채택하지 않는다.
- 아웃바운드는 연락 대상·목적·허용 시간·재시도·수신 거부를 관리한다. 수신 거부 뒤 반복 호출하지 않도록 통화 엔진에서도 제한한다.

국내 법률의 구체적 적용은 서비스·목적·정보 종류에 따라 별도 검토한다. 개인정보위의 2025-08-06 생성형 AI 개인정보 처리 안내서 공개 자료를 출발점으로 삼을 수 있으나 이 자료만으로 전화 녹음·광고성 발신의 모든 요건을 확정할 수는 없다. [S13]

미국 FCC는 2024년 AI 생성 음성에도 TCPA의 인공·사전녹음 음성 관련 제한이 적용됨을 명확히 했다. [S14] ‘모든 AI 전화가 금지됐다’로 요약하지 않는다. 이번 조사에서는 관련 성명·공식 자료를 확인했으며 2026년의 관할별 전체 규정 준수 판단은 수행하지 않았다.

## 10. 성과·비용 평가

권장 단계별 분모:

`발신 시도 또는 수신 → 연결 → 대상·권한 확인 → 요청 파악 → 실행 → 결과 대조 → 고객 안내 → 후속 업무 완료`

| 지표 | 확인할 내용 |
|---|---|
| 응답·연결률 | 전화를 받았는가, 올바른 상대와 연결됐는가 |
| 과업 완료율 | 실제 예약·주문·기록 갱신이 끝났는가 |
| 잘못된 실행률 | 잘못된 대상·수량·시간으로 처리했는가 |
| 정정·재문의율 | 고객이나 직원이 다시 연락해 고쳤는가 |
| 인계 성공률 | 필요한 담당자에게 맥락과 함께 연결됐는가 |
| 대화 품질 | 끼어들기, 과도한 침묵, 반복 질문, 고객 포기 |
| 현업 시간 | 통화 뒤 기록·검토·수정·재연락까지 포함한 투입 |
| 비용 | 완료 업무 한 건당 전화·음성·모델·도구·검토·운영 비용 |

Containment는 사람에게 넘기지 않은 비율로 쓰이기도 한다. 고객이 포기해서 끊은 통화를 성공으로 세지 않도록 정의를 확인한다. 짧은 통화나 높은 통화량이 반드시 좋은 성과는 아니다.

비용은 분당 음성 API 가격만으로 비교하지 않는다. 전화망, STT·TTS 또는 실시간 모델, 침묵·대기 과금, 재발신, 동시 통화 인프라, 녹취 저장, 평가·현업 검토 비용을 포함한다. 구체 가격표는 구현 경로를 정한 뒤 별도로 최신 확인한다.

## 11. 파일럿과 글의 구성 제안

### 파일럿

1. 반복 확인 업무 하나를 고른다. 도착 시간 확인이나 단순 예약 확인처럼 완료 조건을 정할 수 있는 범위가 출발점이다.
2. 실제 통화 표현·예외·업무 시스템 상태를 정리한다. 데이터 수집 권한과 비식별화도 함께 검토한다.
3. 발화 정정·침묵·소음·연결 실패·도구 실패를 포함한 시험 통화를 구성한다.
4. 초기에는 실행 범위를 좁히고 담당자가 결과를 검토한다. 사람 인계가 실제로 작동하는지 확인한다.
5. 완료율·재작업·고객 경험·총비용으로 기존 방식과 비교하고 검증한 범위만 넓힌다.

현업의 “이 표현이면 다시 물어봐야 한다”, “이 일정 변경은 창고에 먼저 확인해야 한다” 같은 판단을 재질문·확인·승인·인계 규칙으로 남기는 과정이 암묵지 자산화와 연결된다.

### 포스트 제목·전개

추천 제목: **“확인하고 다시 전화드릴게요”를 하루 종일 반복하고 있다면**

- 들어가며: 운전자·창고·고객에게 같은 정보를 전달하는 가상 운영 장면.
- 본문: 음성 에이전트와 기존 음성 기능의 차이, DHL·음식점·예약 사례.
- 기술: 두 처리 경로, 발화 종료·정정, 말과 실행 상태의 차이.
- 현업: 사람 인계, 한국어 테스트, 완료 기준과 비용.
- 나가며: 통화 뒤 입력·확인까지 줄이려면 현업 규칙과 연결 기술이 함께 필요하다는 상담 제안.

미래 CTA는 최근 반복 전화 업무 하나의 흐름을 함께 점검하자는 내용이 적합하다. 자사의 미확인 음성 에이전트 구축 실적이나 절감 보장은 만들지 않는다. 연락처: `contact@epsilondelta.ai`.
