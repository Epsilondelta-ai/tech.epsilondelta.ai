## 1. 핵심 결론

에이전트 메모리는 과거 상호작용과 작업에서 얻은 정보를 보존하고 다음 작업에 필요한 부분을 다시 제공하는 체계다. 대화 원문 저장뿐 아니라 유용한 정보 선별, 적용 범위 구분, 검색, 정정과 폐기까지 포함해 봐야 한다. LangChain은 메모리를 여러 실행에서 다시 사용할 수 있는 지속적인 컨텍스트로 설명한다. [S1][S2]

경영진에게 던질 질문은 **“AI가 얼마나 많이 기억하는가?”보다 “우리 업무에 필요한 내용을 올바른 범위에서 다시 쓰는가?”**다.

어제 고쳐준 형식을 오늘 또 설명하는 문제도 있지만, 지난번에만 허용한 예외를 모든 고객에게 적용하는 문제도 있다. 메모리 도입은 기억을 늘리는 일과 기억의 적용을 통제하는 일을 함께 다뤄야 한다.

후킹 제목 후보: **어제 가르쳐준 일을 오늘 또 설명하고 있다면: AI 에이전트의 메모리**.

## 2. 개념을 혼동하지 않기

### 2.1 현재 문맥, 대화 기록, 메모리

| 개념 | 역할 | 업무 예시 |
|---|---|---|
| 컨텍스트 | 이번 모델 호출에서 참고하는 입력 | 현재 요청, 검색 결과, 작업 지시 |
| 대화·실행 기록 | 실제로 무엇을 말하고 실행했는지 남긴 이력 | 사용자 메시지, 도구 결과, 수정 요청 |
| 작업 상태·체크포인트 | 진행 중 작업을 이어가는 데 필요한 상태 | 확인 완료 항목, 대기 중 승인, 다음 단계 |
| 장기 메모리 | 다른 실행에서도 재사용할 정보 | 고객 선호, 확인된 예외 사례, 업무 절차 |
| 모델 학습 | 모델 파라미터를 바꾸는 과정 | 별도의 학습 데이터·훈련·검증을 거친 업데이트 |

이 표는 역할 구분이다. 하나의 제품에서 여러 기능을 함께 제공할 수 있다. DB에 대화를 저장했다고 모델이 다음 호출에서 자동으로 읽는 것은 아니다. 읽어오는 경로가 필요하다. 반대로 메모리를 활용한다고 매번 모델 파라미터를 학습시키는 것도 아니다.

### 2.2 두 가지 분류 축

LangChain 문서는 기억을 불러오는 범위와 기억의 내용을 구분한다. [S1]

**범위:** 단기 메모리는 현재 스레드·작업의 문맥, 장기 메모리는 여러 세션에 걸쳐 활용할 정보다. 단기라는 말이 반드시 RAM 저장이나 짧은 보관 기간을 뜻하지는 않는다. 작업 상태를 DB에 영속화해 재개할 수도 있다.

**내용:** 사실·선호를 담는 의미 기억(semantic), 사건과 결과를 담는 경험 기억(episodic), 일을 수행하는 방법을 담는 절차 기억(procedural)으로 나눠 생각할 수 있다.

| 내용 | 가상의 업무 예 | 함께 남길 조건 |
|---|---|---|
| 사실·선호 | 고객 담당자는 표보다 요약을 먼저 원함 | 누가 확인했는가, 어느 고객·담당자인가 |
| 사건·경험 | 특정 거래에서 추가 확인 후 예외를 승인함 | 당시 조건, 승인자, 실제 결과 |
| 절차 | 보고서 작성 전 기간과 지표 정의 확인 | 기준 소유자, 버전, 적용 업무 |

‘단기·장기·의미·경험·절차’ 다섯 종류를 같은 수준으로 나열하지 않는다. 범위와 내용은 겹쳐 사용할 수 있는 분류다.

### 2.3 RAG·Skills·Context Graph와의 관계

- **RAG:** 검색한 자료를 응답에 사용하는 방식이다. 메모리의 읽기 단계에도 활용할 수 있다. RAG를 무조건 정적 문서 검색으로 한정하거나 메모리의 반대 개념으로 놓지 않는다.
- **Agent Skills:** 업무 지침과 참고자료·스크립트의 묶음. 검증한 교훈을 스킬 수정으로 반영할 수 있지만 모든 실행 기록이 스킬이 되는 것은 아니다.
- **Context Graph:** 사람·사건·관계·시간·출처를 연결해 메모리의 구조와 검색을 돕는 구현 선택지다. 메모리에 그래프 DB가 필수인 것은 아니다.
- **시맨틱 레이어:** 승인된 지표 정의와 계산 경로를 제공한다. 메모리에 남은 개인 선호가 공식 매출 계산식을 임의로 덮어쓰면 안 된다.
- **업무 시스템:** 잔액, 재고, 입금 상태처럼 최신성이 중요한 값은 원천 시스템에서 확인한다. 메모리는 확인할 대상과 과거 처리 맥락을 돕도록 구성한다.

이 관계 설명은 기존 포스트와 연결하기 위한 종합·설계 관점이다.

## 3. 무엇을 남길지 결정하는 방법

아래는 도입 설계 제안이다.

### 3.1 기억 후보와 확정 기준을 나눈다

같은 대화에 확인된 사실, 사용자 주장, AI의 추측, 임시 요청이 섞여 있다. 이를 모두 사실로 압축하면 잘못된 기억을 만들 수 있다. 예를 들어 ‘고객이 입금했다고 말했다’와 ‘은행 거래 내역에서 입금을 확인했다’는 다른 기록이다.

원문·실행 결과를 증거로 남기고 재사용할 기억은 별도 후보로 추출한다. 개인적인 출력 형식 선호는 비교적 가볍게 반영할 수 있지만, 전사 규칙·금액 기준·권한 변경은 담당자의 검토와 승인 후 반영하도록 나눈다.

### 3.2 범위를 먼저 붙인다

`조직 → 업무/프로젝트 → 고객 또는 사용자 → 작업/세션`처럼 적용 대상을 구분한다. 구현상 namespace나 ID는 정리 수단이며 그 자체가 인증·인가를 보장하지는 않는다. 요청자의 신원을 확인하고 실제 접근 제어와 연결해야 한다.

### 3.3 가상 예시: ‘이번 보고서에서만 제외’

사용자가 ‘이번 분기 보고서에서는 일회성 거래를 별도로 보여달라’고 했다고 하자. 이를 ‘이 고객의 모든 보고서에서 일회성 거래 제외’로 저장하면 의미가 달라진다.

남길 내용은 대상 고객, 해당 분기·보고서, 별도 표시라는 처리 방식, 요청자와 원문 근거다. 다음 보고서에서는 적용 조건을 확인한다. 반복 요청이 관측되더라도 공식 규칙으로 바꿀지는 기준 소유자가 결정한다.

## 4. 기술 구성: 기억의 읽기·쓰기 순환

참고 흐름 — 특정 제품의 필수 구조가 아닌 설계안:

`상호작용·실행 기록 → 기억 후보 추출 → 출처·범위·충돌 검사 → 승인/저장 → 권한·시간 조건으로 검색 → 이번 컨텍스트에 제공 → 사용 결과 평가 → 정정·만료·삭제`

### 4.1 쓰기 경로

대화에서 후보를 추출할 때 유형, 적용 대상, 근거, 유효 기간을 함께 생성한다. 기존 기록과 중복인지, 새 사실로 대체할지, 별개 사건인지 검사한다. 승인 전 후보와 확정된 기준을 구분한다.

응답 중 바로 저장하는 방식은 다음 요청에 빨리 반영할 수 있지만 지연이 늘 수 있다. 비동기로 추출·정리하면 응답 부담은 줄지만 저장 전 다음 요청이 올 수 있다. 같은 세션에서는 작업 상태를 사용하고 장기 저장 완료 여부를 추적하는 구성이 필요하다. LangChain 문서는 hot path와 background 쓰기를 구분한다. [S1]

### 4.2 읽기 경로

주제 유사도만으로 검색하지 않는다. 먼저 조직·사용자·프로젝트·권한 범위를 제한하고 유효 시점과 상태를 확인한다. 그 안에서 키워드, 벡터 유사도, 관계 탐색 등을 조합해 후보를 찾고 필요한 정보만 이번 입력에 넣는다.

‘지난주에 처리하지 못한 고객 건’은 완료 여부와 기간 필터가 중요하다. 문장이 비슷한 오래된 완료 건을 가져와도 업무에는 도움이 안 된다. 최종 답변이 사용한 기억의 ID와 출처를 추적할 수 있게 한다.

### 4.3 저장 방식 선택

| 방식 | 유용한 상황 | 주의할 점 |
|---|---|---|
| 파일·Markdown | 개인·프로젝트 지침, 작은 규모의 검토 가능한 메모 | 동시 수정, 권한, 크기 증가, 오래된 내용 |
| 관계형·문서·키값 저장소 | 명시적 속성, 상태, 고객별 정보 | 스키마와 갱신·중복 규칙 |
| 벡터 검색 | 표현이 달라도 관련 경험 찾기 | 숫자·ID·날짜와 권한 필터를 별도로 처리 |
| 그래프·시간 모델 | 관계 변화와 여러 사건의 연결 | 추출 오류, 엔터티 혼동, 운영 복잡도 |
| 혼합 구성 | 구조화 필터와 의미 검색을 함께 사용 | 저장소 간 정정·삭제 일관성 |

저장소 개수로 완성도를 판단하지 않는다. 현재 업무의 검색·수정·감사 요구에 맞춰 고른다.

### 4.4 요약과 장기 기억의 차이

Anthropic은 긴 작업에서 compaction, 구조화된 노트, 하위 에이전트 분업 등을 설명한다. 압축은 현재 문맥을 줄여 작업을 이어가도록 돕고, 외부 노트는 이후 다시 읽을 정보를 보존한다. [S3]

설계상 요약만 남기면 ‘이번에만’ 같은 조건이나 반대 의견이 사라질 수 있다. 원문 위치를 연결하고 중요한 결정·미확인 사항·제약을 구분한다. 긴 컨텍스트에 모든 기록을 다시 넣는 방법과 선택적 기억 검색을 비용·정확도 측면에서 비교한다.

### 4.5 최소 기록 구조 — 의사 명세

```yaml
memory_id: example-report-exception
tenant_id: example-org
scope: customer-and-report
subject_id: example-customer
kind: episodic
content: 해당 보고서에서 일회성 거래를 별도로 표시하도록 요청받음
source_ref: 승인된 원문 기록의 식별자
evidence_type: user_request
observed_at: 기록을 수집한 시각
valid_from: 적용 시작 시점
valid_until: 적용 종료 조건 또는 시점
status: candidate
owner: 검토 책임자
supersedes: 대체하는 이전 기억의 식별자
access_policy: 서버가 적용할 접근 정책 참조
```

이 예시는 실행 가능한 제품 설정이 아니다. `observed_at`과 실제 적용 시점을 나눠야 뒤늦게 들어온 정보도 처리할 수 있다. 신뢰 점수를 모델이 높게 적었다는 이유만으로 승인된 사실로 간주하지 않는다.

## 5. 구현 도구에서 확인한 기능

| 구현 | 공식 자료에서 확인한 범위 | 검토 관점 |
|---|---|---|
| LangGraph | 스레드 상태의 체크포인트, namespace·key 기반 장기 store [S1] | 작업 상태와 장기 기억의 경계 |
| LangMem | 대화 정보 추출, 기억 관리, 프롬프트 업데이트 도구 [S4] | 자동 절차 변경의 검증·승인 |
| Amazon Bedrock AgentCore Memory | 단기 이벤트·장기 기억 및 추출 전략 [S5] | 보관 정책, actor/session 구분, 권한 |
| Graphiti | 변화하는 관계를 시간 정보와 함께 표현하고 검색하는 그래프 [S6] | 유효 시점, 근거 연결, 관계 충돌 |
| Mem0 | 핵심 정보를 추출·갱신하는 메모리 구성과 평가 연구 [S7] | 원문 보존, 잘못된 기억의 수정, 비용 |

Zep의 과거 v2 Memory API 문서도 검색되지만 현재 API 사용법의 근거로 그대로 복사하지 않는다. 버전별 스레드·세션 인터페이스 차이는 실제 구현 시 확인한다. 메모리 제품의 ‘학습’은 저장 정보나 지침 갱신을 뜻할 수 있으므로 파라미터 학습과 구분한다.

## 6. 실제 활용 사례

### 6.1 S&P Global Market Intelligence — 내부 다중 에이전트의 상태·문맥

Amazon의 공식 소개에는 S&P Global Market Intelligence의 내부 플랫폼 Astra 사례가 나온다. 여러 전문 에이전트의 상태와 문맥을 관리하기 위해 AgentCore Memory를 중앙 체크포인트 계층으로 사용했다고 담당자가 설명한다. [S8]

같은 발언에서 경험 기억으로 과거 분석을 활용하는 기능은 앞으로의 활용으로 표현한다. 배포 시간이 수주에서 수분으로 줄었다는 설명도 AgentCore 전체에 대한 것이므로 메모리만의 생산성 효과로 인용하지 않는다.

**집필 활용:** 대규모 조직에서 에이전트가 일을 이어가도록 상태를 공유하는 현업 사례. 과거 경험을 학습해 분석 품질이 개선됐다는 실적으로 확대하지 않는다. 발표 당사자는 고객이지만 게시 주체는 공급사이며, 현재 전체 운영 규모를 추가 확인한 것은 아니다.

### 6.2 OpenNote — 학습 서비스에서 세션 간 연속성

Mem0 고객 사례는 OpenNote가 학습자의 이전 질문과 학습 흐름을 이어가기 위해 메모리를 도입했다고 설명한다. 전체 이력을 매번 넣던 방식에서 관련 요약을 활용하는 방식으로 바꿨으며 결과 표에는 프롬프트당 토큰 사용량 40% 감소를 제시한다. [S9]

최초 게시 2025-05-21, 페이지 표시 갱신일 2026-09-09. 제목의 비용 절감 표현보다 본문 표의 측정 대상인 토큰 사용량을 기준으로 인용한다. 성적 향상이나 서비스 전체 비용 40% 감소로 바꾸지 않는다.

**집필 활용:** 제품 경험의 연속성과 운영 비용을 함께 설명할 수 있는 교육 서비스 도입 사례. 사내 직원용 AX와는 적용 대상이 다르지만 반복 설명을 줄이는 메커니즘은 비교할 수 있다.

### 6.3 New Computer의 Dot — 저장보다 검색을 개선한 사례

LangChain의 2024-07-02 사례는 개인 AI 서비스 Dot의 기억 검색 개선을 설명한다. 상태·시작일·기한 같은 메타데이터를 붙이고 의미 검색, 키워드/BM25, 필터를 비교했다. 합성 사용자와 라벨링된 관련 기억으로 평가했다. [S10]

기존 기준 구현 대비 recall 50%, precision 40% 향상을 공개했다. 퍼센트포인트 상승이나 업무 성공률로 표현하지 않는다. 현재 서비스 운영 여부·규모는 이 과거 글로 확인되지 않는다.

**집필 활용:** ‘저장했는데 왜 기억하지 못하는가’를 검색·평가 문제로 설명하는 기술 보조 사례. 기업의 사내 도입 실적처럼 소개하지 않는다.

### 6.4 데모와 도입 사례를 구분

AWS 고객지원 튜토리얼은 고객 선호와 과거 문의를 저장·검색하는 코드와 이벤트 훅을 보여준다. 실제 고객센터의 운영 성과는 아니다. [S11]

Mem0의 다중 채널 지원 예시 역시 기술 구현 출발점으로 쓸 수 있지만 실존 기업 성과로 바꾸지 않는다. 제품 홈페이지의 고객 로고만으로 메모리 사용 방식이나 성과를 추정하지 않는다.

### 6.5 사례 우선순위와 자료의 한계

기업 내부 업무 사례는 S&P Global을 먼저 쓰고, OpenNote를 고객 서비스의 연속성 사례로 보강한다. Dot은 검색 품질 설명이 필요할 때 선택한다. 공개 웹 조사에서는 국내 명명 기업의 구현과 운영 성과를 함께 확인할 충분한 1차 자료를 확보하지 못했다. 대표가 추가로 제공한 익명 PE사 구축 경험은 12절에 별도 기록하며, 이 자료의 추가로 기존 사례 우선순위를 변경하지 않는다.

핵심 구분: 도입 실적의 범위, 고객 발언, 공급사의 제품 기능, 실험 결과. ‘에이전트 도입 성공’을 ‘메모리 덕분에 성공’으로 바꾸지 않는다.

## 7. 기억이 틀리거나 오래됐을 때

다음은 자체 설계·시험 시나리오다.

| 문제 | 원인 | 대응 |
|---|---|---|
| 다른 고객의 조건 재사용 | ID·조직·범위 혼동 | 인증된 신원으로 범위 제한, 교차 사용자 시험 |
| 지난 예외를 전사 정책으로 적용 | 사건과 규칙을 구분하지 않음 | 후보·일회성 예외·승인된 절차 분리 |
| 이미 해결한 문제를 다시 제안 | 상태·시간 필터 없음 | 완료 상태와 유효 시각으로 검색 |
| AI 추측이 확정 사실로 남음 | 자기 출력의 무검증 재수집 | 출처 유형 표시, 외부 근거 확인 |
| 두 에이전트가 같은 기억 덮어씀 | 동시 쓰기 충돌 | 버전 검사·조건부 갱신·충돌 처리 |
| 삭제한 내용이 다시 나타남 | 요약·색인·캐시·원문에서 재생성 | 파생 기록 추적, 재추출 차단과 삭제 검증 |
| 새 사실이 아직 검색되지 않음 | 비동기 처리 지연 | 처리 상태 추적, 현재 작업 상태와 보완 |
| 기억대로 실행했으나 이미 처리된 업무 | 메모리를 실행 사실의 최종 근거로 사용 | 원천 시스템 확인과 중복 실행 방지 |

공식 정책, 원천 시스템 상태, 개인 선호, 추론된 경험은 권위가 다르다. 최신이라는 이유만으로 낮은 신뢰도의 정보가 공식 규칙을 대체하지 않게 한다. 충돌을 해소할 근거가 없으면 담당자에게 확인한다.

## 8. 보안·삭제·거버넌스

Microsoft는 2026-02-10 실제 웹 링크와 프롬프트에서 특정 회사를 기억하고 우선 추천하도록 유도하는 시도를 관측했다고 공개했다. 31개 회사의 50개 이상 프롬프트를 제시하며 효과와 지속성은 플랫폼·시점마다 달랐다고 설명한다. 이는 50건의 침해 성공을 뜻하지 않는다. [S12]

외부 문서의 지시가 장기 기억으로 저장되면 이후 다른 작업에서도 영향을 줄 수 있다. Microsoft의 후속 보안 글과 OWASP 자료도 기억을 민감한 데이터이자 에이전트 행동에 영향을 주는 입력으로 다룬다. [S13][S14]

설계 권장 사항:

- 외부 문서에서 추출한 내용과 승인된 내부 지침을 별도 신뢰 수준으로 관리.
- 읽기·쓰기·수정·삭제 권한을 나누고 고위험 절차 변경은 사람의 검토를 거침.
- 사용자가 기억 내용을 확인·정정할 수 있게 하고 정책상 필요한 보관 기간을 정함.
- 비밀번호·토큰 등 비밀정보를 일반 기억에 저장하지 않음.
- 원문·요약·임베딩·캐시·체크포인트의 파생 관계를 추적해 삭제 범위를 확인.
- 접근 권한 철회 시 기존 검색 결과와 캐시가 계속 노출되지 않는지 시험.
- 의심 기록 격리, 버전 복구, 해당 기억을 사용한 실행의 추적 경로 마련.

AWS의 다중 테넌트 구현 예시는 애플리케이션 범위 지정에 더해 IAM 기반 ABAC를 함께 사용한다. namespace 이름만 나누는 것으로 권한 검사가 끝난다고 설명하지 않는다. [S15]

법령별 보관·삭제 의무는 업무·지역·계약에 따라 추가 확인해야 한다. 본 자료는 구체적인 법률 적합성 판정이 아닌 기술·운영 설계 자료다.

## 9. 평가: 기억을 찾았는가, 올바르게 썼는가

LongMemEval은 정보 추출, 여러 세션을 종합하는 추론, 시간 추론, 지식 갱신, 답변 유보를 평가하는 500개 질문을 제시한다. 기억 평가를 오래된 사실 하나의 회상으로만 좁히지 않는 참고 자료다. [S16]

Mem0 논문은 LoCoMo에서 기억 추출·갱신 구성을 비교한다. 이런 수치는 모델, 데이터셋, 평가자, 검색 범위와 지연 조건을 함께 봐야 한다. 벤치마크 개선 비율을 기업 업무의 투자수익률로 옮기지 않는다. [S7]

### 자사 시험 세트 — 제안

1. 어제 확정한 출력 형식을 새 세션에서도 적용하는가.
2. 이번 보고서에만 적용한 제외 조건을 다음 보고서에 무단 적용하지 않는가.
3. 담당자 변경을 알려준 뒤 과거 담당자에게 보내지 않는가.
4. 과거 실패 사례를 현재 조건과 구분해 활용하는가.
5. 다른 고객·직원의 기억이 검색되지 않는가.
6. 근거가 없는 질문에는 확인을 요청하는가.
7. 정정·삭제한 기억이 요약이나 캐시에서 다시 살아나지 않는가.
8. 악성 문서의 지시를 업무 규칙으로 저장하지 않는가.

측정할 항목: 필요한 기억의 recall, 가져온 기억의 precision, 잘못된 기억 저장률, 최신성·범위 준수, 최종 업무 성공률, 반복 설명 횟수, 담당자 수정 시간, 검색·추출 지연과 비용.

비교 조건은 메모리 없음, 전체 이력 제공, 선택적 메모리 제공 등으로 나눌 수 있다. 최근 정답을 평가 입력에 미리 넣는 누설을 피하고, 변경 전후에 같은 시험을 반복한다. ‘찾았지만 잘못 쓴 경우’와 ‘애초에 저장하지 못한 경우’를 분리해 원인을 본다.

## 10. 첫 도입과 포스트 기획

추천 시작점은 반복 설명과 수정이 잦은 업무 하나다. 고객별 보고 형식, 프로젝트의 미완료 작업, 상담에서 이미 확인한 조치 등이 후보가 될 수 있다. 이는 적용 예시이며 특정 기업의 도입 실적이 아니다.

담당자와 무엇을 기억할지, 어느 범위에 적용할지, 누가 정정할지부터 정한다. 작은 저장 구조와 조회 도구를 연결하고 예외·삭제·권한을 시험한다. 전사 지침 자동 수정은 초기 기본값으로 두지 않는다.

글 흐름 제안:

- 들어가며: 어제 고친 내용을 다시 설명하거나 지난 예외를 잘못 기억한 가상 장면.
- 개념: 대화 기록과 업무 기억, 범위와 내용의 두 분류 축.
- 기술: 기록→선별→검증→저장→검색→적용→정정의 순환.
- 사례: S&P Global의 상태·문맥, OpenNote의 사용자 연속성, 필요하면 Dot의 검색 평가.
- 실패: 잘못된 일반화·오래된 기억·권한·오염을 업무 사례로 설명.
- 나가며: 현업 교정을 검증한 지식·절차로 남기는 암묵지 자산화와 운영 지원.

엡실론델타 CTA는 기억할 업무 기준의 추출, 고객·프로젝트 범위 설계, 데이터 연결, 평가·정정·운영 지원으로 구체화한다. 연락처는 `contact@epsilondelta.ai`. ‘모든 대화를 저장하면 스스로 성장한다’는 약속은 피한다.

## 12. 직접 제공받은 프로젝트 경험 상세

추가 현장 자료: 엡실론델타 대표가 2026-09-18 직접 제공한 익명 PE사 구축 경험이다. 기존 글 구성과 사례 우선순위는 유지한다. 이 사례의 본문 배치와 비중은 아직 정하지 않았다. [S17]

### 12.1 현업이 원했던 ‘학습’

고객 PE사의 부사장이 직접 요청한 요구사항은, 에이전트가 사용할수록 자신의 선호와 업무 방식을 이해하고 그에 맞춰 일을 개선하는 것이었다. 부사장은 이를 ‘학습’이라고 표현하며 이런 식으로 일하는 방식을 학습시킬 수 있는지 물었다고 한다. [S17]

대표는 엔지니어의 입장에서 이 구현을 모델 훈련(train)으로 설명하지 않았다. 저장한 메모리를 컨텍스트로 다시 읽어 작업에 반영하는 방식이므로 **‘메모리 기반 개선’**이라는 표현을 사용했다.

집필에서는 현업의 표현을 틀린 말로 교정하는 장면으로 만들 필요가 없다. 현업은 점차 자신을 이해하는 업무 경험을 요구했고, 개발팀은 그것을 메모리 저장·재사용을 통한 개선으로 구현했다는 흐름이 중요하다.

### 12.2 실제로 나눈 네 가지 범위

| 메모리 범위 | 대표가 설명한 저장 대상 | 다시 읽어 개선할 대상 |
|---|---|---|
| Organization level | 조직이 일하는 방식과 특성 | 조직의 업무 방식에 맞춘 작업 |
| User level | 특정 사용자의 선호와 업무 스타일 | 해당 사용자를 위한 작업 방식 |
| Thread / chat session level | 특정 대화에서 기억해야 할 내용 | 그 대화에서 이어가는 작업 |
| Workspace level | 이번 딜 프로젝트에서 기억하고 개선해야 할 부분 | 해당 딜 프로젝트의 작업 |

이 표는 실제 설명받은 적용 범위를 정리한 것이다. 네 범위의 표기 순서가 권한 우선순위나 고정된 포함 관계를 뜻하지는 않는다. 하나의 사용자가 여러 딜에 참여할 수도 있으므로 범위 구분과 충돌 해결 규칙은 별개로 설명한다.

### 12.3 대표가 명명한 layered reflexion

이 프로젝트에서 **layered reflexion은 네 범위로 나눈 메모리를 다시 컨텍스트로 활용해 작업을 개선하는 방식을 가리키는 대표의 표현**이다. 문헌의 표준 명칭으로 소개하거나 원 논문이 제안한 계층 구조라고 설명하지 않는다. 사용자의 요청에 따라 해당 표현 자체를 별도로 검색하지 않았다.

대표의 설명에서 확인한 흐름:

`기억하고 개선할 내용 확인 → 해당 범위의 메모리에 저장 → 작업 시 메모리를 컨텍스트로 다시 읽음 → 그 내용을 반영해 작업 개선`

조직의 특성은 조직 범위에, 사용자 스타일은 사용자 범위에, 대화에서 이어갈 내용은 thread 범위에, 딜별 내용은 workspace 범위에 남겨 활용했다. 여기서 레이어를 나누는 이유는 단순히 저장 공간을 분리하는 데 있지 않다. **어떤 대상과 상황의 경험을 다음 작업에 적용할지 구분하는 것**으로 설명할 수 있다. 마지막 문장은 구현 설명을 바탕으로 한 편집적 해석이다.

대표가 별도로 설명하지 않은 저장소 제품, 자동 분류 방식, 회고 실행 시점, 평가 모델, 승인 절차, 충돌 시 우선순위는 구현 사실로 추가하지 않는다. 효과에 관한 정량 수치나 부사장의 사후 만족 발언도 제공받지 않았다.

### 12.4 설명을 돕는 예시 — 실제 고객 발언·정책 아님

네 범위를 독자에게 풀어 설명할 때 아래와 같은 가상 예시를 사용할 수 있다. 실제로 PE사에서 저장했던 내용이라고 단정하지 않는다.

- 조직: 투자 검토 자료에서는 사실과 가정을 구분해 정리한다는 공통 업무 기준.
- 사용자: 특정 사용자는 세부 분석 전에 핵심 쟁점부터 보고 싶어 한다는 선호.
- Thread: 이번 대화에서는 두 가지 가정 중 어느 것을 기준으로 계산하기로 했는지.
- Workspace: 현재 딜에서 추가 확인해야 하는 사항과 이전 검토에서 바로잡은 내용.

thread의 임시 조건을 조직 규칙으로 일반화하지 않고, 한 딜에서 얻은 내용을 다른 딜에 적용하기 전 범위를 확인한다는 설명에 활용할 수 있다. 이를 실제 구현된 자동 통제 기능이라고 쓰지는 않는다.

### 12.5 ‘메모리가 개선의 엔진’이라는 저자의 관점

대표는 메모리 기반 개선을 중요하게 보며, 메모리가 에이전트 개선의 엔진 역할을 할 수 있다고 생각한다. 이는 저자의 기술·운영 관점으로 기록한다. [S17]

그 관점을 풀어 쓰면: 사람이 수정해준 내용이 현재 답변에만 반영되면 다음 작업에서 같은 설명을 반복할 수 있다. 교정 내용과 적용 조건을 기억하고 필요한 작업에서 다시 읽으면 이전 경험을 다음 수행에 반영할 수 있다. 이때 메모리는 대화를 보관하는 곳에 더해 개선 내용을 다음 작업에 전달하는 역할을 한다.

본문에서는 ‘메모리만 있으면 자동으로 좋아진다’고 단정하기보다 **무엇을 남기고 어느 범위에서 다시 쓰느냐에 따라 개선을 이어갈 수 있다**는 저자의 주장으로 전개하면 좋다.

## 13. Reflexion 추가 조사

### 13.1 원 논문의 방식

Reflexion은 Shinn 등 연구진의 NeurIPS 2023 논문이다. 모델 가중치를 갱신하는 대신 수행 결과에 관한 언어 피드백을 경험 메모리에 남기고 다음 시도에서 활용한다. [S18]

논문은 Actor(행동·답변 생성), Evaluator(수행 평가), Self-Reflection(다음 시도에 유용한 회고 생성)을 구분한다. 평가 신호에는 성공 여부·점수·언어 피드백 등이 쓰일 수 있고, 평가 방식도 과업에 따라 규칙이나 LLM 등으로 달라진다. 역할을 나눴다는 것이 반드시 서로 다른 기반 모델 세 개를 구매·운영해야 한다는 뜻은 아니다.

`작업 수행 → 결과 평가 → 바꿀 점을 언어로 정리 → 경험 메모리 저장 → 다음 시도에 제공`

실행 이력과 회고를 구분하며, 실험에서는 저장할 경험 수를 제한하기도 한다. 의사결정·질의응답·코딩 과업을 평가한 연구다. 이번 글에서는 벤치마크 점수보다 실패와 피드백을 다음 시도의 컨텍스트로 연결한다는 원리를 활용한다. 회고의 정확성과 평가 신호의 품질이 중요하다. [S18][S19]

### 13.2 PE사 구현과 연결해 설명할 범위

공통 관점은 모델을 재훈련하지 않고 이전 작업에서 얻은 정보를 메모리와 컨텍스트로 활용한다는 데 있다. PE사 사례에서는 그 기억의 적용 범위를 조직·사용자·대화·딜 프로젝트로 나눴다.

다만 제공받은 설명만으로 원 논문의 Actor–Evaluator–Self-Reflection 구조를 그대로 구현했다고 단정하지 않는다. 본문에서는 **Reflexion의 원리를 설명한 뒤, 우리가 구축한 범위별 메모리 기반 개선을 별도의 현장 설계로 소개**하는 편이 정확하다. 원 논문의 직접 재현이나 학술적 신규 알고리즘 검증을 주장하지 않는다.

### 13.3 Train·In-context Learning·메모리 기반 개선

| 표현 | 이번 내용에서 설명할 의미 |
|---|---|
| 고객이 말한 학습 | 사용자의 스타일과 업무 방식을 점차 이해하고 개선해주기를 바라는 현업 요구 |
| 모델 훈련·파인튜닝 | 파라미터 갱신. 대표가 설명한 개선 방식은 여기에 해당하지 않음 |
| 컨텍스트를 이용한 적응 | 메모리에서 불러온 내용을 현재 입력으로 활용해 수행을 달리하는 방식 |
| 메모리 기반 개선 | 무엇을 저장·갱신하고 다음 작업에서 어떻게 활용할지까지 포함한 구현 설명 |

In-context learning은 문헌에서 예시·지시·경험을 입력으로 받아 가중치 변경 없이 적응하는 현상을 넓게 설명하는 데 쓰인다. Reflexion 논문도 관련 연구와 이 관점을 연결한다. 따라서 ‘ICL과 완전히 무관하다’고 단정할 필요도 없고, 해당 시스템 전체를 단순한 few-shot ICL로 축약할 필요도 없다. 컨텍스트를 활용하는 모델의 작동과 그 컨텍스트를 지속적으로 관리하는 시스템을 구분하고, 고객에게는 ‘메모리 기반 개선’으로 설명하면 의도가 명확하다.

### 13.4 후속 구현·운영 논의용 질문

아래는 추가로 논의할 설계 질문이며 PE사에 이미 구현했다고 확인한 기능이 아니다.

- 사용자 선호와 조직의 필수 기준이 충돌할 때 무엇을 적용하는가?
- 딜의 예외를 다른 딜에 재사용하려면 어떤 검토를 거치는가?
- 회고에서 추출한 교훈이 틀렸을 때 어느 기록으로 되돌리는가?
- 한 번의 교정을 장기 선호로 저장할지, 임시 요청으로 남길지 어떻게 구분하는가?
- 메모리 반영 전후의 반복 수정·작업 품질을 어떤 사례로 비교하는가?

이 질문은 자료의 구현 세부를 보강할 때 사용한다. 블로그에 모조리 경고·해명 목록으로 넣기보다 본문 흐름에 필요한 항목만 선택한다.
