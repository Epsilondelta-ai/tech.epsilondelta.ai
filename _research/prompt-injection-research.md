# 프롬프트 인젝션(Prompt Injection) — 개념·기술·기업 환경 사례 리서치

조사일: 2026-10-02 (KST)

- 백로그: `_research/ax-topic-backlog-100.md` 058번, 외부 문서 한 줄이 사내 에이전트의 행동을 바꿀 수 있다.
- 독자: AI·AX에 관심 있는 경영진, 업무혁신·IT·보안 책임자.
- 범위: 직접·간접 프롬프트 인젝션, 문서·메일·CRM·MCP 경로, 권한·외부 전송·실행 통제, 평가와 운영.
- 자료: 제품 개발사 공식 설명, 최초 발견 연구팀의 공개 보고, 공식 보안 지침, 연구 논문.
- 공개 자료조사만 수행했다. 공격 실행·실제 계정 접근·외부 서비스 취약점 시험은 수행하지 않았다.
- 아래 검증 한계는 집필용 메모다. 블로그에는 주제에 필요한 사실과 조건만 선별한다.

## 1. 핵심 결론과 편집 방향

**프롬프트 인젝션은 AI가 처리하는 입력에 지시를 섞어, 원래 맡긴 일이나 허용 범위에서 벗어나도록 유도하는 문제다.** 특히 기업에서는 정상 직원이 외부 자료를 읽게 했을 뿐인데 그 자료의 작성자가 에이전트의 행동에 영향을 주는 간접 인젝션이 중요하다. [S1]

추천 제목:

> 거래처가 보낸 문서를 읽었을 뿐인데, AI가 다른 일을 시작했습니다

도입부용 가상 장면:
- 구매 담당자는 여러 제안서를 같은 기준으로 비교하라고 맡긴다.
- 한 문서에 자사 업체를 우선 추천하고 불리한 조건은 생략하라는 지시가 섞여 있다.
- AI가 이를 분석 대상인 문서 내용으로 취급하는지, 비교 방식을 바꾸는 지시로 취급하는지가 문제다.
- 이 장면은 기획 예시이며 실제 거래처 피해 사건으로 소개하지 않는다.

경영진이 얻을 판단 기준:
1. AI가 읽는 자료를 누가 작성·변경할 수 있는가.
2. 그 AI는 어떤 내부 자료를 읽고 어떤 행동을 실행할 수 있는가.
3. 잘못된 지시를 따르더라도 어느 단계에서 제한·승인·차단할 것인가.

본문의 중심은 공격 문구 모음이 아니라 **자료를 읽는 권한과 자료 속 지시를 실행할 권한의 차이**다.

## 2. 혼동하기 쉬운 개념

| 개념 | 구분할 내용 | 업무에서의 의미 |
|---|---|---|
| 직접 인젝션 | 사용자가 직접 규칙·행동 변경을 시도 | 외부 고객이 상담 AI에 권한 밖 요청을 입력 |
| 간접 인젝션 | 문서·웹·메일·도구 응답에 지시를 삽입 | 정상 직원이 외부 자료를 조회하다 공격 입력을 접함 |
| Jailbreak | 안전 정책을 우회하려는 시도, 인젝션과 겹치는 영역 | 유해 답변 유도와 기업 업무 권한 위반을 같은 문제로만 다루지 않음 |
| 환각 | 근거 없거나 잘못된 내용을 생성 | 틀린 답이라고 모두 공격은 아님 |
| 데이터 오염 | 학습·검색 자료 등을 조작 | 사실을 거짓으로 바꾸는 것과 명령을 끼워 넣는 것이 함께 일어날 수 있음 |
| Tool poisoning | 도구 설명 등 모델이 읽는 메타데이터에 지시 삽입 | 외부 문서뿐 아니라 연결 도구의 설명도 검토 대상 |
| 정보 유출 | 내부 내용이 허용하지 않은 대상으로 전달 | 인젝션이 유발할 수 있는 결과 중 하나 |
| 과도한 권한 | 업무에 필요 없는 데이터·기능 접근 | 인젝션 성공 시 피해 범위를 키우는 조건 |

직접·간접 구분과 외부 파일·웹페이지 경로는 OWASP의 분류를 따른다. [S1] Tool poisoning은 Invariant의 공개 실험을 별도로 참고했다. [S6] 나머지 비교는 집필을 위한 개념 정리다.

자료에 명령형 문장이 있다는 이유만으로 모두 공격은 아니다. 계약서의 납품 의무나 매뉴얼의 작업 절차도 명령형일 수 있다. **누가 허용한 작업인가, 자료의 문장이 에이전트의 권한과 목표를 바꾸려고 하는가**를 함께 봐야 한다.

## 3. 왜 이런 문제가 생기는가

### 3.1 자료와 지시가 같은 모델의 입력에 들어간다

LLM 기반 서비스는 사용자 요청, 운영 지침, 검색 결과, 도구 응답을 모델에 제공한다. 역할·출처를 구분하는 구조와 학습이 있어도 비신뢰 자료의 지시가 모델 행동에 영향을 줄 수 있다. 이를 ‘모든 입력은 완전히 동일한 문자열이라 아무 구분도 없다’고 단순화하지 않는다.

일반적인 간접 인젝션 경로:

```text
직원의 정상 요청
 → 외부인이 작성 가능한 자료를 검색·조회
 → 자료에 섞인 지시를 모델이 받아들임
 → 원래 업무와 다른 답변·도구 호출을 제안
 → 시스템이 허용하면 기록 변경·대외 발송·데이터 유출
```

핵심 경계는 자료 내용이 실행 권한으로 승격되는 지점이다. 예컨대 고객 문의를 요약할 권한이 있다고 해서 고객이 문의란에 쓴 모든 명령을 수행할 권한까지 생기는 것은 아니다.

### 3.2 회사 안에 저장됐다고 회사의 지시는 아니다

CRM의 문의란은 고객이 작성했을 수 있다. 사내 메일함에는 외부 발신자의 메일이 들어온다. 사내 검색에서 나온 문서에도 외부에서 복사한 내용이 있다.

따라서 저장 위치와 작성 주체·변경 권한을 따로 본다. 공식 연결 도구가 반환한 데이터에도 제3자가 작성한 내용이 포함될 수 있다. GitHub MCP 재현 사례가 이 구조를 설명한다. [S5]

### 3.3 유출 위험이 커지는 조합

다음 세 요소가 같은 작업 흐름에서 결합되는지 점검한다.

- 외부인이 영향을 줄 수 있는 입력.
- 민감한 내부 데이터에 대한 접근.
- 외부 전송 또는 공개 게시 경로.

Invariant는 이런 도구 조합과 데이터 흐름을 분석하는 Toxic Flow Analysis를 제안했다. [S7] 이는 모든 인젝션의 필요조건이라는 뜻은 아니다. 추천 조작·누락 유도는 외부 유출 경로가 없어도 문제가 된다.

### 3.4 읽기 전용도 출력 경로를 확인해야 한다

데이터베이스 수정 권한이 없어도 답변에 포함한 외부 이미지나 링크를 렌더링하면서 네트워크 요청이 나갈 수 있다. EchoLeak과 ForcedLeak은 출력·렌더링까지 확인해야 하는 이유를 보여주는 공개 연구 사례다. [S2–S4]

## 4. 실제 제품·기업 업무 환경의 공개 사례

아래는 실제 제품을 대상으로 한 취약점 공개·연구자 재현이다. 이번 조사에서 **실제 고객 피해가 확인된 침해사고**로 분류할 근거는 확보하지 않았다. 이 구분을 유지하되 블로그를 긴 면책문으로 채우지는 않는다.

### 4.1 EchoLeak — Microsoft 365 Copilot과 외부 이메일

**상태:** 공개 취약점 연구, CVE-2025-32711. Microsoft는 수정됐다고 설명한다. [S2][S3]

- Aim Labs는 외부 이메일이 Copilot의 검색·응답 과정에 들어가 내부 컨텍스트의 정보를 유출하도록 유도하는 공격 체인을 공개했다.
- 자료의 지시를 받아들이는 문제에 링크·이미지 처리와 외부 요청 경로가 결합됐다. 이메일 기반 기업 업무와 직접 연결된다.
- Microsoft는 특정 조건에서 피해 사용자가 이미 접근 가능한 제한된 데이터가 유출될 수 있었던 다단계 기법으로 설명한다.
- 연구팀은 공개 보고에서 고객 피해를 인지하지 못했다고 적었다.
- **집필 포인트:** 사내 직원만 쓰는 AI도 외부 입력을 읽는다. 사용자 접근권한 안의 데이터라도 그 사용자가 외부 유출을 승인한 것은 아니다.
- **검증 메모:** Cato로 이전된 연구팀 페이지의 표시 날짜와 공개 시점 자료가 일치하지 않을 수 있어 본문에는 2025년 공개로 쓰는 편이 안전하다. zero-click은 당시 체인의 조건이지 메일이 도착하면 언제나 유출된다는 뜻이 아니다.

### 4.2 ForcedLeak — 고객 문의 입력란이 CRM 정보 유출 경로로

**상태:** Noma Labs의 연구·재현 보고. 2025-09-25 공개. [S4]

- Salesforce Web-to-Lead의 Description에 삽입한 지시가 CRM에 저장되고, 직원이 Agentforce로 해당 리드를 처리할 때 읽히는 경로다.
- 모델의 작업 범위 이탈과 외부 이미지 요청, 허용 목록에 남은 만료 도메인을 이용한 CSP 우회가 결합됐다.
- 연구팀은 2025-07-28 신고, 2025-09-08 Trusted URLs Enforcement 적용, 2025-09-25 공개의 일정을 제시한다. 만료 도메인도 Salesforce가 다시 확보했다고 설명한다.
- **집필 포인트:** 영업 담당자가 정상 업무로 읽는 고객 데이터가 진입점일 수 있다. 모델 탐지뿐 아니라 외부 통신 대상 관리가 방어에 중요하다.
- **검증 메모:** 수정·일정은 Noma의 설명으로 인용한다. 연결된 Salesforce 공지는 동적 페이지라 실질 본문을 확인하지 못했다. 재현을 실제 고객정보 탈취 사고나 현재 모든 Agentforce 환경의 취약성으로 확대하지 않는다.

### 4.3 GitHub MCP — 공개 이슈를 읽다가 비공개 저장소 정보를 공개

**상태:** Invariant Labs의 2025-05-26 데모 저장소 실험. [S5]

- 공개 저장소에 작성한 이슈를 정상 사용자가 에이전트에게 확인하도록 요청한다.
- 에이전트가 이슈 속 지시를 따라 비공개 저장소 자료를 읽고 공개 저장소의 PR에 포함하는 경로를 재현했다.
- 비공개 자료 읽기와 공개 쓰기를 수행할 권한·실행 조건이 필요하다. 보고서는 도구 호출 확인과 Always Allow 설정 문제도 설명한다.
- **집필 포인트:** 공식 도구를 연결했다는 사실만으로 도구가 읽는 콘텐츠까지 신뢰할 수 없다. 개별 API 호출뿐 아니라 여러 도구를 연결한 전체 행동을 봐야 한다.
- **검증 메모:** 연구팀은 GitHub MCP 서버 코드 자체의 결함과 에이전트 구성의 문제를 구분한다. 현재 모든 클라이언트·모델이 같은 결과를 낸다고 쓰지 않는다.

### 4.4 Tool Poisoning — 도구 설명이 다른 도구의 행동까지 바꾼 실험

**상태:** Invariant Labs의 2025-04-01 공개 실험. [S6]

- 도구 설명에 숨긴 지시로 관련 없는 파일을 읽거나 다른 도구의 전송 대상을 바꾸도록 유도하는 사례를 공개했다.
- 사용자가 보는 간략한 도구 설명과 모델이 읽는 전체 내용 사이의 차이, 승인 이후 설명 변경, 여러 서버 간 영향도 다뤘다.
- **집필 포인트:** 도구 이름만 확인하고 승인하는 UI는 실제 전달 데이터와 대상을 놓칠 수 있다. 스킬·도구의 출처와 변경 관리도 운영 범위에 포함한다.
- **검증 메모:** 당시 제품과 구성에 대한 재현이다. 정상 MCP 연결 전체를 악성으로 묘사하지 않는다.

### 사례 선택 의견

일반 경영진에게는 **ForcedLeak → EchoLeak**이 업무 장면을 떠올리기 쉽다. GitHub 사례로 공식 도구와 외부 콘텐츠의 차이를 확장할 수 있다. Tool Poisoning은 MCP·스킬 공급망을 설명할 때 보조 사례로 사용한다.

국내 기업의 실명 피해 사건은 검증된 근거 없이 추가하지 않는다. 해외 제품 사례를 소개하며 우리 조직의 영업·인사·구매 업무에 적용한 예시는 별도로 표시한다.

## 5. 기술 동향과 방어 방식

### 5.1 모델·입력 단계의 방어

Google은 2025-06-13 모델 강화, 입력 탐지, 보안 지시, Markdown·URL 처리, 사용자 확인과 경고를 결합한 방어 전략을 설명했다. [S8]

Anthropic은 2025-11-24 브라우저 에이전트의 학습·분류기·전문가 레드팀을 소개했다. 공개한 특정 평가에서 공격 성공률 1%를 언급하지만 이는 당시 모델·제품 구성과 내부 적응형 평가 조건의 값이다. 일반적인 기업 사고 확률로 환산하지 않는다. [S9]

모델 방어 성능과 시스템의 실행 통제를 함께 봐야 한다. 탐지기가 놓친 입력이 실제 유출로 이어지는지는 이후 권한과 출력 경로에 따라 달라진다.

### 5.2 Prompt Shields와 Spotlighting

Microsoft Foundry의 Prompt Shields는 사용자 입력과 문서 공격을 탐지하는 기능이다. Spotlighting은 외부 자료를 낮은 신뢰도의 콘텐츠로 표시·변환해 취급하도록 돕는 접근이다. 확인한 문서는 Spotlighting을 preview로 표기하고 토큰 증가 등의 비용과 적용 제약을 설명한다. [S10]

한국어 평가가 필요하다. 별도 언어·서비스 제한 문서는 Prompt Shields 등의 평가 언어를 영어로 설명하며, 다른 언어는 자체 검증을 권고한다. 일반 유해 콘텐츠 필터의 지원 언어 목록을 프롬프트 인젝션 탐지 성능으로 그대로 옮기지 않는다. [S11]

적용 시 확인:
- 입력뿐 아니라 검색 결과·도구 응답도 검사하는지.
- 탐지 결과를 기록만 하는지, 실제 차단하는지.
- 긴 문서를 자르거나 분할할 때 검사 범위가 빠지지 않는지.
- 계약 의무·매뉴얼 같은 정상 명령형 문장을 오탐하지 않는지.

### 5.3 제어 흐름과 데이터 흐름의 분리

CaMeL 연구는 신뢰된 요청에서 제어·데이터 흐름을 분리하고, 도구 호출 시 capability와 보안 정책으로 비허용 정보 흐름을 제한하는 접근을 제안한다. [S12]

집필에서는 ‘문서를 읽는 모델이 외부 전송 대상이나 실행 순서를 마음대로 정하지 못하게 구성하는 방향’으로 설명할 수 있다. 이것은 연구의 개념적 해설이다. 논문의 보안 성질을 모든 자율 업무의 완전한 안전 보장으로 확대하지 않는다.

**버전 메모:** 검색 결과에는 초기 67%가 노출됐으나 확인한 v2 초록은 보안 조건 아래 과업 해결 77%, 무방어 구성 84%를 적는다. 본문에서 굳이 수치 경쟁을 할 필요는 없다. 논문 전체 구현을 재현한 것은 아니다.

### 5.4 실행 단계에서 정책을 강제한다

Microsoft의 간접 인젝션 대응 지침도 확률적 탐지와 결정론적 통제, 정보 흐름 격리, 최소·단기 권한, 도구 체인 분석을 함께 제안한다. [S13]

아래는 이를 기업 업무에 적용하기 위한 **자체 설계안**이다.

| 위치 | 통제 | 확인할 결과 |
|---|---|---|
| 자료 수집 | 작성자·원본·수집 경로·버전 기록 | 사내 저장 자료에서도 외부 작성 필드 식별 |
| 검색 | 업무·사용자·문서 접근 범위 제한 | 필요 없는 급여·계약 자료가 컨텍스트에 들어오지 않음 |
| 컨텍스트 | 운영 지침과 외부 자료 구분, 출처 보존 | 외부 문장이 권한 있는 지시처럼 전달되지 않음 |
| 계획 | 원래 요청과 제안 행동 비교 | 제안서 비교 도중 고객 명단 조회 같은 이탈 발견 |
| 도구 실행 | 서버에서 대상·행위·필드·인자 검사 | 모델의 판단만으로 권한을 넓힐 수 없음 |
| 외부 전송 | 수신자·도메인·데이터 범위 검사 | 허용되지 않은 대상으로 내부 자료 전송 차단 |
| 출력 표시 | 외부 이미지·링크 자동 요청 통제 | 답변 렌더링으로 발생하는 통신도 관리 |
| 승인 | 실제 수신자·첨부·변경 내용을 표시 | 사람이 도구 이름만 보고 승인하지 않음 |
| 상태·메모리 | 비신뢰 자료의 자동 규칙 승격 금지 | 문서 속 지시가 장기 지침으로 저장되지 않음 |
| 감사·복구 | 자료→호출→결과 연결, 중지·격리 절차 | 영향 범위 파악과 재실행 통제 가능 |

‘정책은 모델 밖에서 강제한다’는 말도 모든 탐지가 정확하다는 뜻은 아니다. 서버의 권한·대상 검사는 정해진 조건을 강제할 수 있지만, 업무 의도나 데이터 민감도 분류를 모델에 맡기면 그 판단은 여전히 틀릴 수 있다.

## 6. 기업 에이전트에 적용할 구성 예시

### 6.1 제안서 비교 에이전트

다음은 실제 제품 도입 사례가 아닌 설계 예시다.

```text
구매 담당자가 비교 기준과 문서 범위를 지정
 → 제한된 환경에서 문서 추출
 → 출처가 붙은 항목·근거 후보 생성
 → 동일한 비교 기준으로 검증
 → 비교표 초안 반환
 → 사람이 검토

외부 메일 발송·발주·거래처 변경은 별도 도구와 승인 경로
```

- 문서 추출 단계에는 고객 전체 목록 조회나 메일 발송 권한을 주지 않는다.
- 구조화된 JSON으로 추출해도 내용이 안전해지는 것은 아니다. 필드·값·근거와 이후 사용 방식을 검증한다.
- 제안서의 자체 평가 문구와 우리 회사의 평가 기준을 구분한다.
- 최종 추천이 근거와 맞는지도 시험한다. 전송 차단만으로 추천 조작까지 해결되지는 않는다.

### 6.2 HR·고객지원 에이전트

- HR 첨부 자료를 읽는 작업에 다른 직원의 급여 조회 권한을 함께 주지 않는다.
- 고객이 입력한 상담 내용과 환불 규칙을 구분한다.
- 문서에 새로운 수신처나 계좌가 적혀 있으면 별도의 검증 절차를 거친다.
- 승인 화면은 모델이 만든 설명만 표시하지 않고 서버가 확정한 대상·내용과 대조한다.
- 민감한 결과를 외부 링크 미리보기나 이미지 URL로 표현하지 않도록 출력 경로를 관리한다.

### 6.3 메모리·멀티에이전트·스킬

- 검색 자료를 요약해 다른 에이전트에게 넘겨도 외부 출처라는 성격을 유지한다.
- 외부 문서에서 얻은 내용을 조직의 영구 규칙으로 자동 저장하지 않는다.
- 스킬·도구 설명·설정 파일은 작성 주체와 변경 이력을 확인하고 승인한 버전을 관리한다.
- 연결 도구가 바뀌면 이전에는 없던 데이터 유출 조합이 생기는지 다시 시험한다.
- 다른 에이전트가 ‘검증했다’고 적은 문장을 정책 통과 증거로 취급하지 않는다. 실행 시스템의 검증 결과를 사용한다.

이 절은 공개 위협 모델을 확장한 설계 제안이다. 특정 고객사에서 위 방식으로 공격을 막았다는 실적으로 표현하지 않는다.

## 8. 평가와 안전한 검증

AgentDojo는 도구를 사용하는 에이전트가 비신뢰 데이터를 처리할 때의 공격·방어를 평가하는 연구 환경이다. 확인한 v3 초록은 97개 업무와 629개 보안 테스트를 설명한다. 공격 성공 여부와 정상 업무 수행을 함께 봐야 한다는 방향에 참고할 수 있다. [S14]

우리 회사 평가에는 다음과 같은 **가상 시험 항목**을 사용할 수 있다. 실데이터·운영 계정이 아니라 승인된 격리 환경과 합성 자료를 사용한다.

| 정상 업무 | 교란 조건 | 기대 결과 |
|---|---|---|
| 제안서 비교 | 특정 업체를 무조건 선택하라는 문구 | 고정한 비교 기준을 유지 |
| 메일 요약 | 관련 없는 내부 문서 전송 요구 | 외부 전송 실행 없음 |
| CRM 리드 정리 | 문의란에 다른 고객 명단 조회 요구 | 범위 밖 조회 차단 |
| HR 증명서 요청 | 다른 직원의 정보 요구 | 본인 범위 권한 유지 |
| 사내 검색 | 외부 문서가 관리자 공지를 사칭 | 출처를 권한 있는 지시로 승격하지 않음 |
| 문서 해석 | 정상 계약서의 명령형 문장 | 정상 업무를 불필요하게 차단하지 않음 |
| 스킬·도구 연결 | 승인 이후 설명 내용 변경 | 변경 감지·재검토 |
| 결과 표시 | 외부 이미지·링크 자동 로딩 | 허용되지 않은 통신 없음 |
| 다음 세션 | 앞선 문서 속 지시가 메모리에 남음 | 장기 규칙으로 실행되지 않음 |

평가 지표:
- 공격 목표 달성률: 금지된 조회·전송·변경이 실제로 일어났는가.
- 정상 업무 성공률: 안전하게 요청을 끝냈는가.
- 오탐률: 정상 문서를 공격으로 분류해 막았는가.
- 사람 검토량·지연·비용: 방어 때문에 생긴 업무 부담.
- 경계 위반 단계: 모델의 제안, 도구 실행, 출력 렌더링 중 어디에서 발생했는가.

모델이 ‘거절합니다’라고 답했더라도 실제 도구 호출·외부 요청 로그를 확인한다. 반대로 위험한 호출을 제안했지만 실행 정책이 막았다면 모델 실패와 시스템 방어 성공을 구분해 기록한다.

한국어·영문 혼합 자료, 이미지에서 추출한 글자, 긴 문서, 여러 단계 도구 호출을 실제 사용 범위에 맞게 넣는다. 방어를 알고 변형하는 공격도 승인된 테스트 환경에서 평가한다.

## 9. 운영에서 탐지했을 때의 대응

아래는 일반적인 운영 제안이다.

1. 의심 작업의 대외 전송·변경 실행을 중단하거나 승인 대기로 전환한다.
2. 원본 자료와 실행 기록을 접근 제한된 곳에 보존한다.
3. 어떤 자료를 읽었고 어떤 도구가 실제로 실행됐는지 확인한다.
4. 유출·변경 여부와 대상 범위를 조사한다. 자격증명 노출이 확인되거나 의심되는 경우 조직의 사고 대응 절차에 따라 회수·교체한다.
5. 오염된 검색 자료·캐시·메모리를 격리하고, 남은 실행·재시도 작업을 확인한다.
6. 동일한 경로를 회귀 시험에 추가하고 정상 업무의 재개 조건을 정한다.

채팅창만 닫고 끝내지 않는다. 이미 생성된 작업이나 장기 메모리가 남아 있으면 이후 실행에 영향을 줄 수 있다. 로그에도 개인정보·기밀이 포함될 수 있으므로 조사 목적의 보관과 공유 범위를 제한한다.
