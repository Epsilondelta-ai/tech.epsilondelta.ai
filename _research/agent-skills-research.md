# [사전 조사] Agent Skills란? 범용 에이전트에 우리 회사 일을 가르치는 방법

- 조사 기준일: 2026-09-08
- 대상: AI·AX에 관심 있는 경영진과 현업·기술 책임자
- 목적: 개념·기술·실제 활용 사례를 바탕으로 후속 테크블로그 포스트를 기획한다.
- 연결 주제: 암묵지 자산화 → FDE의 현업 공동개발 → 확인한 업무 방법을 Skills로 정리·배포·운영
- 근거: 공식 사양·제품 문서, 기업·실무자의 직접 발표, 공개 구현, 연구 원문을 구분한다.
- 문서 성격: 리서치 노트다. 예시 스킬, 도입 단계, 평가표는 별도로 표시한 작성자의 제안이며 실제 고객 구축 실적이 아니다.

## 0. 먼저 읽을 조사 결론

### 이 글에서 사용할 정의

> Agent Skills는 업무 지침과 예시, 참고자료, 필요하면 실행 스크립트와 양식까지 묶어, 에이전트가 해당 업무를 할 때 찾아 읽고 사용하도록 만든 재사용 가능한 패키지다.

공식 사양은 이를 가벼운 공개 포맷으로 설명한다. 핵심 파일은 `SKILL.md`다. [Agent Skills 개요][overview]

### 경영진에게 전달할 핵심

1. **‘가르친다’는 실행 시점의 지침 제공을 뜻한다.** 파일을 설치하는 것만으로 모델 가중치가 바뀌거나 모든 피드백을 영구 학습하는 것은 아니다. [Anthropic의 기술 소개][intro]
2. **회사의 확인된 업무 방법을 배포할 수 있다.** 무엇을 확인하고 어떤 순서로 처리하며 어떤 결과를 만들어야 하는지를 자료·코드와 함께 관리한다. 최신 가격·계약·승인 상태는 연결된 업무 시스템에서 확인할 수 있다.
3. **실제 비개발 업무 사례가 있다.** 광고대행사의 SEO 진단, 전략 메모, 회계 스프레드시트 처리, HR 정책 검토와 영업·마케팅 운영이 확인된다. 아래에서 실무 이용과 제품 기능·공개 예제를 나눴다.
4. **스킬의 존재, 호출, 업무 성공은 서로 다른 확인 항목이다.** 올바른 스킬을 찾았는지와 최종 산출물이 맞는지를 따로 평가해야 한다. [호출 설명 평가][description-evals], [산출물 평가][output-evals]
5. **지침은 권한 통제와 다르다.** ‘승인을 받으라’고 적는 것에 더해 실제 도구·업무 시스템에서 실행 권한과 승인 상태를 확인해야 한다. [Claude Code 권한 문서][permissions]
6. **공개 포맷의 호환성과 실행 결과의 호환성은 다르다.** 설치 경로, 도구 이름, 인증, 런타임, 제품별 확장과 모델 성능은 별도 검증 대상이다. [구현 가이드][implementation]

### 중심 논지 후보

현장에서 확인한 업무 절차와 판단 기준을 스킬로 묶고, 실제 사례로 시험하고, 담당자가 갱신해야 조직의 자산으로 쓸 수 있다. 스킬 파일 작성은 그 과정의 출발점이다.

이 문장은 자료를 종합한 **편집적 결론**이다. 파일 수나 설치 횟수가 성과를 보장한다는 주장은 하지 않는다.

### 1-3. Brainlabs: 베테랑의 진단 기준을 공용 업무 방법으로

**사용과 구성.** 광고대행사 Brainlabs는 SEO 진단과 브랜드 자료 제작 등에 스킬을 사용한다. Notion을 원본 저장소로 삼고 GitHub로 수정 검토를 연결한다. 각 스킬에는 담당자가 있으며 변경사항을 검토·승인한다. [공급사 고객 인터뷰][brainlabs]

**현업이 남긴 것.** SEO팀의 진단 기준과 축적된 맥락, 발표자료·소셜 그래픽·문서의 브랜드 규칙이다. 수백 개로 늘어난 스킬의 중복·상충 지시·토큰 낭비를 찾아 통합안을 제안하는 검사 스킬도 만들었다.

**범위.** 약 4주간 400개 스킬 작성과 약 1,000명 규모의 Cowork 배포를 보고한다. 이는 구축·활용 지표다. 매출 증가나 한 스킬의 순수 효과를 입증하지는 않는다. 접근권한 준수는 이 회사의 운영 환경에 대한 설명이며 스킬 포맷 자체의 보증이 아니다.

**글의 역할.** 기존 암묵지 글과 가장 직접적으로 연결할 수 있다. 무엇을 확인해야 좋은 결과인지 현업이 정리하고, 변경을 관리하는 과정에 초점을 둔다.

### 1-4. HubSpot: 팀의 문체와 판단 틀을 메모에 담기

**사용과 구성.** HubSpot의 제품·마케팅·Business Systems 담당자들은 전략 메모, 업무요건서와 교육자료에 Skills를 쓴다. 한 제품 리더는 자신의 문체와 의사결정 틀을 `memo-writer`에 담았다고 설명한다. 커넥터가 Slack·회의록 등 관련 맥락을 가져온다. [실무자 Q&A][hubspot]

**사람의 역할과 시간.** 제품 리더 Daniel Jacobson은 아이디어에서 검토 가능한 초안까지의 시간이 2시간에서 20분으로 줄었다고 설명한다. 첫 출력은 최종 형태의 60~70% 수준이며 주장과 논조를 사람이 다듬는다. 스킬·커넥터·공유 맥락을 함께 사용한 해당 담당자의 후기이며 완성 문서까지의 시간은 아니다.

**해석.** 스킬이 문서의 모양만 정하는 데 그치지 않고 팀의 사고·설명 방식을 반복 적용하는 사례다. 담당자의 후기를 HubSpot 전체 생산성이나 완성 문서의 자동 승인으로 확대하지 않는다.

### 1-5. Rakuten AI: 관리회계의 스프레드시트 처리

**사용과 효과.** Rakuten AI의 Yusuke Kaji는 여러 스프레드시트를 처리하고 중요한 이상치를 찾으며 조직의 절차대로 보고서를 만드는 일에 Skills를 사용한다고 밝혔다. 해당 작업은 이전에 하루 걸렸지만 약 1시간에 수행한다는 후기다. [출시 자료][launch], [당사자 게시물][rakuten]

**확인되지 않은 것.** 작업 건수, 오류율, 검수 포함 여부, ERP·MCP 구성은 공개되지 않았다. 하루를 임의로 8시간으로 환산하거나 월 결산 전체를 1시간에 끝냈다고 쓰면 안 된다.

**글의 역할.** 회사의 보고 절차와 검수 기준을 반복해서 적용한다는 짧은 현업 사례로 좋다. 상세 구현을 설명할 근거는 부족하다.

### 1-6. Jamf: 직원이 만들기 시작한 다음의 관리 문제

**사용과 운영.** Jamf는 HR·Legal 등에서 스킬을 작성·공유하며, 월별 정책 검토 스킬로 지역별 준수 기한을 표시하는 사례를 공개했다. 일반 사용, custom Skills·MCP 구성, 별도 API 구현에 서로 다른 검토 경로를 적용한다. [고객 사례][jamf]

**수치의 범위.** 208은 스킬 수가 아니라 작성·공유에 참여한 직원 수다. HR의 월 838시간 절감은 21개 구현 과제 전체의 추정치이므로 특정 정책 스킬의 효과로 옮길 수 없다.

**글의 역할.** 누구나 작성할 수 있는 형식이 생긴 뒤, 부서의 검토·배포·운영 책임을 어떻게 나눌지 보여준다.

### 1-7. Zapier: 실제 팀의 절차를 SKILL.md로 공개

**사용과 구성.** Zapier는 영업·마케팅·고객지원 조직이 작성하고 사용하는 스킬 라이브러리를 공개했다. 캠페인 실행 자료, 리드 점검, 영업 준비와 고객 사례 작성의 절차가 들어 있다. [당사 설명][zapier], [공식 저장소][zapier-repo]

**구체적인 파일.** Customer Story Writer에는 승인된 녹취·브리프·CRM 자료를 읽고, 검증된 주장과 추가 근거가 필요한 주장을 나누며, 고객·브랜드·법무·게시 승인 항목을 확인하는 절차가 있다. 결과물에는 초안뿐 아니라 주장 검토표와 미해결 질문도 포함된다. [SKILL.md 원문][story-skill]

**해석.** ‘고객 사례를 잘 써라’라는 요청이 실제 업무 절차로 어떻게 구체화되는지 설명하기 좋다. 파일의 승인 지침이 실제 게시 권한을 강제하는지는 실행 환경에서 따로 확인해야 한다.

**수치 주의.** 같은 글에 등장하는 ClickUp의 시간 절감 수치는 별도 구현에서 영감을 얻은 사례다. 이를 ClickUp의 Agent Skills 직접 성과로 인용하지 않는다.

### 1-8. Box: 기존 업무 제품 안에 Skills를 넣기

**제품 통합.** Box는 사전 제작된 문서 Skills를 기존 AI 제품의 문서 생성·편집 기능에 통합했다. 기존 게이트웨이의 로깅·접근통제 경로에 파일 업로드·다운로드를 추가하는 방식이다. [Box 제품팀 사례][box]

**범위.** 고객에게 제공할 기능을 약 한 달에 구현했다고 설명한다. 계약 변경 표시를 2분에 생성했다는 이야기는 Box 내부 직원의 시험이다. 완전한 법률 검토·승인 시간이나 외부 고객 성과가 아니다.

**글의 역할.** Skills가 사용자의 로컬 폴더뿐 아니라 기존 업무 소프트웨어의 기능으로도 통합될 수 있음을 설명한다.

### 1-9. 법무 공개 예시: 계약 검토에 무엇을 담는가

Anthropic의 공개 법무 플러그인은 회사의 협상 지침과 입장, 거래 조건을 바탕으로 조항별 위험·변경안·협상 쟁점을 정리하는 `review-contract` 스킬을 제공한다. 계약 자료와 회사 기준을 받아 초벌 검토를 돕는 구현 예시다. [공식 파일][legal-skill]

이는 실제 로펌의 도입 성과가 아니다. 법률 전문가의 검토가 필요한 업무를 어떻게 절차로 표현할지 보여주는 자료로 사용한다.

### 1-10. 사례 선택 권고

본문의 주 사례는 **Brainlabs → HubSpot → Zapier** 조합을 권한다. 조직의 노하우 축적, 개인·팀의 문서 업무, 실제 공개 파일이라는 서로 다른 역할을 맡길 수 있다. 회계 독자를 끌어들이려면 Rakuten을 짧게 넣고, 운영·거버넌스는 Jamf로 설명할 수 있다.

이번 조사에서 공장·물류·병원의 특정 현장 업무를 `SKILL.md`가 개선했다는 직접 사례는 충분히 확보하지 못했다. 다른 포스트의 제조·의료 AI 사례를 Skills 사례로 재분류하지 않는다.

## 2. 개념과 다른 구성 요소의 관계

### 2-1. 공개 형식으로 자리 잡은 과정

Anthropic은 2025-10-16 Agent Skills를 소개했고, 같은 기술 글에 2025-12-18 공개 표준화 업데이트를 명시했다. 업무 절차를 AI에 제공한다는 발상 전체의 최초 발명으로 소개할 수는 없다. [기술 소개][intro]

공식 사이트에서 말하는 표준은 스킬 폴더·메타데이터·지침을 공유하는 공개 형식이다. 설치 장소와 실행 권한, 모든 클라이언트의 동일한 행동을 인증하는 제도가 아니다. [개요][overview], [구현 가이드][implementation]

### 2-2. 어떤 종류의 지식을 묶는가

Anthropic의 skill-creator 설명은 모델의 부족한 능력을 보완하는 스킬과 조직·사용자의 선호 및 업무 방법을 담는 스킬을 구분한다. 전자는 모델이 발전하면 효용이 줄 수 있고, 후자는 회사의 방식에 맞는지가 중요하다. 한 스킬에 두 성격이 함께 있을 수도 있다. [skill-creator 개선 글][skill-creator]

견적서의 필수 항목, 회사의 보고서 구성, 예외를 확인할 순서처럼 반복할 수 있는 방법이 후보가 된다. 현재 가격·재고·고객 계약처럼 자주 바뀌는 값은 스킬 안에 복사해 고정하기보다 최신 원천을 조회하게 만드는 것이 적절할 수 있다. 이 구분은 **기업 적용을 위한 설계 제안**이다.

### 2-3. 비교표

| 구성 요소 | 주된 역할 | Skill과 함께 쓰는 방식 |
|---|---|---|
| Prompt | 이번 요청과 지시 | 스킬의 지침도 활성화되면 문맥에 들어간다. 재사용·발견·배포 구조가 추가된다. |
| Tool | 조회·계산·파일 작성 등 호출 가능한 동작 | 스킬이 어떤 도구를 언제 어떻게 쓸지 안내한다. 인증이 자동으로 생기는 것은 아니다. |
| MCP | 외부 도구·자료 등을 연결하는 통신 규약 | CRM 도구를 연결하고 스킬이 이를 쓰는 절차를 담을 수 있다. MCP도 resources·prompts를 다룬다. |
| Memory | 진행 상태·선호·과거 경험 등의 기록 | 기억한 교정을 검토해 스킬 개선안으로 만들 수 있다. 자동 학습·승격은 별도 구성이다. |
| RAG | 관련 자료를 찾아 판단의 근거로 제공 | 스킬이 어떤 자료를 찾아 어떻게 처리할지 안내한다. 두 방식은 함께 쓸 수 있다. |
| Context Graph | 업무 대상과 판단·행동·결과의 관계 및 이력 | 과거 예외와 근거를 조회하고 스킬이 현재 업무 절차에 반영할 수 있다. |
| Agent | 목표에 따라 행동·도구 사용을 결정하며 일하는 시스템 | 하나의 에이전트가 여러 스킬을 이용할 수 있다. |
| Plugin | 여러 확장 기능의 설치·배포 묶음 | 스킬·에이전트·훅·MCP 서버 등을 함께 담을 수 있다. 스킬 단독 배포도 가능하다. |
| Fine-tuning | 데이터로 모델을 추가 학습 | 스킬은 파일·문맥을 제공하는 방식이다. 필요하면 추가 학습과 병행할 수 있다. |
| 프로젝트 공통 지침 | 프로젝트 전반의 배경·지속 규칙 | 필요할 때 펼쳐 보는 업무별 스킬과 역할을 나눌 수 있다. 로딩 방식은 제품마다 다르다. |

기본 개념 근거: [Context Engineering][context], [MCP 구조][mcp], [메모리 문서][memory], [에이전트와 워크플로][agents], [플러그인][plugins], [RAG와 추가 학습][rag-finetuning]. Context Graph와의 연결은 기존 포스트를 바탕으로 한 **설계 해석**이다.

‘MCP는 연결만 하고 Skill만 지식을 담는다’거나 ‘Skill을 쓰면 RAG와 전문 에이전트가 필요 없다’는 식의 배타적 구분은 피한다.

## 3. 기술 구조: 파일 안에 무엇이 들어가는가

### 3-1. 표준 필수·선택·권고를 나누기

| 구분 | 내용 |
|---|---|
| 필수 | `SKILL.md`, YAML frontmatter의 `name`·`description`, Markdown 본문 |
| 이름 | 디렉터리명과 일치. 1~64자이며 명세의 소문자·숫자·하이픈 제약 적용 |
| 설명 | 1~1,024자. 무엇을 하고 언제 사용할지 설명 |
| 선택 필드 | `license`, `compatibility`, `metadata`, 실험적인 `allowed-tools` |
| 선택 디렉터리 | `scripts/`, `references/`, `assets/`. 세 폴더가 모두 필요한 것은 아님 |
| 작성 권고 | 본문 500줄 미만, 활성화 지침 5,000토큰 미만 등을 권고. 강제 성능 한도가 아님 |

근거: [Agent Skills 사양][spec]. `metadata.version` 같은 자체 버전 정보는 넣을 수 있지만 자동 버전 관리 기능이나 표준 필수 필드가 아니다. `compatibility`도 요구사항 설명이며 필요한 패키지를 설치해 주는 기능은 아니다.

### 3-2. 설명용 디렉터리

아래는 **가상의 견적 작성 스킬**이다. 이 조사에서 실제 파일이나 실행 도구를 설치한 것은 아니다.

```text
prepare-sales-quote/
├── SKILL.md                    # 언제 사용하고 어떤 순서로 처리하는가
├── references/
│   ├── approval-guide.md       # 예외와 승인 절차의 설명
│   └── output-examples.md      # 좋은 초안과 보류해야 할 예시
├── scripts/
│   └── validate_quote.py       # 합계·필수 항목·형식 검증
└── assets/
    └── quote-template.xlsx     # 회사 양식
```

독자에게는 업무 인수인계 묶음에 비유할 수 있다. 절차서만 주는 것이 아니라 양식·계산 도구·좋은 예시를 함께 주는 것이다. 실제 이해와 준수는 별도로 확인해야 한다.

### 3-3. 지침과 스크립트의 분담

지침에는 판단 기준과 업무 분기, 입력이 부족할 때의 대응을 담는다. 합계 계산·필수 필드·파일 구조처럼 반복해서 확인할 항목은 코드로 검사할 수 있다. 스크립트는 명확한 인자·오류·구조화된 출력을 제공하고 런타임·의존성을 문서화하는 편이 좋다. [스크립트 작성 가이드][scripts]

스크립트를 실행할 때 코드 전체를 모델 문맥에 넣지 않고 결과만 받을 수도 있다. 그러나 코드가 있다는 사실만으로 원천 데이터나 판단 전체가 정확해지는 것은 아니다. [Claude Skills 개요][claude-overview]

### 3-4. 좋은 지침에 필요한 내용

다음은 공식 작성 가이드를 업무용으로 풀어낸 **편집 제안**이다. [작성 원칙][authoring]

- 언제 쓰고 언제 쓰지 않는가.
- 필수 입력과 신뢰할 원천은 무엇인가.
- 어떤 순서로 자료를 확인하고 계산하는가.
- 예외·충돌·정보 부족이면 어디서 질문하거나 멈추는가.
- 어떤 형식과 근거를 갖춘 산출물을 내야 하는가.
- 무엇을 검사하고 누가 최종 결정하는가.

모델이 이미 아는 일반론을 길게 적기보다 회사에서 달라지는 부분을 구체화한다. 다만 사람이 정리하지 못한 암묵지가 스킬 파일로 저절로 추출되는 것은 아니다.

## 4. 작동 원리: 발견·활성화·실행

### 4-1. Progressive Disclosure

공식 가이드가 설명하는 기본 흐름은 다음과 같다. [구현 가이드][implementation]

```text
사용 가능한 Skills를 발견
        ↓
이름·설명으로 어떤 일을 맡길 수 있는지 파악
        ↓
요청과 관련 있는 Skill을 선택
        ↓
선택한 SKILL.md의 지침을 읽기
        ↓
필요한 참고자료·양식·스크립트를 사용
        ↓
산출물과 실제 실행 결과를 확인
```

모든 스킬의 본문을 매번 넣는 방식과 다르다. 설치된 목록의 설명에도 비용이 들며, 스킬을 잘 선택하고 계속 준수한다는 보장은 없다. 긴 작업에서 활성화한 지침을 어떻게 유지할지도 클라이언트의 구현에 달려 있다.

### 4-2. description이 중요한 이유

설명이 너무 넓으면 관계없는 작업에 호출되고, 너무 좁으면 필요한 순간에 빠질 수 있다. 실제 사용자가 할 법한 요청과 비슷하지만 다른 요청을 함께 시험한다. [호출 설명 최적화][description-evals]

| 구분 | 가상 견적 스킬의 평가 요청 |
|---|---|
| 호출 대상 | A사에 보낼 제품 두 종류의 견적 초안을 만들어 달라 |
| 호출 대상 | 지난 거래 조건을 확인해 이번 수량으로 견적을 다시 작성해 달라 |
| 호출 제외 후보 | ‘견적서’의 영어 표현을 알려 달라 |
| 호출 제외 후보 | 이미 작성된 견적서를 첨부해 메일을 보내 달라 — 초안 작성과 발송 권한을 분리한 설계일 때 |

이 예시는 작성자의 테스트 설계다. 호출 제외 여부는 조직이 정의한 스킬 범위에 따라 달라진다. 설명을 고치는 데 쓴 질의와 검증용 질의를 나누고, 반복 실행에서 결과가 흔들리는지도 본다.

### 4-3. 제품에 따라 달라지는 동작

| 항목 | 공개 포맷의 범위 | 제품별 확인 사례 |
|---|---|---|
| 설치·발견 | 폴더 구조를 정의하며 공통 설치 경로를 강제하지 않음 | 로컬 경로, 저장소, 업로드와 관리 배포 등이 다름 |
| 필드 검증 | `name`·`description` 필수 | Claude Code는 현재 문서상 모든 필드를 선택적으로 허용하고 이름·설명을 유도할 수 있음 |
| 호출 | 필요한 지침을 활성화하는 구조 | 직접 호출 문법, 모델의 선택, 별도 활성화 도구가 다름 |
| 실행 | 스크립트·자료를 활용할 수 있는 형식 | 로컬·서버·API 컨테이너의 네트워크와 패키지 조건이 다름 |
| 동의·권한 | 실험적인 필드 외에 실행환경 전체를 규정하지 않음 | Gemini CLI는 활성화 시 사용자 동의와 폴더 읽기 허용을 설명 |

근거: [명세][spec], [Claude Code][claude-code], [Gemini CLI][gemini], [Claude 실행환경 개요][claude-overview]. 위 동작은 **조사일에 확인한 제품 문서 기준**이다.

`.agents/skills/` 같은 경로는 여러 구현이 채택한 관례일 수 있으나 명세의 필수 설치 장소가 아니다. Claude Code의 `context: fork`, `disable-model-invocation` 등도 모든 지원 제품에 공통인 필드로 설명하지 않는다.

### 4-4. allowed-tools의 이름만 보고 판단하면 안 된다

**현재 Claude Code의 `allowed-tools`는 해당 턴의 도구 사전승인이다. 목록 밖의 모든 도구를 금지하는 allowlist가 아니다.** 다른 도구는 기본 권한 설정을 따르며, 이 사전승인은 다음 사용자 메시지에 해제된다고 문서가 설명한다. 표준에서도 실험적 필드다. [Claude Code 공식 설명][claude-code]

따라서 `allowed-tools: Read`를 적었다는 이유만으로 읽기 전용 스킬이라고 보장할 수 없다. 실행을 막아야 하는 요구는 호스트의 권한·관리 정책·검사 지점에서 구현한다. 문서상 확장 필드와 실제 권한 정책의 우선순위도 사용 제품에서 확인한다. [권한 문서][permissions]

이 항목은 독자가 세부 필드를 암기하도록 하기보다 **지침·사전승인·실행 차단이 다른 것**임을 설명하는 데 활용한다.

## 5. 하나의 업무에 적용해 보는 가상 예시

### 5-1. 견적서 초안 작성

아래는 기업 적용을 설명하기 위한 **가상 구성**이다. 공개된 고객 프로젝트나 즉시 설치 가능한 완제품이 아니다.

고객·제품·수량을 입력받아 최신 단가와 계약을 확인하고, 계산과 예외 검토를 거쳐 회사 양식의 초안을 만든다고 가정한다. 원천 시스템·인증·도구는 별도로 연결되어 있어야 한다.

```yaml
---
name: prepare-sales-quote
description: >
  고객과 제품, 수량에 맞는 회사 견적 초안을 작성하고 검증한다.
  신규 견적 작성이나 거래 조건을 반영한 재작성 요청에 사용한다.
  용어 설명이나 견적 발송만을 요청한 경우에는 사용하지 않는다.
metadata:
  owner: sales-operations
  version: "0.1.0"
---
```

지침 본문에는 다음과 같은 절차를 둘 수 있다.

1. 고객·제품·수량·통화·유효기간에 필요한 정보가 있는지 확인한다.
2. 연결된 업무 시스템에서 최신 단가·거래 조건·적용 정책을 조회한다. 조회 실패는 정보 없음과 구분한다.
3. 검증된 계산 절차로 금액을 계산하고 회사 양식에 초안을 작성한다.
4. 예외와 미확인 항목, 적용한 자료의 시점·출처를 표시한다.
5. 승인 대상이면 승인권자에게 검토할 정보를 전달한다. 이 스킬의 범위는 초안 작성이며 확정·발송 도구는 별도 권한을 따른다.
6. 필수 항목·합계·양식·근거가 일치하는지 검사하고 결과와 남은 질문을 반환한다.

### 5-2. 무엇을 어디에 둘까

| 정보·기능 | 둘 곳의 예 | 이유 |
|---|---|---|
| 확인 순서·검수 방법 | Skill 지침·예시 | 반복할 수 있는 업무 방법 |
| 최신 단가·현재 재고 | 업무 시스템·조회 Tool | 자주 바뀌는 값을 오래된 파일에 고정하지 않기 위해 |
| 고객별 계약 | 권한을 반영한 검색·문서 원천 | 계약 버전과 열람 범위 확인 |
| 합계·필수 필드 검증 | 테스트한 스크립트·서비스 | 정확히 확인할 부분을 재사용하기 위해 |
| 현재 진행·승인 대기 | 작업 상태 저장소·Memory | 여러 세션과 담당자 사이에서 이어가기 위해 |
| 승인·확정·외부 발송 | 업무 시스템과 실행 권한 | 자연어 지침을 따르지 않아도 허가 없는 실행을 막기 위해 |
| 과거 예외의 근거·결과 | 업무 기록·필요하면 Context Graph | 과거 판단을 현재의 기본 규칙과 구분해 참고하기 위해 |

이 배치는 **설계 제안**이다. 회사마다 필요한 도구와 데이터가 다르며 처음부터 모든 기능을 구현할 필요는 없다.

### 5-3. 문서 작성과 업무 완료를 구분한다

스킬이 견적 파일을 만들었어도 합계가 맞는지, 고객과 통화가 맞는지, 승인 조건이 반영됐는지는 별도 확인이 필요하다. 승인된 금액을 바꾼 뒤 이전 승인을 그대로 재사용하거나 재시도로 메일을 중복 발송하지 않도록 실행 시스템도 검증한다.

지침이 만들어 낸 행동의 **최종 상태와 산출물**을 평가한다는 원칙은 공식 평가 자료에서도 확인된다. [스킬 산출물 평가][output-evals], [에이전트 평가][agent-evals]

## 6. 정말 효과가 있는가: 연구와 평가

### 6-1. SkillsBench 최신 논문판

2026-06-14 수정된 **arXiv v4**는 87개 과제·8개 도메인·18개 모델–실행환경 조합을 같은 조건의 스킬 유무로 비교한다. 전문가가 정리한 스킬을 제공한 평균 통과율은 33.9%에서 50.5%로 높아졌으며 차이는 **16.6%포인트**다. [논문 v4][skillsbench]

저자들의 v1.1 설명은 전체 과제 중 일부에서 성능이 나빠졌음도 밝힌다. 스킬을 호출한 기록이 있다고 성공한 것도 아니다. [연구팀의 릴리스 설명][skillsbench-release]

이는 준비된 과제·스킬·실행환경의 평가다. 회사의 매출·인건비 효과나 임의의 공개 스킬을 설치했을 때의 성능으로 바꿀 수 없다. 오래된 검색 결과의 86개·11개 도메인·16.2%포인트와 최신 논문 수치를 혼합하지 않는다. 실시간 순위표와 논문 집계도 다르다.

### 6-2. 공개 스킬을 붙여도 좋아지지 않은 실험

SWE-Skills-Bench는 실제 저장소와 요구사항을 이용해 공개 소프트웨어 개발 스킬을 비교했다. 49개 스킬 중 39개에서 통과율 개선이 없었고, 일부는 버전이 맞지 않는 지침 때문에 성능이 나빠졌다고 보고한다. [2026-03-16 연구 원문][swe-skills]

이 결과를 ‘Skills가 쓸모없다’로 일반화하기도 어렵다. 전문 업무에 맞춘 스킬과 공개 라이브러리의 범용 스킬은 조건이 다르다. 해당 연구는 소프트웨어 개발 과제이며 회계·인사·마케팅의 운영 효과를 직접 측정하지 않았다.

### 6-3. 스킬을 고르는 문제까지 포함하면

다른 연구는 약 3만 4천 개의 스킬에서 관련 항목을 검색·선택해야 하는 조건을 다룬다. 미리 잘 맞는 스킬을 제공한 경우보다 현실적인 선택 조건에서 이득이 줄 수 있음을 보고한다. [2026-04-06 연구 원문][skills-wild]

**편집적 해석:** 회사에 필요한 평가는 ‘좋은 스킬을 줬더니 잘했는가’뿐 아니라 ‘많은 스킬 중 필요한 것을 골랐는가’도 포함해야 한다. 세 연구는 과제·모델·스킬 제공 방식이 달라 수치를 직접 순위 비교하지 않는다.

### 6-4. 기업용 평가표 제안

공식 가이드는 동일한 입력을 스킬 유무 또는 이전 버전으로 비교하고, 실행마다 독립된 문맥에서 시작하며, 산출물·시간·토큰을 확인하는 방식을 제안한다. 정성적인 품질은 사람이 검토할 필요가 있다. [공식 가이드][output-evals]

| 평가 축 | 견적 업무에서 확인할 항목 |
|---|---|
| 발견·선택 | 필요한 요청에서 호출하고 비슷하지만 다른 요청에서는 빠지는가? |
| 입력·근거 | 최신 정책·계약을 찾고 출처와 유효 시점을 확인하는가? |
| 산출물 | 금액·필수 항목·파일 형식·회사 양식이 맞는가? |
| 예외 처리 | 자료 충돌·권한 부족·조회 실패에서 질문하거나 보류하는가? |
| 승인·실행 | 승인 없는 확정·발송이 실제로 차단되는가? |
| 재시도 | 다시 실행해도 중복 거래·발송이 생기지 않는가? |
| 비용·시간 | 검토·수정까지 포함한 총 업무시간과 비용이 줄었는가? |
| 회귀 | 스킬·모델·도구·정책 변경 뒤에도 기존 사례를 통과하는가? |

위 표는 **작성자의 제안**이다. 공식 문서의 예시 테스트 개수나 임계값을 모든 기업의 충분한 검증 기준으로 제시하지 않는다.

### 6-5. 스킬을 만들기 전에 기준 사례를 확보한다

정상 사례, 예외 사례, 하지 말아야 할 작업을 먼저 모은다. 스킬을 반복 수정할 때 사용한 사례와 마지막 검증용 사례를 나눈다. 답변이 그럴듯한지뿐 아니라 원래 업무에서 무엇을 줄이거나 개선하려 했는지를 함께 본다.

모델이 새로운 스킬을 작성하도록 도울 수는 있지만, 그 결과를 바로 사내 공통 규칙으로 승인하는 것은 별개의 결정이다. 사람이 정리한 지침도 틀릴 수 있으므로 작성 주체와 무관하게 실제 평가가 필요하다.

## 7. 작성 이후의 운영과 거버넌스

### 7-1. 누가 어떤 변경을 책임질까

아래는 **기업 운영 제안**이다. 특정 제품의 강제 절차가 아니다.

| 역할 | 책임 |
|---|---|
| 현업 소유자 | 업무 절차·예외·좋은 결과의 기준과 정책 변경 |
| 기술 담당자 | 도구·스크립트·런타임·배포·관측·복구 |
| 보안·준법 담당자 | 접근 범위, 민감정보, 외부 연결, 검토가 필요한 업무 |
| 실제 사용자 | 현업 사례·수정 피드백·과도한 호출·누락 보고 |

개인이 고친 문장이 조직의 공통 정책인지 일회성 예외인지 확인하고, 변경 제안·검토·평가·제한 배포·확대의 단계를 둔다. Brainlabs와 Jamf는 소유자·부서 검토를 갖춘 실제 운영의 참고 사례다. [Brainlabs][brainlabs], [Jamf][jamf]

### 7-2. 함께 버전 관리할 것

- 스킬 지침, 참고 정책, 스크립트·의존성과 양식.
- 평가 질의·입력 파일·검증 기준.
- 사용 제품·모델·도구 버전과 권한 설정.
- 변경 이유와 현업 승인, 배포·되돌리기 방법.

스킬 파일을 되돌리는 것과 이미 실행한 업무를 되돌리는 것은 다르다. 발송된 메일·확정된 주문에는 별도 복구 절차가 필요하다. 이 버전 관리 묶음과 복구 구분은 **운영 설계 제안**이다.

### 7-3. 스킬 공급망도 검토 대상이다

스킬은 자연어 지침뿐 아니라 코드·참고자료·외부 링크를 포함할 수 있다. 설치할 때 본문만 읽고 끝내면 나중에 불러오는 자료와 실행 코드를 놓칠 수 있다. [Claude Skills 보안 설명][claude-overview]

Cisco는 공개 Skill Scanner로 악성 지시·코드·데이터 유출 등의 탐지를 돕는다. 이 저장소도 검사 결과가 없다고 안전을 보장하지는 않는다고 명시한다. [공개 도구][scanner]

보안 통제를 자연어 지침에만 맡기지 않고 권한·샌드박스·업무 시스템과 함께 구성한다. 해당 환경에 적용한 파일·네트워크 격리가 무엇을 막는지도 확인한다. [권한][permissions], [샌드박스][sandbox]

### 7-4. 적게 만들고 실제 사용을 확인한다

스킬이 많아질수록 중복·상충 설명, 이름 충돌, 오래된 정책과 미사용 항목이 생길 수 있다. 파일 개수보다 실제로 선택·사용된 결과를 보고 통합·폐기·수정할 대상을 정한다.

이는 스킬의 선택·실행·효과를 나누어 평가해야 한다는 자료를 운영에 적용한 제안이다. 스킬을 더 많이 설치하는 것을 성숙도나 성과 지표로 삼지 않는다.

## 9. 기존 포스트와 연결할 논지와 구성

### 9-1. 세 포스트의 연결

- 암묵지 글: 숙련자가 아는 판단 기준 중 무엇을 드러내고 확인할 것인가?
- FDE 글: 누가 현업과 함께 그 기준을 구현하고 운영 가능하게 만들 것인가?
- Skills 글: 확인한 업무 방법을 어떻게 여러 사람과 에이전트가 재사용하고 갱신할 것인가?

모든 암묵지가 문서 한 장으로 바뀐다고 주장하지 않는다. 현장에서 확인하고 표현할 수 있는 절차·예시·검증 기준을 묶는다는 설명이 적절하다.

### 9-2. 들어가며 후보

| 후보 | 후킹과 연결 |
|---|---|
| Brainlabs의 SEO 진단 | 오늘 담당자가 무엇을 기억했느냐에 따라 품질이 달라지는 상황에서 공용 기준을 만드는 이야기 |
| HubSpot의 메모 작성 | 회의록을 요약하는 데서 팀의 판단 방식과 문서 형식을 반복 적용하는 이야기 |
| 가상 견적서 | 작성할 때마다 회사의 가격·예외·양식을 다시 설명해야 하는 상황. 실제 고객으로 꾸미지 않는다. |

권장 구성은 **현업 사례 → Skill의 정의 → 파일·실행 구조 → Tool·MCP·Memory와의 관계 → 평가·운영 → 나가며**다. 원고에서는 기술 항목을 모두 같은 깊이로 열거하기보다 선택한 업무 하나로 설명하면 읽기 좋다.

### 9-3. CTA 연결 메모

엡실론델타가 도울 일을 업무 절차 발견, 스킬 범위 설정, 원천 데이터·도구 연결, 현업 평가, 권한·배포·변경 관리로 구체화할 수 있다. 회사에 맞는 스킬을 만들려면 업무 지식과 에이전트 운영을 함께 이해해야 한다는 논지로 연결한다.

나가며에는 실제로 자주 반복하거나 숙련자에게 물어보는 업무 하나부터 논의하자는 제안과 `contact@epsilondelta.ai`를 넣는 방향이 적합하다. 고객 후기의 수치를 자사 실적·보장치로 사용하지 않는다.

## 10. 내부에서 확인한 운영 예시 — 공개 본문 사용은 선택

이 절은 외부 고객 사례가 아니라 **현재 작업 공간에서 확인한 내부 편집 기록**이다. 회사 전체의 생산성 실증이나 AI 작성 여부 판정 자료가 아니다.

기존 FDE 포스트는 `im-not-ai`의 스킬·규칙·검증 스크립트를 활용해 윤문했다. 단일 호출 결과와 문서 전체를 재검토한 결과가 달랐고, 정밀 패스의 finalizer는 새로 들어간 우선순위·범위 단정 등을 보정했다. 관련 자료는 `_workspace/2026-09-07-002/02_diagnosis.md`, `09_finalize.json`에 있다.

특히 윤문 입력은 이미지 추가 전 버전이었다. 그 결과의 frontmatter는 `draft = true`, `images = []`였으며, 당시 게시 원고에는 이미지 6개와 `draft = false`가 있었다. 그대로 덮어쓰면 게시 설정과 이미지가 사라질 수 있어 실제 반영에서는 본문 변경만 병합했다.

이 사례가 보여주는 것은 스킬의 평가 범위다. **제공받은 입력을 잘 다듬는 것과 현재 게시 시스템에 안전하게 반영하는 것은 다른 과업**이었다. 자료의 최신 버전, 유지할 필드, 최종 환경 상태를 포함한 검증이 필요하다. 이 문서는 스킬을 추가로 실행하거나 기존 산출물을 수정하지 않았다.

| 피할 표현 | 조사 결과에 맞는 설명 |
|---|---|
| 한 번 가르치면 영구히 학습한다 | 스킬은 실행 시점에 지침·자료를 제공한다. 가중치 학습과 자동 갱신은 별개다. |
| Skill은 긴 프롬프트와 완전히 다른 기술이다 | 지침도 문맥에 들어간다. 발견·자료·코드·배포의 관리 구조를 설명한다. |
| 스킬마다 에이전트를 하나씩 만든다 | 하나의 에이전트가 여러 스킬을 사용할 수 있다. |
| 표준이므로 어디에서나 동일하게 작동한다 | 실행환경·도구·권한·확장 필드·모델을 검증한다. |
| scripts·references·assets가 모두 필수다 | `SKILL.md`가 핵심이며 나머지는 선택적인 구성이다. |
| allowed-tools가 목록 밖 도구를 모두 막는다 | 현재 Claude Code에서는 해당 턴의 사전승인이다. 호스트별 동작을 확인한다. |
| 승인받으라는 문장이 결재를 강제한다 | 실제 권한·승인 상태는 실행 시스템에서 검사한다. |
| Brainlabs의 400개 스킬이 높은 ROI를 입증한다 | 작성·활용 규모와 실제 업무 성과는 구분한다. |
| HubSpot의 문서 업무 전체가 2시간에서 20분으로 줄었다 | 한 제품 리더가 아이디어에서 검토 가능한 메모 초안까지 걸리는 시간을 설명한 후기다. |
| Jamf는 208개 스킬로 월 838시간을 절감했다 | 208은 사람 수, 838시간은 HR의 21개 구현 과제 전체 추정이다. |
| Rakuten 월 결산을 1시간에 끝냈다 | 후기는 특정 스프레드시트 처리·이상 탐지·보고 작업에 관한 것이다. |
| Box의 계약 검토가 2분에 완료된다 | 내부 시험에서 변경 표시 문서를 생성한 시간이며 법률 검토 완료가 아니다. |
| ClickUp의 절감 수치는 공개 Zapier 스킬의 효과다 | 다른 구현에서 영감을 얻은 사례와 Skills 직접 사용을 구분한다. |
| 벤치마크 통과율이 16.6% 향상됐다 | 최신 논문은 33.9%→50.5%, 16.6%포인트 차이다. 기업 KPI가 아니다. |
| 공개 스킬이나 자동 생성 스킬은 모두 효과적이다 | 적합성·선택·버전·실행 조건에 따라 도움이 없거나 악화될 수 있다. |
| 보안 스캐너 통과는 인증이다 | 검토를 보조하는 탐지 결과이지 안전 보증이 아니다. |
