# AI 에이전트 관측성(Agent Observability) — 개념·기술·운영 사례 리서치

조사일: 2026-10-09 (KST)

- 백로그: `_research/ax-topic-backlog-100.md` 047번 ‘AI가 왜 틀렸는지 추적할 수 있는 운영 기록’.
- 대상: 경영진, 현업 책임자, 데이터·플랫폼·에이전트 개발팀.
- 자료: OpenTelemetry 공식 문서, Langfuse·LangSmith 기술 문서와 고객 발표. 제품 기능·공급사 사례·사용자 제공 경험·설계 제안을 구분한다.
- 공개 웹 자료 조사이며 고객 시스템·로그 접속, 인터뷰, 성과 재현은 수행하지 않았다.
- 검증 메모는 집필 판단용이다. 주제와 관계없는 선제 해명을 블로그에 모두 옮기지 않는다.

## 1. 핵심 결론

**에이전트 관측성은 요청을 처리하며 읽은 자료·모델 호출·도구 실행·승인·업무 결과를 연결해 문제를 진단하고 개선하는 능력이다.**

대화 화면에서는 완료라고 답했어도 업무 시스템에는 결과가 없을 수 있다. 검색한 문서가 오래됐는지, 모델이 잘못 해석했는지, 도구 인자가 틀렸는지, 실제 시스템이 거절했는지를 구분해야 한다.

기록은 원인 조사의 근거다. 수집만으로 원인이 자동 확정되지는 않는다. 현업 판정과 수정·평가·재검증에 연결할 때 운영 자산이 된다.

추천 제목: **AI가 잘못 처리했는데, 대화 기록에는 문제가 없습니다**

후킹: 완료 답변을 받았지만 다음 담당자가 결과를 찾지 못하는 가상 업무 장면. 엡실론델타 고객의 실제 사고로 묘사하지 않는다.

독자 이득: 대화 로그와 실행 경로의 차이를 이해하고, 모델을 바꾸기 전에 고칠 지점을 찾으며, 완료율·지연·비용·재작업으로 운영을 판단한다.

## 2. 엡실론델타 직접 경험 — 사용자 제공 사실

사용자가 이번 대화에서 제공한 1차 경험이다. 공개 자료와 별개로 취급한다.

1. PE사 에이전트 구축 프로젝트에서 **OpenTelemetry 기반 Langfuse**를 사용했다.
2. 내부 프로젝트에서 과거 **LangChain**을 주로 사용하던 시기에는 **LangSmith**를 사용했다.
3. 현재는 주로 **Langfuse와 OpenTelemetry**를 사용한다.
4. 팀의 원래 기술 기반은 **MLOps**였고 현재 **AgentOps**까지 확장했다.
5. 팀은 **Observability를 매우 중요하게 생각한다**.

사용자는 ‘그 어떤 팀보다’ 중요하게 생각한다고 표현했다. 팀의 강한 관점으로 반영하되 경쟁사 대비 순위·효과가 입증된 주장으로 바꾸지 않는다.

활용 가능한 문장:

> 저희 엡실론델타는 MLOps를 기술 기반으로 시작해 AgentOps까지 영역을 넓혔습니다. PE사 에이전트 구축에는 OpenTelemetry 기반 Langfuse를 사용했고, 내부 프로젝트에서는 LangChain을 주로 쓰던 시기에 LangSmith를 사용했습니다. 현재는 주로 Langfuse와 OpenTelemetry로 관측 체계를 구성합니다.

확인하지 않은 내용: PE사 이름, 구체적인 수집 항목, 배포·저장 위치, SDK 버전, 장애·개선 사례, 비용·품질 개선 수치, 고객 인용, 도구 선택을 바꾼 이유. 다음 기술 설계를 해당 프로젝트의 실제 구성으로 쓰지 않는다. 최신 SDK 버전을 과거 프로젝트에 소급하지 않는다.

집필용 해석: MLOps에서 모델·데이터·버전·배포를 관리했다면, AgentOps에서는 검색·메모리·도구·분기·위임·승인·실제 실행 결과까지 조사 범위가 넓어진다. 이 부분은 사용자가 제공한 배경에서 도출한 편집 의견이다.

## 3. 개념 지도

| 개념 | 의미 | 업무 예시 |
|---|---|---|
| Monitoring | 정한 상태·지표를 지속 확인 | 실패율·지연이 기준을 넘었나 |
| Observability | 남긴 신호로 동작을 조사하는 능력 | 어느 단계에서 어떤 조건으로 실패했나 |
| Log | 개별 사건 기록 | 권한 거절·검색 결과 없음 |
| Metric | 집계 수치 | 완료율·p95 지연·호출 수 |
| Trace | 요청 처리의 연결된 실행 경로 | 검색→모델→도구→결과 확인 |
| Span | 경로 안의 작업 단위 | 모델 호출·조회·API 실행 |
| Session | 여러 요청의 상호작용 묶음 | 채팅 세션 |
| Business task | 실제 완료를 판단할 업무 단위 | 발주 한 건·딜 조사 작업 |
| Evaluation | 결과·과정을 기준에 따라 판정 | 근거 적합성·승인 준수 |
| Audit record | 책임·승인·변경 근거 보존 | 승인자·정책·변경 대상 |

Trace·span은 분산 추적 개념이다.[S1] 한 대화에 여러 업무가 생기거나 한 업무가 여러 대화·실행에 걸칠 수 있다. session ID와 업무 ID를 구분한다.

관측성은 실제 사례를 확보하고 Evals는 그 결과를 판정한다. 실패 사례를 다음 회귀 시험에 넣고 수정·제한 배포 후 다시 관측한다. 기존 Evals·FinOps·Durable Execution 글과 연결 가능하다.

## 4. 기술 구성

### 4.1 OpenTelemetry와 관측 백엔드

OpenTelemetry는 계측 API·SDK·프로토콜·Collector 등의 기반이다. Langfuse 같은 저장·조회·평가 화면과 역할이 다르다.

```text
에이전트·검색·모델·업무 API
 → 계측: trace·span·event·metric
 → 실행 맥락 전파: HTTP·큐·비동기 연결
 → OTLP 전송
 → Collector 또는 직접 exporter
 → Langfuse·LangSmith·기존 APM
 → 현업 판정·실패 분석·수정·회귀 검증
```

Collector는 구성 선택지이며 반드시 거쳐야 하는 것은 아니다. GenAI 화면과 기존 APM을 함께 사용하면 어떤 span을 어디로 보낼지 정한다.[S2][S3][S7]

### 4.2 실행 맥락 전파

Trace ID·span ID 등을 전달해 서비스·비동기 작업을 연결한다.[S2] 여기서 context는 모델에게 제공한 프롬프트·문서라는 뜻과 다르다.

- 동기 작업은 부모·자식 span으로 연결한다.
- 큐·다른 프로세스에는 맥락 전달과 수신측 계측이 필요하다.
- 재시도 번호와 업무 ID를 함께 남긴다.
- 여러 입력 합류·지연 실행에는 span links 등을 검토한다.
- 하루 뒤 승인처럼 긴 업무는 계속 열린 span 하나보다 업무 ID로 여러 trace·승인 이벤트를 연결하는 방식을 검토한다.

후반 항목들은 설계 제안이다. SDK 설치만으로 모든 외부 시스템과 업무 단계가 자동 연결되는 것은 아니다.

### 4.3 수집할 항목과 진단 질문

| 단계 | 기록 후보 | 확인할 문제 |
|---|---|---|
| 요청 | 업무 ID·가명 사용자·조직·환경 | 누구의 어느 환경 문제인가 |
| 검색 | 문서 ID·버전·검색어·필터·시간 | 잘못되거나 오래된 근거인가 |
| 메모리 | 참조 범위·항목 ID·버전 | 다른 사용자·딜의 정보가 섞였나 |
| 모델 | 모델·프롬프트 버전·토큰·시간 | 변경 뒤 품질·비용이 달라졌나 |
| 도구 | 이름·허용된 인자·오류·결과 참조 | 대상·입력·권한이 맞았나 |
| 분기·위임 | 선택 경로·반복·담당 에이전트 | 라우팅이나 반복 문제인가 |
| 승인 | 승인 대상·정책·승인 결과 | 허용된 작업을 승인받았나 |
| 완료 | 업무 시스템 ID·상태·확인 시점 | 실제 반영됐나 |
| 피드백 | 수정·반려 이유·평가 버전 | 무엇을 다음 시험에 넣을까 |

입력·고객정보·메모리를 전부 원문 저장하라는 제안이 아니다. 필요한 메타데이터와 허용된 내용으로 조사 근거를 확보한다. 모델이 출력한 설명이나 reasoning 필드는 접근 가능한 출력이며 내부 사고 전체를 읽는 증거가 아니다.

### 4.4 GenAI 의미 규약

모델·사용량·작업 유형의 속성 이름을 맞추면 다른 프레임워크의 기록도 비교하기 쉽다. chat·retrieval·execute_tool·invoke_agent 같은 작업 유형을 확인할 수 있다.[S4]

2026-10-09 확인 시 OTel 기존 GenAI 페이지는 별도 semantic-conventions-genai 저장소로 이동했다고 안내한다. 관련 속성에는 Development 항목이 있으므로 모든 규약이 확정됐다고 표현하지 않는다. 계측 라이브러리·백엔드의 버전과 속성 매핑을 관리한다.

### 4.5 Langfuse

현재 SDK는 OTel 기반 계측과 trace·observation 연결을 제공한다. Observation은 OTel span의 제품 내 표현이고 generation은 모델·토큰·비용 등을 다루는 특화 표현이다.[S5] 프롬프트 관리·평가·피드백과 연결하며 클라우드·셀프호스팅을 지원한다.

확인 시점의 최신 안내는 Python SDK v4와 JS/TS SDK v5다. 전체 입출력은 root observation에 두며 이전 trace-level 방식과 차이가 있다. 코드 집필 시 서버·SDK 호환성을 다시 확인한다. 이 최신 정보를 엡실론델타 기존 프로젝트 사용 버전으로 쓰지 않는다.

### 4.6 LangSmith

실행 조사·평가·운영 모니터링을 제공한다.[S6] LangChain/LangGraph와 연결할 수 있지만 해당 프레임워크가 필수는 아니다. 현재 공식 문서는 OTel 기반 수집, 다른 프레임워크의 계측, Collector fan-out도 안내한다.[S7]

‘LangSmith는 LangChain 전용이고 Langfuse만 OTel을 지원한다’는 비교는 현재 문서와 맞지 않는다. 엡실론델타의 사용 이력은 팀의 선택이며 제품의 배타적인 지원 범위가 아니다.

## 5. 실제 기업 운영 사례

### 5.1 Ramp — 실행 기록에서 반복 실패를 찾아 수정

자료: Langfuse 고객 발표 요약, 2026-09-18.[S8]

- Ramp는 셀프호스팅 Langfuse와 OTel 기반 관측을 사용한다고 설명한다.
- Reflect가 실행 기록을 평가·군집화하고 반복 문제를 조사해 수정안을 제안하며 담당자가 수락·거절한다.
- 12개 에이전트에 적용하고 120개 이상의 제안을 반영했다고 발표했다.
- Ramp Research에 대해 토큰 사용 10~20% 감소, 도구 호출 15% 감소, 세션 시간 30% 단축을 발표했다.
- 집필 포인트: 수집→패턴 발견→담당자 수정 결정→운영 개선. 도구 설치만의 효과로 쓰지 않는다.
- 검증 메모: 발표자 경험을 공급사가 게시한 자료이며 독립 재현은 하지 않았다. Ramp 전체 사업·모든 에이전트 성과로 확대하지 않는다.

### 5.2 Trade Republic — 운영 절차를 에이전트로 바꾸는 과정

자료: Langfuse 고객 발표 요약, 2026-09-18.[S9]

- 금융사의 Ops Tools 팀은 셀프호스팅 Langfuse로 고정 프롬프트 절차를 도구 호출형 ReAct 구조로 전환한다.
- 실제 실행을 관측하고 좋은·나쁜 사례를 평가해 데이터셋에 남긴다.
- 수정용 homework set과 별도 exam set을 나누고 기존 절차와 새 에이전트를 비교한다. 두 세트 통과를 출시 판단에 사용한다고 설명한다.
- 집필 포인트: 이미 운영 중인 업무를 바꿀 때 실제 사례와 별도 검증으로 품질을 확인한다.
- 검증 메모: 절감률·자율 금융거래 범위를 이 자료만으로 추정하지 않는다.

### 5.3 Rakuten — 기업용·사내 AI의 실험과 검증

자료: LangChain 고객 사례, 2024-02-14.[S10]

- 시장 분석·고객지원·문서 답변 등의 기업용 AI와 사내 문서 AI를 설명한다.
- LangSmith로 실행을 확인하고 맞춤 평가 기준으로 모델·구성을 비교한다. 프롬프트 공유와 팀 협업도 설명한다.
- 집필 포인트: 여러 팀의 접근을 실험·평가 근거로 비교하고 운영 지식을 공유한다.
- 검증 메모: 당시 직원 확대 계획·생산성 목표를 달성 실적으로 쓰지 않는다.

### 5.4 엡실론델타 — PE사·내부 프로젝트 경험

2절의 확인된 사실만 활용한다. 금융 업무를 다루는 PE사에서 Langfuse·OTel을 사용한 경험과 MLOps 기반의 AgentOps 관점이 차별점이다. 확인하지 않은 실패 로그·개선 성과는 가상의 설명 예시나 설계 제안으로 구분한다.

추가 후보: LangChain 고객 목록에 Cisco의 중앙 관측 플랫폼과 Toyota의 Agent Andon Board 발표가 있다.[S11] 목록만으로 상세 구현·성과를 서술하지 않는다. 제조 사례가 필요하면 발표 영상·전문을 추가 확인한다.

## 6. 실행 완료까지 추적하는 가상 설계

```text
발주 업무 ID A
 요청 → 재고·공급사 조회 → 모델 후보 생성
 → 정책 검사 → 담당자 승인 → ERP API
 → 발주 ID·확정 상태 조회 → 결과 안내
```

- HTTP 200이어도 승인 대기라면 발주 확정 완료는 아니다.
- 모델 호출이 정상 종료돼도 SKU 선택이 틀렸다면 업무 실패다.
- API 응답 지연 중에도 외부 시스템에 생성됐을 수 있다. 업무 키·재시도·외부 결과를 함께 확인한다.
- 중복 방지는 멱등성·정책·실행 서비스가 담당한다. 관측으로 그 동작을 조사한다.

이 장면은 PE사 실제 사고가 아니다. 완료 문구·도구 응답·원천 시스템 상태를 연결하는 설계 예시다. 현업과 완료 기준을 먼저 합의한다.

## 7. 경영진이 확인할 지표

| 지표 | 확인할 내용 |
|---|---|
| 실제 완료율 | 합의된 업무 시스템 결과를 충족했나 |
| 인계·재작업 | 정당한 예외 인계와 부실 결과 수정을 구분 |
| 전체 처리 시간 | 승인·대기·재시도 포함 |
| 단계별 지연·p95 | 평균에 가려진 느린 요청·병목 |
| 반복·도구 호출 수 | 불필요한 루프·실패 재시도 |
| 성공 업무당 비용 | 모델·도구·검토·재작업 포함 |
| 근거·정책 적합성 | 현업 또는 평가 기준으로 판정 |
| 변경 전후 품질 | 모델·프롬프트·검색·도구 버전별 비교 |
| 관측 완전성 | span 누락·연결 끊김·수집 실패·샘플 비율 |

분모·기간·평가 방식·배포 버전을 명시한다. 샘플링된 trace의 비율은 전체 업무 집계와 구분한다.

## 8. 데이터·비용·관측 운영

- 입력·출력·도구 결과·첨부 중 무엇을 저장할지 정한다. 거래 자료 원문을 무조건 수집하지 않는다.
- 전송 전 마스킹을 점검한다. 직접 만든 SDK 입력만 가리고 제3자 OTel span은 그대로 내보내는 누락도 확인한다.[S12]
- 조직·사용자·프로젝트 조회 권한, 보관·삭제, 개발·운영 환경을 구분한다.
- Langfuse는 trace 단위 샘플링을 안내한다.[S13] 오류 중심 tail sampling은 별도 Collector 설계가 필요할 수 있다. head sampling에서 이미 버린 정보는 나중에 복구되지 않는다.
- 비동기 배치 전송은 짧은 프로세스 종료에서 flush/shutdown을 확인한다.
- 중복 계측·부모 연결 끊김·시간 불일치·필터로 빠진 업무 API를 점검한다.
- 병렬 span 시간을 단순 합하면 실제 지연을 과대 계산한다.
- 토큰 비용과 실제 청구·캐시·재시도·외부 도구 비용을 함께 확인한다.
- 관측 장애 시 업무 지속·기록 손실 알림 정책을 정한다. 도구 전체 기능의 실패 특성을 동일하게 가정하지 않는다.

## 9. 개선 루프와 도입

실행 관측 → 실패·지연 사례 선별 → 현업 판정 → 원인 가설·수정 → 회귀 평가 → 제한 배포 → 업무 성과 확인.

업무 하나를 선정하고 완료 기준을 정한 뒤 요청·검색·모델·도구·결과를 연결한다. 실제 실패를 시험문제로 남기고 근거 데이터·도구·승인·완료 확인 중 문제가 생긴 지점을 고친다.

흔한 실패: 최종 대화만 저장, 모델 호출만 추적, 대응 담당자 부재, 피드백과 실행 ID 분리, 버전·환경 혼합, 수집한 기록을 수정·평가에 사용하지 않음.
