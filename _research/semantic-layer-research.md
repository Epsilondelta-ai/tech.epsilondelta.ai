# 시맨틱 레이어: 영업팀과 재무팀의 매출이 다르면 AI도 헷갈립니다

## 1. 핵심 결론

시맨틱 레이어는 데이터의 업무상 의미와 계산 규칙을 정의하고, 분석 도구나 AI가 그 정의에 따라 데이터를 조회하도록 연결하는 계층이다. 단순히 컬럼 이름을 한글로 번역하는 사전보다 넓다. 지표 계산식, 집계 단위, 테이블 관계, 시간 기준 등을 기계가 사용할 수 있게 모델링한다. dbt, Looker, Snowflake, Cube는 서로 다른 위치와 방식으로 이를 구현한다. [S1][S2][S3][S4]

이번 글의 중심 질문은 **“AI가 숫자를 계산할 수 있는가?”보다 “어느 정의와 범위로 계산해야 하는지 알고 있는가?”**다.

부서별 숫자가 다르다고 항상 한쪽이 틀린 것은 아니다. 수주액, 회계상 매출, 입금액은 다른 사건을 측정한다. 모두를 하나의 숫자로 강제 통합하면 오히려 정보가 사라진다. 서로 다른 지표의 이름과 용도를 구분하고, 같은 지표를 같은 기간·권한·데이터 시점으로 조회할 때 같은 계산 기준을 사용하도록 해야 한다.

영업팀과 재무팀이 항상 각각 수주와 회계 매출만 본다고 일반화하지 않는다. 도입 장면에서는 가상의 회사가 용어를 혼용하는 상황으로 설정한다.

## 2. 경영진에게 설명할 개념

### 2.1 쉬운 비유

데이터베이스를 식재료 창고에 비유하면 시맨틱 레이어는 메뉴별 재료와 조리법을 정리한 운영 기준에 가깝다. AI가 ‘이름이 비슷한 재료’를 골라 매번 새로운 계산을 하는 대신, 어떤 지표를 어떤 조건으로 구할지 정해진 정의를 사용한다.

비유를 쓸 때는 여기까지만 활용한다. 실제 기술은 재료를 옮기는 일이 아니라 데이터 관계와 집계 규칙을 조회 경로에 반영하는 것이다.

### 2.2 무엇을 정의하는가

| 구성 요소 | 업무상 의미 | 가상의 판매 분석 예 |
|---|---|---|
| 엔터티·키 | 같은 대상을 연결하는 식별자 | 고객 ID, 주문 ID |
| 차원(Dimension) | 나누거나 걸러 보는 기준 | 지역, 판매 채널, 주문일 |
| 측정값·사실 | 기록에 담긴 수량과 금액 | 주문 항목 금액, 수량 |
| 지표(Metric) | 업무 목적에 맞춘 계산 결과 | 완료 주문 금액 합계, 주문당 평균 금액 |
| 집계 단위(Grain) | 한 행이 무엇을 뜻하는가 | 주문 한 건인지 상품 항목 한 건인지 |
| 관계·조인 | 테이블을 어떤 조건으로 연결하는가 | 주문과 고객의 다대일 관계 |
| 시간 규칙 | 어느 날짜·시간대·주기로 묶는가 | 주문일 기준 월별, 한국 시간 |
| 설명·동의어 | 현업 표현과 모델의 연결 | 구매 채널, 주문 경로 등 표현의 대응 |
| 권한·운영 정보 | 누가 무엇을 볼 수 있고 언제 갱신했는가 | 사업부별 열람 범위, 최종 적재 시각 |

제품마다 measure, fact, metric의 의미와 지원 범위가 다르다. 이 표는 공통 이해를 위한 정리이며 특정 제품의 스키마 명세가 아니다. [S1][S2][S3][S4]

### 2.3 유사 개념과의 관계

| 구분 | 주로 해결하는 문제 | 시맨틱 레이어와의 연결 |
|---|---|---|
| 데이터 웨어하우스·레이크하우스 | 데이터를 저장·처리 | 실제 조회·계산의 기반 |
| ETL/ELT·데이터 마트 | 원천을 정제하고 분석 구조로 변환 | 지표가 의존할 신뢰 가능한 테이블 제공 |
| 데이터 카탈로그·용어집 | 데이터와 정의의 발견·문서화 | 정의를 찾게 돕지만 그것만으로 계산을 강제하지는 않음 |
| BI 대시보드 | 결과를 시각화하고 탐색 | 공통 모델을 소비하는 화면 중 하나 |
| Text-to-SQL | 질문을 SQL로 변환 | 질문에 맞는 지표·관계를 선택할 의미 정보가 필요 |
| RAG | 관련 문서·근거 검색 | 정책 설명에는 유용하며 정형 집계는 실행 도구와 연결 가능 |
| MCP | AI와 도구 사이 호출 인터페이스 | 지표 조회 도구를 연결하지만 지표 정의를 대신하지 않음 |
| 온톨로지·지식그래프 | 개념·관계와 도메인 지식 표현 | 분석 지표 모델과 결합 가능하나 동의어는 아님 |

이 비교는 편집용 종합 정리다. ‘시맨틱 레이어=모든 업무 맥락’이나 ‘시맨틱 검색=시맨틱 레이어’로 설명하지 않는다. 기존 BI에서도 쓰던 모델링 방식이 생성형 AI의 데이터 접근에 다시 중요해진 맥락으로 소개한다.

## 3. 매출 예시를 어떻게 풀 것인가

### 3.1 숫자가 다를 수밖에 없는 경우

가상 회사의 월간 보고를 생각한다.

| 질문의 실제 목적 | 선택할 지표의 예 | 확인할 기준 |
|---|---|---|
| 이번 달 얼마나 새 계약을 따냈나? | 신규 수주액 | 계약 확정 시점, 취소·변경 처리 |
| 이번 달 손익 보고에 반영할 실적은? | 회계 매출 | 회사가 승인한 회계 정책과 마감 기준 |
| 이번 달 현금은 얼마나 들어왔나? | 입금액 | 입금일, 미매칭 입금, 선금 구분 |
| 어느 채널에서 판매가 늘었나? | 채널별 판매 지표 | 주문/출고/결제 중 기준, 환불·할인 처리 |

여기서 AI가 할 일은 숫자 하나를 자신 있게 고르는 것이 아니라 사용 목적을 확인하고 해당 지표를 조회하는 것이다. ‘매출’처럼 여러 의미가 가능한 말에는 재질문하거나 적용한 정의를 명시하도록 설계한다. 구체 회계 인식 방법을 이 글에서 일반 법칙으로 규정하지 않는다.

### 3.2 같은 지표인데도 숫자가 달라지는 경우

환불 반영 여부, 시간대, 내부 거래 제외, 통화 환산 시점, 중복 데이터, 마감 전후, 조회권한이 다를 수 있다. 지표 이름만 통일해도 원천 오류나 늦게 들어온 데이터까지 자동으로 해결되지는 않는다.

권장 답변 형식 — 설명용 예시:

> 조회 지표: 완료 주문 금액(회계 매출과 별도 관리하는 운영 지표)
> 기간: 지정 월의 시작 이상, 다음 달 시작 미만 / 한국 시간
> 범위: 권한이 있는 국내 온라인 채널
> 제외: 취소 주문 / 할인·환불은 해당 지표 정의에 명시한 방식 적용
> 데이터 기준 시각 및 지표 버전: 조회 결과와 함께 표시

금액만 답하지 않고 어떤 숫자인지 확인할 정보를 함께 전달한다.

## 4. 기술 구성: 질문에서 숫자까지

### 4.1 참고 아키텍처 — 자체 설계 제안

`현업 질문 → 의미·기간 확인 → 허용 지표 탐색 → 지표·차원·필터 선택 → 쿼리 생성·검증 → 권한 내 데이터 실행 → 수치와 기준 설명`

원천 시스템에서 분석 테이블까지의 적재·정제는 이 조회 흐름에 앞서 별도로 운영한다.

1. **질문 해석:** 사용자가 말한 매출의 뜻, 기간, 지역을 확인한다. 미확정 조건을 조용히 추정하지 않는다.
2. **지표 발견:** 설명·동의어와 함께 사용 가능한 지표를 제공한다. 사용자의 업무·권한과 무관한 모델까지 한꺼번에 노출하지 않는다.
3. **쿼리 구성:** 승인된 지표 ID와 차원·필터로 요청하거나 시맨틱 모델을 참고해 SQL을 생성한다.
4. **실행 검증:** 허용된 연산·필터·관계인지 확인한다. 임의 원천 테이블 접근을 허용하면 공통 기준을 우회할 수 있다.
5. **계산:** 데이터 엔진이 집계를 수행한다. 모델이 응답 문장에서 직접 금액을 합산하는 방식과 구분한다.
6. **응답:** 실행 결과에 없는 숫자나 인과 설명을 생성하지 않게 한다. 지표 정의·조회 범위·갱신 시점을 함께 보여준다.
7. **기록:** 질문, 선택 지표, 모델 버전, 권한, 실행 결과와 사용자 교정을 추적한다.

### 4.2 의미를 알려주는 것과 실행을 제한하는 것

AI에게 계산식 설명을 컨텍스트로 주는 방식과, 정해진 지표 조회 인터페이스만 호출하도록 하는 방식은 통제 수준이 다르다. 전자는 SQL 생성의 참고 정보를 제공하고 후자는 조회 가능한 연산 범위를 좁힐 수 있다. 실제 제품은 두 방식을 조합하기도 한다.

따라서 ‘시맨틱 모델을 넣었다’만 확인하지 말고 **최종 실행이 공통 정의를 실제 사용했는지** 확인한다. 자연어 해석, 지표 선택, 결과 설명에는 여전히 오류 가능성이 있으므로 계산 경로의 재사용만으로 전체 응답의 정확성을 보장한다고 표현하지 않는다.

### 4.3 조인 때문에 매출이 늘어나는 문제

설명용 숫자: 주문 A의 총액이 100이고 상품 항목이 두 개라면, 주문 테이블을 항목 테이블과 연결한 뒤 주문 총액을 단순 합산할 경우 100을 두 번 더해 200이 될 수 있다. 금액 단위와 무관한 중복 집계 예시다.

처음부터 행 단위와 관계를 정확히 선언해야 한다. dbt의 MetricFlow는 엔터티 유형을 이용해 조인 경로를 만들고 fan-out·chasm 조인을 제한한다고 설명한다. 문법상 실행 가능한 쿼리와 업무상 올바른 집계는 따로 검증할 일이다. [S5]

### 4.4 합계로 끝나지 않는 지표

아래는 설계 시 확인할 일반적인 집계 문제다.

- 전환율: 기간별 전환율의 단순 평균과 전체 전환 수/전체 대상 수는 다를 수 있다.
- 순고객 수: 여러 채널에서 구매한 고객을 채널별로 센 뒤 더하면 중복된다.
- 재고: 날짜별 잔량을 모두 더한 값과 월말 재고는 다른 의미다.
- 누계: 어느 날짜부터 누적하는지, 데이터가 없는 날짜를 어떻게 처리하는지 정한다.
- 과거 지역별 매출: 고객의 현재 지역을 쓸지 거래 당시 지역을 쓸지 정한다.

dbt 문서는 단순·비율·누계·파생·전환 지표 등 여러 유형을 구분한다. 특정 문법은 버전별로 달라지므로 글에는 계산 원리 중심으로 설명한다. [S6]

### 4.5 지표 명세의 예

아래는 제품 독립적인 의사 명세이며 실행 가능한 dbt·Cube 설정 파일이 아니다.

```yaml
metric_id: completed_order_amount
label: 완료 주문 금액
purpose: 온라인 판매 운영 분석
grain: 주문당 1행
source: 검증된 주문 분석 테이블
calculation: 완료 주문의 확정 금액 합계
time_basis: 주문 완료 시각
timezone: Asia/Seoul
dimensions: [판매채널, 상품군, 지역]
policy_refs: [취소환불처리기준, 통화환산기준]
owner: 판매운영 담당자
version: 승인된 지표 정의 버전
access: 사용자 역할에 따른 범위 적용
```

자료 소유자가 의미·예외를 확정하고 개발자가 실제 테이블·계산식과 연결해야 한다. `grain`을 적었다고 원천 데이터의 중복이 사라지는 것은 아니므로 키 유일성도 시험한다.

## 5. 실제 기업의 AX·분석 도입 사례

### 5.1 Sweetgreen — 숫자 대사에서 대화형 분석으로

**자료:** dbt Labs 고객 인터뷰형 글, 최종 수정 2026-01-21. [S7]

- 외식 체인 Sweetgreen은 같은 대시보드에서도 매출이 달라지고 새 질문마다 개별 데이터 흐름을 만드는 문제를 설명했다.
- 주문·고객·상품 등 사업 사건에 맞춰 사실·차원 테이블을 재구성하고 지표 정의, 테스트, 문서화를 정비했다. 그 위에 Claude·MCP·dbt Semantic Layer를 연결했다.
- 담당자는 데이터팀의 처리 여력을 기다리며 2주가 걸리던 요청을 셀프서비스 분석으로 30분에 처리하는 변화를 소개했다. SQL 실행 시간의 전후 비교는 아니다.
- 글 하단에 대화형 기능은 Claude Desktop 사용자 약 15~20명, 시맨틱 모델 3~5개로 시작하는 소규모 파일럿이라고 명시한다.
- **집필 가치:** 기반 정비와 제한된 AI 적용을 함께 설명하기 좋다. 전사 완전 도입으로 확대해서 쓰지 않는다.

### 5.2 Drata — 고객 담당자의 분기 보고서 작성

**자료:** Cube 고객 사례, 게시일 미확인, 조사일 열람. [S8]

- 고객 담당자는 여러 대시보드의 지표를 모아 비교 기준을 계산하고 분기 고객 보고서(QBR)를 작성했다. 자료는 건당 2~3시간, 담당자당 분기 20~30시간의 기존 작업 부담을 설명한다.
- 공통 시맨틱 레이어를 구조화된 API 조회와 자연어 분석에 함께 사용했다. 의미가 드러나는 이름, 풍부한 설명, 명시적인 관계, 사전 계산한 비교 지표를 준비했다.
- 공급사 사례는 고객 담당자가 분기 수십 시간을 되찾았다고 설명한다. 절감 산식과 독립 검증 자료는 제시하지 않는다.
- **집필 가치:** 같은 지표를 고객 대시보드와 AI 보고서에서 재사용하는 구체적 업무. 보고서 생성 속도만 아니라 숫자를 모으고 맞추는 과정을 다룰 수 있다.

### 5.3 Alcon — 기존 대시보드와 AI 답변의 지표를 맞추기

**자료:** Cube 고객 사례, 게시일 미확인, 조사일 열람. [S9]

- 안과 제품 기업 Alcon은 팀마다 KPI 계산 방식이 달랐고 기존 대시보드로 답할 수 없는 질문마다 개발 요청이 필요했다고 설명한다.
- Cube로 계정·제품·주문 등을 모델링하고 지표 계산, 접근 제어, 캐싱, API를 공통으로 관리했다.
- 새 시스템을 시험할 때 챗봇의 KPI 응답과 기존 Tableau 화면의 값이 일치했다고 소개한다. 승인된 지표만 답변에 쓰도록 하는 운영 규칙도 설명한다.
- **집필 가치:** 기존 BI를 버리는 이야기가 아니라 BI와 대화형 분석이 같은 계산 기준을 사용하도록 연결한 이야기.
- 공개 문서만으로 전체 사용자 수나 모든 질문의 정확도는 확인되지 않는다. 의료기업 사례지만 진단·진료 AI 사례가 아니다.

### 5.4 Bilt Rewards — 고객용 분석 화면의 비용과 중복 로직

**자료:** dbt Labs 고객 사례, 게시일 미확인, 조사일 열람. [S10]

- 리워드 플랫폼 Bilt는 소규모 분석팀으로 다수 파트너에게 분석 화면을 제공했다. 기존 임베디드 BI의 사용자별 과금과 BI·웨어하우스에 나뉜 변환 로직을 문제로 설명한다.
- 지표와 관계를 dbt에 모으고 GraphQL 경로로 데이터를 받아 자체 화면에서 표현하는 구조로 변경했다.
- 자료는 BI 임베드에서 이전하면서 분석 비용을 80% 절감했다고 소개한다. 비용 감소를 AI 모델 성능 개선이나 AI 도입 단독 성과로 해석하지 않는다.
- 이 사례 페이지의 AI·LLM 활용은 탐색 단계다. 별도 2025 행사 소개에는 LLM 연결 발표가 있지만 발표 소개만으로 후속 운영 규모를 확정하지 않는다. [S11]
- **집필 가치:** 지표 정의와 화면을 분리하는 구조의 경제적 이유를 설명하는 보조 사례.

### 5.5 사례 선정 우선순위와 국내 조사 결과

본문에는 Sweetgreen과 Drata를 우선 사용하고 Alcon을 보강하면 서로 다른 업무를 보여줄 수 있다. Bilt는 비용·임베디드 분석을 설명할 때 선택한다. 모두 공급사가 공개한 고객 사례이므로 출처를 문장 가까이 붙인다.

이번 조사에서 국내 기업의 명명된 시맨틱 레이어 도입과 실제 운영 효과를 함께 확인할 수 있는 충분한 1차 자료는 확보하지 못했다. 국내 BI·클라우드 도입만을 시맨틱 레이어 기반 AI 도입으로 바꾸어 쓰지 않는다. 한국어 제품 소개나 데모는 실제 고객 성과의 근거에서 제외했다.

## 7. 보안·성능·운영

### 7.1 같은 계산 기준과 같은 열람 범위는 다른 문제

지점장은 자기 지점, 본사 담당자는 전사 범위를 조회할 수 있다. 같은 지표라도 권한에 따라 총액은 달라질 수 있다. ‘누가 물어도 같은 숫자’보다 **같은 정의·같은 범위·같은 데이터 시점에서 일관된 결과**라고 설명하는 편이 정확하다.

Cube는 인증과 데이터 인가를 구분하고 사용자 그룹·속성 또는 security context에 따라 접근 정책을 적용한다. Power BI의 RLS는 Workspace Viewer에 적용되지만 Admin·Member·Contributor에는 적용되지 않는다고 문서에 명시한다. 연결 계정을 넓은 권한으로 만들고 프롬프트로만 조회 범위를 제한하는 구성은 피해야 한다. [S13][S16]

### 7.2 사전 집계와 최신성

Cube의 사전 집계는 미리 물리화한 질의 결과를 이용해 원천 조회 부담을 줄이는 방식이다. 요청과 맞는 사전 집계가 없을 때 원천으로 갈지 오류로 끝낼지 구성에 따라 다르다. [S14]

운영 제안: 결과에 적재 시각을 붙이고 허용 지연을 정한다. 사용자·고객별 권한이 다른 결과를 캐시에서 잘못 재사용하지 않는지 시험한다. 지표 정의를 바꾸면 캐시·사전 집계·하위 보고서의 갱신도 함께 확인한다.

### 7.3 기준의 소유자와 변경 이력

아래는 자체 운영 제안이다.

- 현업 소유자: 지표의 사용 목적, 제외 조건, 승인할 변경을 결정.
- 데이터팀: 원천·키·관계·집계와 테스트를 관리.
- AI팀: 질문 해석·재질문·도구 호출·응답 검증을 관리.
- 보안 담당자: 사용자 신원 전달, 역할별 접근과 감사 기록을 점검.

지표 ID를 유지한 채 정의를 바꾸면 과거 보고와 비교가 깨질 수 있다. 시행일, 버전, 재계산 여부, 영향을 받는 대시보드와 에이전트를 기록한다. 모든 부서를 한 번에 통합하기보다 업무 영역별로 소유권을 두고 공통 고객·제품 기준을 맞추는 접근을 검토한다.

## 8. 실패 시나리오와 평가

실제 사고 목록이 아닌 도입 시험용 시나리오다.

| 시험할 상황 | 기대 동작 |
|---|---|
| ‘이번 달 매출’의 의미가 둘 이상 | 의미·기간을 확인하거나 선택한 정의 명시 |
| 주문과 항목을 연결해 중복 발생 | 올바른 집계 단위로 계산 |
| 전환율·순고객 수를 다른 차원으로 묶음 | 분자·분모 또는 중복 제거 기준 유지 |
| 월말 자정·해외 시간대 | 정한 업무 시간대로 기간 처리 |
| 환불이 다음 달 들어옴 | 승인한 귀속 규칙 적용 |
| 데이터 없음 / 0 / 권한 없음 | 서로 구분해 응답 |
| 권한이 다른 두 사용자가 같은 질문 | 각자 허용 범위만 반환 |
| 지표 밖의 질문 | 지원 범위를 설명하고 확인 절차로 전달 |
| 계산값은 맞고 설명이 틀림 | 수치·단위·증감·해석을 별도 검증 |
| 정책 변경 뒤 기존 질문 재실행 | 예상된 변경과 회귀 오류를 구분 |

Snowflake의 평가 기능은 검증된 질문·SQL을 기준으로 생성 SQL의 실행 결과를 비교하고 정확도·회귀·지연을 기록한다. 평가 대상으로 선택한 질의는 임시 모델에서 제거해 정답이 그대로 참고 자료로 들어가는 것을 막는다고 설명한다. [S17]

자사 평가에서는 SQL 문자열 일치만 보지 말고 결과 행·열·값·단위·필터를 비교한다. 서로 다른 SQL도 같은 정답을 낼 수 있다. 반대로 현재 데이터에서 우연히 같은 결과가 나는 쿼리를 잡으려면 중복·빈값·경계 날짜를 넣은 시험 자료도 필요하다.

성과 지표 제안: 올바른 지표 선택률, 계산 정확도, 재질문 적절성, 권한 위반 건수, 근거 표시, 담당자 수정 시간, 응답 지연, 질문당 비용. 공급사의 ‘100% 정확’ 같은 표현은 전체 업무 보증으로 옮기지 않는다.

## 9. 우리 회사의 첫 적용 — 기획 제안

1. 회의에서 반복해 대사하는 숫자와 현업 질문을 수집한다.
2. 지표 이름·계산식·기간·제외 조건·담당자를 정리한다. 다른 목적의 지표는 이름을 나눈다.
3. 원천 키와 집계 단위를 확인하고 기준 보고서와 계산 결과를 대조한다.
4. 기존 BI 모델을 재사용할지 공통 조회 계층을 둘지 결정한다.
5. 작은 범위의 조회 도구를 AI에 연결하고 자주 묻는 질문과 예외를 시험한다.
6. 제한된 사용자로 운영하며 틀린 지표 선택과 현업 교정을 기록한다.
7. 성과와 관리 부담을 확인한 뒤 지표·부서를 넓힌다.

첫 결과물은 모델 이름이나 대시보드 개수가 아니라 ‘어떤 질문에 어떤 기준으로 답할 수 있는가’ 목록이다. 문서가 없는 상황에서 전사 용어집부터 장기간 만드는 프로젝트로 확대하지 않는다.
