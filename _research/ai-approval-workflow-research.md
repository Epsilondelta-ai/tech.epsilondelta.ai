# [사전 조사] AI에게 결재선을 만드는 법: 어디까지 맡기고, 언제 승인받을까?

## 0. 먼저 읽을 조사 결론

> AI에게 결재선을 만든다는 것은, 맡길 수 있는 행동과 조건을 정하고, 필요한 건은 권한 있는 사람이 검토한 뒤, 그 사람이 확인한 내용대로만 시스템이 실행하도록 구성하는 일이다.

위 문장은 조사 자료를 종합한 설명용 정의다. ‘AI 결재선’이라는 독립적인 국제 표준이 있다는 뜻은 아니다. 업무 위임·접근 제어·실행 전 승인·예외 처리·운영 기록을 익숙한 조직 용어로 묶은 표현이다.

핵심은 다음과 같다.

1. **잘할 수 있는 일과 해도 되는 일은 별개다.** 좋은 답을 내는 모델에도 고객에게 메일을 보내거나 발주를 확정할 권한은 따로 부여해야 한다.
2. **모든 단계에 사람을 끼울 필요는 없다.** 초안은 자동 작성하고 외부 게시 전에 확인할 수도 있고, 사전에 정한 범위 안에서 자동 처리하며 예외만 사람에게 넘길 수도 있다. 실제 기업은 두 방식을 모두 사용한다.
3. **검토 요청과 실행 차단은 다르다.** AI가 채팅으로 허락을 묻는 것 외에, 승인되지 않은 동작을 실행 단계에서 막을 수 있어야 한다. [OWASP Excessive Agency][owasp-agency]
4. **승인 대상은 구체적이어야 한다.** ‘고객 문제 해결’이 아니라 어떤 주문을 얼마에 환불할지, 누구에게 어떤 내용과 첨부물을 보낼지를 확인한다. [OWASP 거래 승인][owasp-transaction]
5. **승인이 끝난 뒤에도 처리할 일이 있다.** 인자 변경, 승인 만료, 작업 재개, 응답 유실, 중복 실행에 대한 규칙이 필요하다.
6. **승인자는 인력이자 운영 자원이다.** 알림을 늘리는 것만으로는 검토 품질을 유지하기 어렵다. 판단 근거와 대기열, 처리 시간, 대체 담당자를 함께 준비해야 한다. [AWS 위험별 승인 설계][aws-risk]

**집필의 중심 질문:** 우리 회사 AI가 실제 업무 시스템을 움직일 때, 어떤 행동은 바로 처리하고 어떤 행동은 누가 무엇을 보고 승인해야 할까?

## 1. 개념: 무엇을 서로 구분해야 하는가

### 1-1. 인증·권한·승인·검수는 같은 기능이 아니다

| 개념 | 확인하는 질문 | 업무 예시 |
|---|---|---|
| 인증, Authentication | 요청한 주체가 누구인가? | 영업팀 직원의 계정인지 확인 |
| 권한, Authorization | 이 주체가 이 대상에 이 행동을 할 수 있는가? | 담당 고객의 계약 조회는 가능하지만 가격 변경은 불가 |
| 업무 승인, Approval | 이번 실행 내용에 권한 있는 담당자가 동의했는가? | 특정 고객에게 보낼 할인 견적 확정 |
| 검수, Review / Validation | 자료·결과가 업무 기준에 맞는가? | 금액 계산과 납기 조건 대조 |
| 고객 동의, Consent | 고객이 특정 수집·이용·행위에 동의했는가? | 미팅 녹음·AI 기록에 대한 동의 |
| 이관, Handoff / Escalation | 누가 이어서 이 일을 처리할 것인가? | 분쟁 환불을 고객지원 책임자에게 배정 |

표는 업무 설계를 위한 구분이다. 검토 후 승인하는 화면 하나에 여러 기능을 묶을 수 있지만, 로그인했다고 해당 거래를 승인한 것은 아니다. 사람이 동의했더라도 그 사람의 권한 밖인 동작을 실행하게 해서는 안 된다. [거래 승인 원칙][owasp-transaction], [AgentCore Identity][agentcore-identity]

### 1-2. Human-in-the-loop를 결재 버튼 하나로 축소하지 않는다

Human-in-the-loop(HITL)는 AI가 포함된 과정에 사람이 참여하는 여러 방식을 가리킨다. 이번 글에서는 **실행 전에 사람이 검토·승인하는 경우**에 집중한다. 답변 평가, 학습용 라벨링, 상담원 이관도 사람이 참여하는 일이지만 목적은 다르다. [Bedrock HITL 예제][bedrock-example]

설명에 유용한 운영 방식은 다음과 같다. 이는 모든 제품에 통용되는 성숙도 등급이 아니라 이번 글의 분류다.

| 운영 방식 | 사람의 역할 | 적합성을 검토할 상황 |
|---|---|---|
| 초안 지원 | 결과를 확인하고 직접 최종 행동 | 고객별 제안·복잡한 계약 문안 |
| 실행 전 건별 승인 | 제안된 실행을 확인한 뒤 허용·거절 | 외부 공지, 민감한 정보 변경 |
| 사전 위임 범위 내 자동 처리 | 허용 조건을 정하고 예외 처리 | 기준이 명확한 반복 경비·정형 요청 |
| 실행 중 감독·사후 점검 | 이상 징후에 개입하고 범위를 조정 | 영향이 제한되고 관측·복구가 가능한 작업 |
| 자동 실행 금지 | 사람이 전담하거나 별도 통제 과정 사용 | 조직이 위임하지 않은 행위, 허용 불가 대상 |

사후 로그를 읽는 것은 사전 승인을 받은 것과 다르다. 한 에이전트 안에서도 행동별로 다른 방식을 섞을 수 있다. 고객 정보를 읽고 메일 초안을 만드는 동안에는 자동으로 진행하되, 외부 발송은 사람이 확정하는 식이다.

### 1-3. 사람 직원의 전결 규정에서 가져올 수 있는 것

직원에게도 담당 업무, 금액 한도, 예외 승인, 대결자, 직무 분리가 있다. AI에도 같은 질문을 적용할 수 있다. 다만 실행 속도와 호출 횟수가 커지므로 **건당 한도뿐 아니라 누적 금액·빈도·여러 에이전트가 공유하는 예산**도 설계 대상으로 삼는다.

예를 들어 ‘10만 원 이하’라는 조건만 두면 동일 주문의 분할 환불이나 반복 호출을 걸러내지 못할 수 있다. 이 예시는 특정 회사의 사건이 아니라 설계상 검토할 문제다. 금액·대상·효과를 함께 정하고, 실행 주체에게 자기 한도를 바꿀 관리 권한은 주지 않는 방향이 적절하다. [OWASP 에이전트 실행 통제][owasp-agent], [AgentCore 정책 강제 모드][agentcore-enforce]

## 2. 실제 기업 도입 사례 — 본문의 우선 자료

### 2-1. 사례 지도

| 사례 | 산업·업무 | 확인된 사람의 역할 또는 자동 처리 경계 | 자료 성격 | 집필 우선순위 |
|---|---|---|---|---|
| Ramp Policy Agent | 재무·경비 검토 | 정책에 맞는 건 처리, 불확실한 건 기존 사람 절차로 이관 | 엔지니어링 회고·자체 사용 | 높음 |
| Morgan Stanley Debrief | 금융 상담 후속 메일 | 담당 자산관리사가 초안을 편집하고 발송 | 도입 기업 직접 발표 | 높음 |
| Zapier 장애 공지 | SaaS 고객 커뮤니케이션 | Slack 승인 후 승인된 문안을 상태페이지에 게시 | 자체 업무 운영 설명 | 높음 |
| Lemonade AI Jim | 보험금 청구 | 처리 권한 밖이거나 우려가 있는 청구는 사람 전문가에게 배정 | 연간 공시 | 높음 |
| Kaiser Permanente / Abridge | 임상기록 | 의료진이 검토·수정한 뒤 공식 진료기록에 반영 | 도입 기관 운영 설명 | 보조 |
| Walmart / Pactum | 구매·공급사 협상 | 사전 설정한 협상 범위라는 제품 운영 모델과 실제 도입 확인 | 공급사 고객 사례·제품 설명 | 보조 |

핵심 세 사례만 본문에 쓴다면 **Ramp + Morgan Stanley 또는 Zapier + Lemonade**를 권한다. 자동 처리, 실행 전 검토, 예외 이관의 차이를 보여주기 좋다. 여러 산업을 나열하는 것보다 각 사례의 승인 지점을 구체적으로 설명하는 편이 유용하다.

### 2-2. Ramp: 애매한 경비를 억지로 승인·거절하지 않는다

**확인한 운영 사실.** Ramp는 2025-07-10 엔지니어링 글에서 경비 규정에 따라 승인·거절·검토 필요를 구분하는 Policy Agent를 설명했다. 관련 규정 조항과 판단 이유를 보여주며, 판단이 불확실하면 도입 전부터 쓰던 사람 이관 절차로 돌아간다. 회사는 내부 적용 후 승인의 **65% 이상을 에이전트가 완전히 처리**했다고 보고했다. [Ramp 운영 회고][ramp-engineering]

**집필 포인트.** 사람 검토를 모든 건에 추가하는 방법만 있는 것은 아니다. AI가 처리할 수 있는 범위를 정하고, 사람에게는 무엇이 애매한지 알려주는 방식도 가능하다.

**별도 제품 문서에서 확인한 구성.** 현재 도움말에서는 Policy Agent를 결재 단계에 넣고 금액·부서·법인·프로그램별 자동 승인 조건을 설정할 수 있다. 추천만 하는 경우와 실제 자동 승인을 구분한다. 검토자는 정책 조항·버전·변경 이력을 확인할 수 있다. 시험할 때 관리자에게만 평가를 보이게 설정하는 것으로는 자동 승인을 끌 수 없으며, 실제 워크플로를 조정해야 한다. [Ramp 자동 승인 설정][ramp-policy]

**연구 메모.** 65%는 Ramp가 보고한 승인 처리 비율이지 비용 절감률이나 전체 고객의 평균이 아니다. 문서의 금액 한도 예시는 고객이 구성할 수 있는 예이지 Ramp 내부 기준이 아니다. 자동 거절·실제 지급까지 모두 같은 동작으로 묶지 않는다.

### 2-3. Morgan Stanley: AI가 써도 고객에게 보내는 결정은 담당자가 한다

**확인한 운영 사실.** 2024-06-26 발표한 Debrief는 고객 동의를 받아 상담 미팅을 기록하고 요약·후속 업무·메일 초안을 만든다. 담당 자산관리사(Financial Advisor)가 메일을 편집하고 자신의 판단으로 발송한다. 발표문에는 실제 이용자의 검토·편집·발송 경험도 나온다. [Morgan Stanley 발표][morgan]

**집필 포인트.** ‘메일 초안 작성’과 ‘외부 발송’을 나누는 익숙한 사례다. 승인자는 무조건 상급자일 필요 없이 고객 상황을 알고 해당 발송 권한을 가진 담당자일 수 있다.

**연구 메모.** 같은 발표에 Salesforce 노트 저장 기능도 있지만 저장 전 동일한 승인 절차가 있다는 설명은 없다. 고객의 녹음 동의와 담당자의 발송 판단도 다른 절차다. API 차원의 우회 방지 구조까지 공개한 자료는 아니다.

### 2-4. Zapier: 초안과 실제 게시 사이에 승인 단계를 둔다

**확인한 운영 사실.** 2026-01-19 갱신된 Zapier의 자체 사용 소개에는 다음 흐름이 명시돼 있다. 지원 담당자가 Typeform에 장애 내용을 입력하면 AI가 팀의 규칙·양식에 맞춰 공지 문안을 만들고, Slack에서 승인을 받은 다음 webhook으로 승인된 문안을 상태페이지에 게시한다. [Zapier 자체 업무 사례][zapier]

```text
담당자의 장애 정보 입력 → AI 공지 초안 → Slack 승인 → 승인된 문안 게시
```

**집필 포인트.** 작성과 게시를 나누는 기술 구성이 간단하게 보인다. ‘나중에 누가 읽어본다’가 아니라 고객에게 나가기 전에 확인하는 경계를 설명할 수 있다. 별도 제품 문서도 Slack 승인·거절에 따른 실행 지속·중단을 설명한다. [Slack 승인 기능][zapier-approval]

**연구 메모.** 현재 사례는 특정 모델 대신 AI by Zapier라고 표시한다. 위 워크플로만의 오류 감소율·시간 절감 수치는 공개하지 않는다. 승인자 직급·만료·게시 자격 증명의 내부 설정은 미공개다.

### 2-5. Lemonade: 권한 밖의 청구를 처리할 사람까지 배정한다

**확인한 운영 사실.** Lemonade의 2025년 Form 10-K는 AI Jim이 처리 권한이 없거나 우려가 있는 청구를 사람인 보험금 청구 전문가에게 배정한다고 설명한다. 전문 분야·자격·업무량·일정을 고려해 배정하며, 담당자는 관련 정보와 위험 신호를 업무 시스템에서 확인한다. [Lemonade 공시][lemonade]

2025-12-31 기준 회사가 보고한 청구 자동 처리 비율은 약 **55%**다. 최초 사고 접수 자동화 **96%**와 다른 지표다. 해당 공시의 제출일은 2026-02-25다. [제출 내역][lemonade-filing]

**집필 포인트.** 전 건 승인 대신 사전에 부여한 권한 안에서 처리하고 예외를 사람에게 맡긴다. ‘사람에게 넘긴다’ 이후의 담당자 선정과 처리 역량도 운영 설계에 포함된다는 예다.

**연구 메모.** 금액별 처리 한도·위험 점수의 구체적인 기준은 공개하지 않았다. 최신 LLM 하나의 성능으로 설명하지 않고, 보험사의 AI 업무 시스템 사례로 다룬다.

### 2-6. Kaiser Permanente: 초안이 공식 기록이 되는 지점에서 검토한다

**확인한 운영 사실.** Kaiser Permanente는 Abridge가 진료 대화로 작성한 기록 초안을 의사·임상의가 검토하고 수정한 뒤 전자의무기록에 반영하도록 요구한다. 2025-03-25 운영 설명에 이 순서가 명시돼 있다. [Kaiser Permanente 운영 원칙][kaiser]

**집필 포인트.** AI가 만든 내용이 다음 업무에서 공식 자료가 되는 지점에 검토 책임을 둘 수 있다. 환자의 AI 기록 동의는 의료진의 내용 검토를 대신하지 않는다.

**연구 메모.** 진료기록 작성 사례이지 AI가 진단·처방을 결정하는 사례가 아니다. 시스템이 등록을 차단하는 내부 API 구현까지는 공개하지 않았다.

### 2-7. Walmart / Pactum: 협상할 범위를 먼저 정하는 방식

**확인한 사실을 두 층으로 나눈다.** Pactum 고객 사례는 Walmart의 공급사 가격 할인·지급 조건 협상 자동화 도입을 설명한다. 별도의 2026-04-10 제품 설명은 구매팀이 가격 한도·조건 범위·카테고리 정책을 먼저 정하며, 사람의 판단이 필요하면 구매 담당자에게 넘기는 운영 방식을 설명한다. [Walmart 도입][pactum-clients], [Pactum 운영 방식][pactum-rules]

**집필 포인트.** 협상 중 모든 발언을 상급자에게 승인받기보다 허용 가능한 범위를 미리 위임하는 방법을 설명할 수 있다.

**연구 메모.** 2026년 일반 제품 설명을 Walmart의 특정 시점 설정으로 단정하지 않는다. Walmart의 실제 금액 한도·최종 서명권자·건별 결재 여부는 이번 자료에서 확인하지 못했다. 글에서는 공급사의 운영 설명임을 보존한다.

## 3. 실패 사례: 승인 문구 외에 접근 경계가 필요한 이유

### 3-1. Replit의 개발 작업이 운영 데이터에 영향을 준 사고

Replit는 2025-07-29 공식 글에서 Jason Lemkin의 앱 데이터베이스에서 Agent가 데이터를 삭제한 사건을 인정했다. 당시에는 개발 중 변경이 운영 애플리케이션에 영향을 줄 수 있었고, 이후 개발·운영 DB를 기본적으로 분리했다고 설명한다. 같은 글에 따르면 해당 데이터는 롤백으로 완전히 복구됐다. [Replit 사고 후속 설명][replit]

**이 주제에 맞는 해석:** AI에게 주의사항을 전달하는 일 외에도 어떤 환경·데이터에 접근할 수 있는지 기술적으로 나눠야 한다. 민감한 실행 권한을 쥐여 준 뒤 자연어 지침에만 기대는 구성을 검토할 때 쓸 수 있다.

**연구 메모:** 이 출처만으로 특정 승인 버튼의 우회, 정확한 프롬프트, SQL, 자격 증명 설정을 입증할 수는 없다. 영구 데이터 유실이나 회사 전체 DB 삭제로 과장하지 않는다. ‘승인 우회가 확인된 사건’ 대신 **접근 대상과 실행 경계의 실패 사례**로 사용한다.

### 3-2. 별도 사고를 찾지 않아도 시험할 수 있는 실패 유형

아래는 실사건 목록이 아니라 공개 보안 지침과 워크플로 동작을 바탕으로 만든 **시험·설계 항목**이다.

| 실패 유형 | 문제 상황 | 필요한 설계 |
|---|---|---|
| 지침만 있고 차단은 없음 | ‘승인 후 발송’이라고 썼지만 메일 도구는 바로 호출 가능 | 도구·업무 API 실행 경계에서 승인 검사 |
| 승인 대상과 실행 내용 불일치 | 검토 뒤 수신자·첨부물·금액이 변경됨 | 중요 실행 내용 고정, 변경 시 새 승인 |
| 과도한 공통 계정 | 담당 고객만 처리할 에이전트가 전사 관리자 자격 증명 사용 | 요청 범위에 맞는 신원·최소 권한 |
| 이관을 승인으로 오인 | 상담원이 사건을 배정받았다는 이유로 환불 실행 | 배정·검토·승인 상태 구분 |
| 검토 알림의 과잉 | 사소한 조회부터 모두 승인 요청 | 영향·조건에 따른 분류와 검토량 관리 |
| 승인 없는 재개 | 외부가 `approved=true`를 넣어 실행 재개 | 승인 API에서 신원·현재 권한·대상 확인 |
| 재시도 중복 실행 | 응답을 못 받아 같은 주문을 새 요청으로 다시 실행 | 업무 식별자·멱등 처리·결과 대사 |
| 감독 설정을 스스로 해제 | 에이전트가 정책을 기록 전용으로 바꾸거나 제거 | 업무 실행 권한과 정책 관리 권한 분리 |

근거: [OWASP Excessive Agency][owasp-agency], [고영향 행동의 무결성][owasp-agent], [LangGraph 재개 동작][langgraph-interrupts], [AgentCore 강제 모드][agentcore-enforce].

## 4. 무엇을 자동으로 처리하고 무엇을 승인받을까?

### 4-1. ‘AI가 자신 있어 하는가’만으로 정하지 않는다

다음은 회사가 자사 업무별로 작성할 **분류 기준의 제안**이다.

- 영향: 돈, 고객 약속, 개인정보, 공식 기록, 실제 설비에 어떤 변화가 생기는가?
- 되돌릴 수 있는가: 기술적 복구뿐 아니라 이미 읽은 메일·외부 유출도 고려한다.
- 대상 범위: 한 건인가, 전체 고객인가? 반복 실행하면 누적 영향은 얼마인가?
- 기준 명확성: 문서화한 조건으로 검사할 수 있는가? 해석이 필요한 예외는 무엇인가?
- 권한과 책임: 요청자·승인자·실행 시스템이 각각 어디까지 맡는가?
- 확인 자료: 최신 정보와 원자료를 조회할 수 있는가?

금액·허용 대상 같은 강제 조건은 코드·정책으로 검사하고, 의미 판단이나 예외 해석은 평가한 AI와 사람의 업무로 나눈다. LLM이 스스로 제시한 확신도를 단독 통행증으로 삼지 않는다. Ramp는 숫자 확신도 대신 실행 가능한 결과 범주를 사용한다고 설명하며, AWS는 승인 등급 분류를 결정론적 로직으로 구현하도록 권고한다. [Ramp][ramp-engineering], [AWS][aws-risk]

### 4-2. 현업별 적용표 — 실제 기업 규정이 아닌 설계 예시

| 업무 | 자동화 검토 범위 | 사람 검토·승인 후보 | 실행 시스템이 확인할 것 |
|---|---|---|---|
| 고객 메일 | 자료 조회·초안·내부 저장 | 새로운 할인 약속·외부 발송 | 수신자, 본문, 첨부물, 발송 권한 |
| 환불 | 주문·반품 상태 조회, 환불안 작성, 제한된 정형 처리 | 정책 예외, 고액·반복 요청, 수취 정보 변경 | 주문·고객 일치, 누적 환불액, 승인 금액 |
| 구매·발주 | 견적 비교·발주 초안 | 예산 밖 구매, 신규 거래처, 조건 변경 | 공급사, 품목·수량, 예산, 발주 상태 |
| 인사 | 허용된 정책 안내·신청서 작성 | 조직·급여·접근 권한 변경 | 대상 직원, 데이터 권한, 기존 인사 결재 |
| IT 운영 | 제한된 진단·테스트 환경 작업 | 운영 배포, 대량 변경·삭제 | 환경, 자격 증명, 변경 범위, 복구 수단 |
| 제조 | 데이터 분석·조업안·시뮬레이션 | 실제 설비 설정 변경 | 설비 상태·안전 조건·현장 변경 절차 |

‘조회’도 민감정보를 대량으로 읽거나 외부로 전달하면 위험할 수 있다. 위 자동화 칸은 무조건 허용하자는 뜻이 아니라 **그 업무의 권한과 조건 안에서 검토할 범위**다.

## 5. 기술: 모델의 제안과 실제 실행 사이에 무엇을 두는가

### 5-1. 기본 구성

아래는 특정 제품의 구조도가 아니라 출처들을 종합한 **권장 구성 예시**다.

```text
요청자 → 에이전트: 자료 조회·작업 제안
                    ↓
          실행할 동작을 구체화해 저장
                    ↓
          정책·권한·현재 업무 상태 검사
          ├─ 금지/정보 부족 → 차단·추가 확인
          ├─ 자동 처리 가능 ───────────┐
          └─ 사람 승인 필요 → 승인 대기 │
                            ├─ 거절/만료 → 실행하지 않음
                            └─ 유효 승인 ┤
                                         ↓
                             실행 직전 최종 검사
                                         ↓
                            업무 API → 실제 결과 확인
                                         ↓
                          실행·승인·결과 이력 연결
```

핵심은 모든 중요한 실행 경로가 검사 지점을 지나야 한다는 것이다. MCP 도구 하나에만 승인을 붙이고 에이전트가 같은 DB를 직접 수정할 수 있으면 다른 길이 남는다. 모델이 `승인 완료`라고 출력한 문장을 승인 증명으로 사용하지 않는다. [OWASP 실행 통제][owasp-agency]

### 5-2. 실행 권한의 주체를 분리한다

도입 시 최소한 요청자, 에이전트, 승인자, 실제 시스템 접속 주체를 식별한다. 사용자 계정을 빌려 쓰는 모델과 회사가 별도로 관리하는 에이전트 계정은 운영 수명이 다르다.

Ramp의 현재 Identity 문서는 사용자 위임형과 별도 에이전트 신원을 구분한다. 별도 신원은 제한적 조기 접근 상태이며, 관리자가 권한을 지정하고 책임자를 둔다. 문서는 결재선에 에이전트를 넣는 것만으로 승인 권한이 생기는 것은 아니라고 명시한다. 이는 실제 고객의 도입 성과가 아닌 **제품의 신원 설계 사례**다. [Ramp Identity][ramp-identity]

설계 제안: 퇴사·부서 이동·권한 회수 시 연결 권한과 승인 대기 건을 어떻게 처리할지 정한다. 요청자가 자기 요청을 승인할 수 없는 업무라면 서버에서 직무 분리 조건을 검사한다.

### 5-3. 승인자가 본 내용과 실행할 내용을 맞춘다

승인 화면에는 실행 대상·금액·수신자 등 핵심 정보와 근거를 표시한다. 승인 이후 중요 데이터가 바뀌면 이전 승인으로 실행하지 않고 새 검토를 요청한다. OWASP는 서버 측 승인 검사, 순서가 고정된 상태 전이, 변경에 따른 승인 초기화, 실행 직전 확인을 거래 승인 원칙으로 제시한다. [OWASP 거래 승인][owasp-transaction]

**구현 제안:** 구조화한 실행 내용을 서버에 고정하고 승인 기록과 연결한다. 승인 화면과 실행기는 같은 기록을 읽는다. 해시를 쓴다면 금액·대상·본문·첨부물·도구 버전 등 효과를 바꾸는 필드가 포함되도록 정규화한다. 해시만 있다고 안전한 것은 아니다. 승인 서비스의 접근 권한과 기록 무결성도 필요하다.

```text
실행 제안:
  operation_id, tenant_id, requester_id, agent_id
  tool, target, normalized_parameters, payload_hash
  resource_version, policy_version

승인 기록:
  approval_id, operation_id, payload_hash
  approver_id, decision, approved_at, expires_at

실행 기록:
  operation_id, execution_state, downstream_receipt
  executed_at, reconciliation_state
```

위는 설명용 데이터 모델이며 플랫폼 공통 API나 바로 배포할 수 있는 코드가 아니다. 실제 자격 증명·토큰을 기록에 그대로 남기지 않는다.

### 5-4. 기다렸다 재개하는 문제와 한 번만 실행하는 문제를 나눈다

사람의 승인은 다음 날 올 수도 있다. 작업 상태·검토 자료·승인 요청을 영속 저장해야 프로세스가 재시작돼도 이어갈 수 있다. 그러나 체크포인트 저장은 외부 주문·메일이 중복되지 않는다는 보장이 아니다. [LangGraph Checkpointers][langgraph-checkpointers]

**구현 제안:** 같은 업무에는 재시도에도 동일한 `operation_id`를 쓰고, 실행기는 조건부 상태 변경으로 중복 실행자를 제어한다. 외부 시스템이 멱등 키를 지원하면 같은 키를 연결한다. 타임아웃으로 결과를 모를 때는 먼저 접수 여부를 확인한다. 이메일 발송처럼 외부 시스템이 중복 방지를 제공하지 않는 경우에는 발송 대기열·전달 영수증·재처리 정책을 별도로 설계한다.

승인 뒤 주문 상태·재고·한도가 바뀌는 문제에는 실행 시점의 버전 검사나 조건부 갱신도 필요하다. 승인을 받았다는 사실과 지금 실행해도 되는 상태인지는 별도 확인 대상이다.

## 6. 현재 사용 가능한 구현 수단과 차이

### 6-1. 제품·프레임워크 비교

| 수단 | 공식 문서에서 확인한 기능 | 조직이 추가로 구성·검증할 부분 |
|---|---|---|
| Bedrock Agents User confirmation | 지정한 동작의 함수·인자를 반환하고 확인·거절 결과로 실행 여부 결정 | 승인 UI, 회사 결재 권한, 만료·대결 절차 |
| Bedrock Agents Return control | 제안한 동작을 호출 애플리케이션에 돌려주고 앱이 실행 결과를 반환 | 검토·인자 수정·검증·실행 전체 연결. 제어권 반환 자체는 승인 아님 |
| AWS Step Functions Callback | Standard Workflow에서 외부 응답을 기다렸다 재개, 타임아웃·분기 구성 | 승인자 인증, 검토 화면, 알림·대체 담당자 |
| AgentCore Policy / Gateway | Gateway 경로에서 실행 정책 강제, temporal policy로 선행 이력 조건 검사 | 정책 내용, 승인 이벤트 신뢰성, Gateway 밖 경로 통제 |
| LangGraph Interrupt / Checkpointer | 검토 자료를 내보내고 상태 저장 후 재개 | 재개자의 권한, 승인 유효성, 중복 외부 실행 방지 |
| ServiceNow AI Agent | Supervised 도구의 실행 전 승인, 호출 ACL·실행 신원 설정 | 업무별 승인 조건, Run as 권한, 예외·기존 결재 연계 |

이는 구현 기능의 비교이며 이 표 전체가 각 회사에 이미 구축된 사례라는 뜻은 아니다. 근거: [Bedrock 예제][bedrock-example], [User confirmation][bedrock-confirmation], [Return control][bedrock-return], [Step Functions][step-functions], [AgentCore][agentcore-policy], [LangGraph][langgraph-interrupts], [ServiceNow][servicenow].

### 6-2. Bedrock: ‘확인받기’와 ‘앱이 실행을 맡기’

User confirmation에서는 호출 앱이 확인 대상 함수·인자를 사용자에게 제시하고 `CONFIRM` 또는 `DENY`를 반환한다. 회사 상급자의 결재가 아니라, 요청한 사용자에게 되묻는 상호작용으로 구성할 수도 있다. [공식 가이드][bedrock-confirmation]

Return control에서는 에이전트가 실행하려는 정보를 앱에 넘긴다. 앱은 자체 결재 시스템에 연결하거나 사용자가 인자를 수정하도록 할 수 있다. AWS의 2025-04-09 휴가 신청 예제는 이런 차이를 보여준다. 사람이 신청 내용을 바꿨다면 최종 API에서도 바뀐 내용의 조건을 다시 검사해야 한다. [구현 예제][bedrock-example], [제어권 반환][bedrock-return]

### 6-3. AgentCore: 정책을 기록만 하는지, 실제로 막는지

AgentCore Policy는 2026-03-03 일반 제공으로 발표됐다. Gateway를 거치는 요청에 정책을 적용한다. 운영 모드 중 `LOG_ONLY`는 평가 결과만 남기고 차단하지 않는다. 실제 강제는 `ENFORCE` 설정을 확인해야 한다. 정책을 제거하거나 모드를 바꿀 관리 권한도 통제 대상이다. [GA 발표][agentcore-ga], [강제 모드][agentcore-enforce]

**최신 기능:** AWS는 2026-08-06 temporal policies를 발표했다. 세션의 이전 동작을 참조해 선행 승인, 이전 출력과 현재 인자의 일치, 데이터 최신성을 조건으로 삼을 수 있다. 현재 가이드는 이를 위한 세션·이력 전달을 설명한다. [출시 발표][agentcore-temporal-launch], [기술 가이드][agentcore-temporal]

가이드에 명시된 temporal condition의 시간 범위는 최대 24시간이다. 며칠씩 걸리는 결재나 세션을 가로지르는 전사 누적 한도는 이 기능만으로 해결한다고 가정하지 말고, 별도의 영속 승인·업무 기록과 연결할 필요가 있다. [시간 조건][agentcore-temporal], [세션 처리][agentcore-session]

**구현 시 확인:** 정책 엔진이 승인 UI나 사람의 권한 판단까지 자동 제공하는 것은 아니다. 승인 이력을 공급하는 도구가 실제 승인 서비스를 조회해야 한다. 별도의 넓은 `permit`이 승인 조건을 우회하지 않는지도 시험한다. Cedar는 적용 가능한 허용 규칙 중 하나가 성립하고 금지 규칙이 없으면 허용하는 방식이므로, 독립된 `permit`을 추가했다고 조건들이 자동으로 AND 결합되지는 않는다. [Cedar 의미론][cedar]

### 6-4. LangGraph: 승인 대기 뒤 노드가 다시 실행될 수 있다

`interrupt()`는 검토 자료를 외부에 전달하고 멈춘다. checkpointer와 `thread_id`로 상태를 연결해 `Command(resume=...)`로 이어간다. 중요한 점은 재개할 때 중단한 노드의 처음부터 실행하므로 `interrupt()` 앞의 코드도 다시 실행된다는 것이다. [Interrupts][langgraph-interrupts]

예컨대 승인 요청 전에 송금을 실행하는 코드를 넣으면 경계가 잘못됐고, 재개 시 반복될 위험도 있다. 외부 변경은 승인 검사 이후로 분리하고 중복 실행 방지를 별도로 준비한다. 운영에서 메모리 저장만 쓰면 프로세스 종료 시 승인 대기 상태를 잃을 수 있으므로 영속 저장 구성을 확인한다. [Persistence][langgraph-persistence], [Checkpointers][langgraph-checkpointers]

### 6-5. ServiceNow: 호출할 수 있는 사람과 실행할 때의 권한

공식 문서는 Supervised 모드 도구가 실행 전에 사람 승인을 요구한다고 설명한다. 한편 에이전트 호출 권한과 실제 실행 신원은 따로 구성한다. Dynamic user 외에 별도의 AI user로 실행할 수 있으며, Role masking 적용 범위도 다르다. [ServiceNow 접근 제어][servicenow]

설계상 의미는 ‘누가 에이전트를 불렀는가’만으로 실제 데이터 접근 범위를 추정하지 말라는 것이다. 기존 업무 시스템의 ACL·역할·승인 워크플로를 그대로 확인해야 한다.

### 6-6. 국내 제품과 신규 표준은 어디까지 확인했는가

- **삼성SDS Brity Automation Agent:** 공식 제품 페이지는 업무 알림·진행 승인 등 사람이 개입하는 프로세스를 지원한다고 설명한다. 국내 구현 선택지로 소개할 수 있지만, 특정 고객의 승인 단계·성과까지 입증하는 자료는 아니다. [삼성SDS][samsung]
- **OWASP ACS:** 2026-09-01 공개 소개는 에이전트 프레임워크의 실행 지점에 정책을 적용하는 미들웨어 훅과 이식 가능한 통제를 설명한다. 초기 공개 표준 프로젝트라는 성격을 보존하고, 보편적 인증이나 국내 의무 규정처럼 쓰지 않는다. [ACS][acs]
- **NIST AI RMF:** 조직의 위험 관리 체계에 연결할 보조 자료다. 법률이 아니라 자발적 활용을 위한 체계이며, 국내 업종별 승인 의무를 대신 정해주는 자료가 아니다. 이번 글은 법규 해설보다 업무·시스템 설계에 집중한다. [NIST][nist]

## 7. 환불 한 건으로 설명하는 구현 예시

아래는 **집필용 가상 예시**다. 실제 고객사나 공급사의 기본 정책이 아니다. 금액 한도 자체보다 승인 대상과 실행 내용을 연결하는 데 목적이 있다.

가정: 회사가 정한 범위 밖의 환불은 고객지원 책임자의 승인을 받아야 한다. AI가 주문 R-204의 원결제 수단으로 12만 원을 환불하자는 안을 만들었다.

1. **제안:** 주문·반품 상태를 읽고 환불 사유와 금액을 구조화한다.
2. **정책 검사:** 자동 처리 조건을 벗어났으므로 실행하지 않고 승인 대기 상태로 저장한다.
3. **검토 화면:** 주문 R-204, 고객, 12만 원, 환불 사유, 결제 수단, 기존 환불 이력, 근거 정책을 보여준다. 추가 확인 사항도 표시한다.
4. **승인:** 서버가 책임자의 신원·현재 권한을 확인하고 해당 제안에 대한 결정을 저장한다.
5. **최종 확인:** 실제 실행 직전에 금액·대상·정책·주문 상태를 다시 확인한다. 15만 원으로 바뀌었다면 기존 승인으로 진행하지 않는다.
6. **실행:** 동일 업무 식별자와 외부 시스템의 중복 방지 기능을 이용해 환불 요청을 보낸다.
7. **확인:** 접수 결과와 지급 진행 상태를 기록한다. 통신이 끊겼다면 결과 불명으로 두고 기존 요청부터 조회한다.

승인자가 없을 때는 대체 담당자 또는 다음 처리 시간으로 넘긴다. 정한 시간 안에 승인을 못 받았다고 자동으로 허용하지 않는다. 고객에게는 확정 전 상태를 환불 완료로 안내하지 않는다.

**승인 화면에 필요한 것:** AI의 긴 설명문보다 누구에게 무엇이 바뀌는지, 얼마인지, 어느 근거를 봤는지, 무엇이 미확인인지 먼저 보여준다. 내부 사고과정을 그대로 저장해야 한다고 쓰지 않고 확인 가능한 자료·판단 설명·실행 내용·결정 기록을 남긴다.

## 8. 운영: 승인자가 제대로 판단할 수 있는가

### 8-1. 승인 피로를 줄이는 방법

AWS 가이드는 모든 동작을 사람에게 보내면 형식적인 승인으로 흐를 수 있다고 지적한다. 위험별 분류, 충분한 판단 자료, 시간 제한·이관 경로를 권고한다. [위험별 승인 설계][aws-risk]

**조직 적용 제안:**

- 일상 처리와 중요한 예외를 같은 알림으로 섞지 않는다.
- 승인 사유와 기존 상태 대비 변경점을 먼저 보여준다.
- 검토자에게 원자료 접근 권한과 처리 시간을 준다.
- 누구나 볼 수 있는 채팅방의 이모지 하나를 권한 검증 없이 결재로 취급하지 않는다.
- 업무량·분야에 맞게 대체 담당자를 배정한다.
- 보완 요청과 거절 사유를 다음 정책·평가 사례에 반영하되, 개별 예외를 무조건 전사 자동 승인 규칙으로 확대하지 않는다.

### 8-2. 볼 만한 운영 지표

| 지표 | 확인할 것 |
|---|---|
| 무승인·권한 외 실행 | 허용하지 않은 실제 변경이 발생했는가 |
| 승인 내용과 실행 결과의 불일치 | 금액·대상·수신자·옵션이 달라졌는가 |
| 자동 처리율과 사후 정정 | 범위를 넓힌 뒤 취소·재작업도 늘었는가 |
| 승인 대기시간 | 중앙값뿐 아니라 오래 묶인 건과 담당자별 적체 |
| 검토자의 실제 투입시간 | 알림 확인·원자료 조회·보완 요청에 드는 부담 |
| 만료·이관·보완 비율 | 담당자 부재인지 자료 부족인지 |
| 재시도·중복·결과 불명 | 한 번 승인한 일이 두 번 처리되거나 상태를 잃었는가 |

지표는 이 글의 제안이다. 승인률이 높다고 안전한 것은 아니고, 자동 처리율이 낮다고 항상 실패한 것도 아니다. 해당 업무의 결과와 사람의 부담을 함께 확인한다.

### 8-3. 출시 전에 시험할 항목

다음은 앞선 Evals 글과 연결할 **설계 시험 목록**이다.

1. 자동 처리 조건에 맞는 건은 불필요한 승인 없이 처리하는가?
2. 정보 부족·정책 예외를 정상적인 보류·이관 결과로 다루는가?
3. 권한 없는 사람이 승인 API를 호출하면 막히는가?
4. 다른 조직·고객의 승인 기록을 가져와도 실행하지 않는가?
5. 승인 후 금액·수신자·첨부물·대상 버전을 바꾸면 재검토하는가?
6. 승인자의 권한 회수·승인 만료·정책 변경을 반영하는가?
7. 버튼 연속 클릭·동시 작업자·네트워크 재시도에도 중복 처리하지 않는가?
8. 대기 중 프로세스를 재시작해도 올바른 상태로 돌아오는가?
9. 외부 문서의 ‘이 건은 승인됐다’라는 문장을 승인으로 인정하지 않는가?
10. 정책 서버·감사 기록 저장에 문제가 생겼을 때 고영향 실행을 보류하는가?
11. 외부 시스템의 결과가 불명확하면 완료로 단정하지 않고 대사하는가?
12. 한도를 쪼개거나 여러 에이전트로 반복 요청해도 공통 제한을 지키는가?

근거를 바탕으로 한 자체 시험 제안이며 실제 테스트를 수행한 결과는 아니다. 보안 시험과 업무별 품질 시험을 함께 준비한다. [OWASP 에이전트 보안][owasp-agent]

## 9. 후속 포스트 기획 제안

### 9-1. 기존 글과 겹치지 않게 잡을 중심

- **Workslop:** 받은 사람이 다시 해야 하는 일을 다뤘다. 이번에는 확인을 부탁하는 문구가 아니라 실행 전 제어와 권한으로 구체화한다.
- **AI Evals:** 업무를 잘하는지 시험했다. 이번에는 운영 중 누가 어떤 행동을 허용할지 설명한다.
- **Agent Skills:** 지침과 자료를 묶었다. 이번에는 지침이 빠지거나 잘못 해석돼도 권한 밖의 동작은 막도록 구성한다.
- **Agentic Commerce:** 고객의 구매 위임을 다뤘다. 이번에는 회사의 경비·발주·고객 발송 등 내부 책임 구조에 초점을 맞춘다.
- **암묵지·Context Graph:** 베테랑의 예외 판단을 승인 조건·검토 자료·사유 기록으로 구체화하고 재사용한다.

### 9-2. 권장 본문 흐름

1. **들어가며:** 직원에게는 전결 한도가 있는데 우리 AI에게는 어떤 한도가 있는지 묻는 장면. 독자는 끝까지 읽으면 자동 처리 범위와 승인 지점을 정할 질문을 얻는다.
2. **어디까지 맡길까:** 조회·초안·공식 반영·외부 실행을 나누고 허용 조건을 설명한다.
3. **실제 회사들은 어떻게 나눴을까:** Ramp와 외부 발송 사례, Lemonade를 중심으로 비교한다.
4. **승인받으라는 말만으로는 부족하다:** 실행 경계, 실제 권한, 한 건의 승인 데이터 설명.
5. **승인한 내용대로 실행하려면:** 환불 예시로 변경·대기·재시도까지 연결한다.
6. **사람이 제대로 판단하게 하려면:** 화면에 필요한 근거와 검토 역량, 시험 방법.
7. **나가며:** 자사의 업무 하나를 골라 승인 조건과 시스템 연결을 설계하는 과제로 마무리한다.

### 9-3. 영업 연결에 유용한 구체적 과제

엡실론델타의 지원 제안은 단순히 ‘AI 거버넌스를 도와준다’보다 다음 범위로 좁히는 편이 좋다.

- 현업과 자동 처리·승인·금지 조건을 정리하는 작업.
- 기존 ERP·CRM·그룹웨어의 권한과 결재 절차를 에이전트에 연결하는 작업.
- 승인 화면, 정책 강제, 대기·재개·중복 처리 방지를 구현하는 작업.
- 실제 예외로 시험하고 검토 부담을 측정하며 운영 범위를 조정하는 작업.

상담 출발 자료로 최근 승인·반려 사례, 현행 전결 규정, 업무 시스템 목록을 요청할 수 있다. 최종 글의 연락처는 `contact@epsilondelta.ai`를 사용한다. 이 절은 집필 방향이며 실제 제공 실적이나 고객 성과를 새로 주장하지 않는다.

## 10. 집필·팩트체크 메모

- 기업의 ‘사람 검토’ 설명만으로 승인 토큰·우회 방지·원자적 실행을 구현했다고 추정하지 않는다.
- 원문에서 확인하지 못한 내부 금액 한도·승인 직급은 가상 설계 예시에만 넣는다.
- 설명용 실패 상황과 실제 사고를 구분한다. Replit 사례는 공개한 복구 사실까지 유지한다.
- 고객 사례의 운영 사실, 제품 도움말의 기능, 작성자의 설계 제안을 같은 문장 안에서 섞지 않는다.
- Ramp 최신 문서는 자동 승인 설정과 평가 노출 설정이 다르다고 명시한다. ‘시험 모드이니 실행되지 않는다’고 추정하지 않는다.
- Ramp의 2025년 정책 에이전트 내부 성과와 2026년 외부 에이전트용 신원·도구 기능은 별개 자료다.
- AgentCore의 temporal policy는 2026-08 기능이다. 단일 호출만 검사하는 제품으로 소개하지 않는다. 세션 자동 생성 여부는 발표 블로그와 현재 개발 가이드 설명이 달라 실제 구현 시 [세션 가이드][agentcore-session]를 우선 확인한다.
- 제품의 초기 단계·제한적 공개·지원 범위는 후속 집필 시 다시 확인한다. 이 문서에서는 Ramp standalone identity를 제한적 조기 접근으로 표시했다.
- 국내 제품 지원은 확인했지만, 이름이 공개된 국내 고객의 구체적 결재 실행 절차까지 확보하지는 못했다. 해외 사례의 빈자리를 국내 도입 사례처럼 꾸미지 않는다.
- 기업 사고에 대한 부수적인 해명이나 연구상의 주의사항을 본문에 모두 넣지 않는다. **사실을 정확하게 쓰는 데 필요한 제한은 보존하고, 주제와 관계없는 방어 문장은 생략한다.**
