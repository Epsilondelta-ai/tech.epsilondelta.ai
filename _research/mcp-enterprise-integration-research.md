# AI는 똑똑한데, 왜 사내 시스템에는 사람이 대신 입력할까?

조사일: 2026-09-14 (KST)
대응 백로그: `ax-topic-backlog-100.md` 036번 — MCP는 사내 시스템 연결에서 무엇을 바꾸나?
대상: AI·AX에 관심 있는 경영진, 현업 책임자, CIO·CTO.
상태: 집필 전 조사 문서. 실제 도입 사례, 제품 기능, 데모, 편집용 가상 예시를 구분했다. 시스템 설치·연동 실험은 수행하지 않았다.

## 1. 이 포스트에서 답할 질문

AI가 고객의 요청을 이해하고 견적 문구까지 작성했는데, 왜 직원은 ERP에서 재고를 복사하고 CRM에 결과를 다시 입력해야 할까?

문제는 모델의 지능만으로 설명되지 않는다. 업무 자료에 접근할 통로, 사용할 수 있는 도구, 실행 권한, 실제 저장 결과를 확인하는 과정이 빠졌을 수 있다. MCP는 AI 애플리케이션과 도구·자료 제공 시스템 사이의 공통 접속 규약이다. 기존 업무 시스템의 기능을 AI가 사용할 수 있게 제공하는 데 활용한다. [S01][S02]

**편집상 핵심 결론:** MCP로 연결 방식을 공통화할 수 있다. 그다음에는 우리 회사에서 어떤 일을 어떤 조건으로 실행할지 도구와 업무 흐름으로 구현해야 한다. 설치 개수보다 사람이 다시 입력하지 않아도 끝나는 업무가 늘었는지를 봐야 한다.

이전 글과의 관계:

- Agent Skills: 일을 수행하는 지침과 자료를 묶는 방법을 다뤘다. 이번에는 그 일을 실행할 도구와 시스템 접속을 다룬다.
- AI 결재선: 실행 권한과 승인을 다뤘다. 이번에는 연결 구조 속 어느 위치에서 그 기준을 강제할지 설명한다.
- 미수금 회수 AX: 입금·청구서·고객 정보를 함께 확인해야 했다. 이번에는 그 정보를 조회하고 업무 시스템에 결과를 남기는 기술로 이어간다.
- 단독으로 읽어도 이해되도록 견적 업무 등 별도 장면으로 시작한다. 앞선 글을 읽어야 이해되는 연재형 강의로 만들 필요는 없다.

## 2. 개념: MCP, API, Tool, Skill은 각각 무엇인가?

| 개념 | 역할 | 견적 업무에 적용한 설명 |
|---|---|---|
| 모델 | 요청을 해석하고 다음 행동·답변을 생성 | 어떤 상품, 수량, 납기를 묻는지 파악 |
| 에이전트 애플리케이션 | 모델 호출·도구 실행·사용자 확인을 운영 | 재고를 조회하고 결과를 보고 견적 초안을 만드는 과정 진행 |
| API | 프로그램이 다른 시스템의 기능을 호출하는 접점 | ERP의 재고 조회, CRM의 기록 생성 |
| MCP | AI 애플리케이션과 서버 사이의 도구·자료 교환 방식 표준화 | 이용 가능한 재고 조회 도구의 설명과 입력 형식을 확인하고 호출 |
| Tool | 실제 수행 가능한 기능 하나 | `get_available_inventory`, `create_quote_draft` |
| Skill | 업무 지침·참고자료·스크립트 등의 재사용 묶음 | 거래처별 견적 작성 순서, 확인할 예외와 양식 |
| RAG | 필요한 근거를 검색해 생성에 활용하는 방식 | 제품 매뉴얼과 계약 조건을 찾아 견적 설명에 사용 |
| RPA / Computer Use | 화면 등 사용자 인터페이스를 조작하는 실행 방식 | API가 없는 구형 프로그램에 정해진 값을 입력 |

표의 견적 도구 이름은 설명을 위한 설계 예시다. MCP 표준에 견적 기능이 들어 있다는 뜻이 아니다.

### MCP는 API를 없애는가?

일반적인 구성에서는 MCP 서버가 기존 REST API나 사내 서비스, 데이터베이스 조회 계층 등을 호출한다. API는 업무 시스템의 기능을 제공하고, MCP는 이를 AI 클라이언트가 발견하고 호출할 수 있는 형태로 노출한다. 연결할 때마다 API 자체를 새로 만드는 일을 뜻하지 않는다. NetSuite 문서에서도 MCP 도구가 NetSuite API 호출·작업으로 이어지는 구조를 확인할 수 있다. [S10]

API와 모델의 도구 호출 기능을 직접 연결하는 방식도 가능하다. 기존에 잘 동작하는 고정 자동화에 반드시 MCP를 추가해야 하는 것은 아니다. **여러 에이전트·AI 애플리케이션이 같은 업무 기능을 재사용해야 할 때** 공통 규약의 가치가 커진다는 것이 이 글의 설계 관점이다.

### 비유 후보

‘공용 업무 창구’가 적합하다. 직원이 시스템마다 메뉴를 찾아 들어가는 대신 AI가 공통 형식으로 업무 기능을 요청한다. 다만 창구가 생겼다고 회사의 결재 규정이나 거래처 구분 기준까지 자동으로 생기지는 않는다.

‘AI의 USB-C’는 빠른 도입 설명에는 쓸 수 있지만, 꽂기만 하면 업무가 완성된다는 인상을 주기 쉽다. 본문에서는 도구 목록과 입력·결과를 실제 업무로 보여주는 편이 낫다.

## 3. 기술 구조: 어디에서 무슨 일이 일어나는가?

### 3.1 Host, Client, Server

- Host: 사용자가 이용하는 AI 애플리케이션. 모델과 대화, 도구 사용을 조정한다.
- Client: Host 내부에서 MCP 서버와 통신하는 구성 요소.
- Server: 도구·자료를 MCP로 제공하는 프로그램. 로컬 프로세스나 원격 서비스일 수 있다.

대표적인 서버 제공 기능은 실행 도구인 Tools, 참조 자료인 Resources, 재사용 템플릿인 Prompts다. MCP 자체가 모델의 판단이나 전체 업무 계획을 대신 수행하는 것은 아니다. 표준 통신은 JSON-RPC를 기반으로 하며 로컬 stdio와 원격 Streamable HTTP를 구분한다. [S01]

### 3.2 도구 발견과 실행

2025-11-25 Tools 명세에서는 `tools/list`로 목록을 조회하고 `tools/call`로 도구를 호출한다. 도구는 이름·설명·`inputSchema`를 제공하고 선택적으로 `outputSchema`를 제공할 수 있다. 결과는 텍스트 외에 `structuredContent` 같은 구조화된 형태로도 반환한다. [S02]

모델이 호출할 도구와 인자를 제안하면 Host·Client가 이를 실제 호출로 연결한다. 서버는 입력과 권한을 검사하고 업무 기능을 실행한다. ‘모델이 직접 ERP 데이터베이스를 수정한다’고 한 덩어리로 쓰면 책임 구분이 흐려진다.

### 3.3 버전 주의 — 집필 시 코드 예제보다 역할 설명 우선

조사일에 버전 없는 architecture URL은 `2026-07-28` 문서로 연결됐다. 해당 문서는 stateless discovery와 `server/discover` 등을 설명한다. 반면 널리 유통된 2025-11-25 자료와 구현에는 다른 수명주기 설명이 남아 있다. **서로 다른 버전의 초기화·발견 절차를 하나의 코드 예제로 섞지 않는다.** [S01][S02]

이번 글은 SDK 설치 강의가 아니므로 공통적인 ‘도구 확인 → 호출 → 결과 검증’을 중심으로 설명한다. 후속 구현 글에서 실제 Host·SDK·서버 버전을 고정하고 호환성을 검증할 것. 조사만으로 모든 제품이 최신 명세를 지원한다고 단정하지 않는다.

## 4. 업무용 도구 설계: API 수만큼 도구를 만들면 끝인가?

Anthropic의 2025-09-11 엔지니어링 글은 API를 그대로 감싼 도구를 늘리기보다, 중요한 업무에 맞는 적은 수의 명확한 도구를 만들 것을 권한다. 전체 연락처를 반환하기보다 필요한 연락처를 검색하게 하고, 반환 정보와 설명을 개선하며 실제 과제로 평가하는 방식이다. [S05]

다음은 이를 견적 업무에 적용한 **편집·설계 제안**이다.

| 설계 항목 | 권장할 구체적인 내용 |
|---|---|
| 이름·설명 | ‘재고’가 실물 재고인지 주문 가능한 재고인지 구분 |
| 입력 | 상품 코드, 창고, 수량 단위, 고객 ID의 의미를 명시 |
| 반환 | 수량과 단위, 창고, 조회 시각, 원천 시스템, 불확실한 항목 |
| 쓰기 범위 | 견적 초안 저장과 고객에게 견적 발송을 분리 |
| 권한 | 요청 사용자와 법인·거래처별 접근 범위를 서버에서 검사 |
| 오류 | 조회 실패와 재고 0을 서로 다른 상태로 반환 |
| 실행 결과 | 생성한 견적 ID, 저장 상태, 버전, 조회 가능한 링크 |

여러 API 호출을 업무 단위 도구 안에서 묶을 수 있지만, 조회와 환불처럼 위험이 크게 다른 작업까지 무조건 합치지는 않는다. 도구 경계는 호출 횟수뿐 아니라 검토·승인·복구 단위도 고려해 정한다.

### 자체 설계 예시: 견적 초안 도구의 계약

다음은 실제 제품 API나 실행 가능한 SDK 코드가 아닌 데이터 계약 예시다.

```json
{
  "tool": "create_quote_draft",
  "input": {
    "customer_id": "C-1042",
    "items": [{"sku": "P-210", "quantity": 20, "unit": "EA"}],
    "request_key": "quote-request-001"
  },
  "result": {
    "quote_id": "Q-2026-001",
    "status": "draft",
    "customer_notified": false,
    "requires_approval": true
  }
}
```

단가·세액은 권한 있는 업무 로직으로 계산한다. 호출자가 넣은 고객 ID는 인증된 사용자와 해당 고객의 관계를 서버가 확인해야 한다. `request_key`는 업무 계층의 중복 실행 방지용 예시이며 MCP의 JSON-RPC 요청 ID와 다르다. 위 JSON 필드만 선언한다고 중복 방지나 승인이 구현되는 것은 아니다.

## 5. 실제 운영 사례 — 블로그에서 우선할 근거

### 5.1 Block: 개발자 외 직원도 사내 자료와 업무 도구를 사용

**근거 성격:** 도입 기업의 담당자가 공개한 운영 회고. Goose 공식 글은 2025-04-21, 동일 저자의 DEV 재게시판은 2025-04-22다. 본문 링크는 공식 글을 우선한다. [S06]

- Block은 Goose에 승인한 MCP 서버를 기본 제공했다. 당시 사내 MCP 서버는 자체 엔지니어가 작성했다고 설명한다.
- Snowflake, GitHub·Jira, Slack·Google Drive, 내부 API를 연결했다.
- 데이터·운영팀은 내부 조회·보고서 작성·여러 자료의 맥락 수집에 활용했다. 지원·위험관리 등 개발 외 업무도 언급한다.
- OAuth와 OS 키체인 등을 사용했고, 당시 로컬 서버 인증 방식의 개선을 검토 중이었다.

**글에 쓸 초점:** 직원이 전문가에게 자료를 뽑아달라고 요청하거나 여러 시스템에서 직접 찾는 과정을 줄이려면, 조직이 승인한 연결과 사용 환경을 함께 제공해야 한다.

**수치 메모:** 원문에 수천 명의 일상 사용과 공통 과업 시간 50–75% 절약에 대한 직원 보고가 있다. 통제 실험이나 회사 전체 비용 절감률은 아니다. 본문은 수치보다 연결한 업무를 우선할 것. 이 사례가 ERP 수주 입력을 자동화했다는 근거는 아니다.

### 5.2 Atlassian: 조회를 넘어 업무 기록을 쓰는 운영 패턴

**근거 성격:** 2026-07-01 공급사의 실제 서비스 이용 집계. 개별 고객사 성공 사례와 구분한다. [S07]

- Rovo MCP Server를 통한 작업 항목 생성, 상태 변경, 결정 기록 등을 설명한다.
- 근무일 하루 500만 건 이상 도구 호출, 호출의 약 3분의 1이 쓰기라고 밝혔다.
- MCP 사용자 중 44%는 소프트웨어 팀 소속이 아니라고 설명한다.
- 기존 권한, 연결 가능한 클라이언트에 대한 관리자 통제, 감사 가시성을 함께 언급한다.

**글에 쓸 초점:** ‘답을 찾아주는 AI’에서 ‘업무 시스템에 결과를 남기는 AI’로 활용 범위가 넓어졌다는 운영 근거다. 회의·분석 결과를 사람이 다시 업무 항목으로 입력하던 일과 연결할 수 있다.

**수치 메모:** 호출 수는 완료한 업무 수가 아니다. 원문의 정확도·토큰 개선 수치는 Teamwork Graph 맥락 활용에 관한 것이므로 MCP 자체의 효과로 옮기지 않는다.

### 5.3 Dust: 회사 도구를 읽고 쓰는 에이전트 플랫폼

**근거 성격:** Anthropic/Claude의 고객 사례. 기존 검색 요약과 현재 페이지 내용이 달라, 실제 열어 확인한 본문을 기준으로 정리했다. [S08]

- Dust는 MCP 클라이언트로 외부 도구에 접근하고, 서버로 자사 에이전트와 맥락을 다른 시스템에 제공한다고 설명한다.
- 업무 예시로 CRM 레코드 갱신, 이슈 생성, 데이터베이스 조회를 들고 있다.
- 권한을 반영한 검색, 역할 기반 접근, 감사 기록도 플랫폼 구성에 포함한다.

**글에 쓸 초점:** 정보를 읽는 기능과 실행 기능을 같은 업무 환경으로 연결하는 구조. 개별 고객의 CRM 입력 시간 절감률은 이 자료에서 확인하지 못했다.

**수치 메모:** 해당 페이지의 하루 약 1만 달러 모델 비용 절감은 프롬프트 캐싱 개선에 관한 결과다. MCP가 이 비용을 절약했다고 쓰지 않는다. 이번 글에서는 제외해도 된다.

## 6. 제품·기술 사례 — 실적과 구분해 설명할 소재

### 6.1 Dust의 Salesforce 쓰기 도구

2026-03-31 변경 이력은 Salesforce 도구가 읽기를 넘어 레코드 생성·갱신을 지원한다고 설명한다. 관리자가 도구를 활성화하고 쓰기 실행 전에 사용자의 승인을 받는 방식이다. 기존에는 조회 후 사람이 갱신해야 했다는 설명이 이번 제목과 직접 맞는다. [S09]

영업 통화 후 기회 단계 변경, 연락처 보완, 활동 기록은 **제품이 제시한 활용 예시**다. 특정 기업의 달성 실적으로 쓰지 않는다. 해당 변경 이력은 검색 도구가 반환한 본문으로 확인했으며 직접 open은 오류가 났다. 집필 시 링크 재확인 권장.

### 6.2 NetSuite: 대화에서 ERP 레코드 생성·갱신까지

공식 MCP Standard Tools SuiteApp 문서는 보고서·저장 검색·SuiteQL 조회 외에 REST Web Services를 통한 레코드 생성·갱신을 명시한다. 연결한 NetSuite 역할의 권한을 적용하고, 별도 역할로 AI에서 허용할 작업을 좁힐 수 있다고 안내한다. [S10]

**활용:** ‘MCP가 API를 대체한다’가 아니라 MCP 도구가 기존 ERP 작업으로 이어진다는 설명에 적합하다. 기능 설치 전 역할을 검토하라는 경고도 중요하다. 사람 계정이 이미 넓은 쓰기 권한을 갖고 있다면 AI 연결에 그 범위를 그대로 허용할지 판단해야 한다.

특정 제조·유통사가 이를 도입해 수주 처리 시간을 얼마 줄였다는 실적은 이번 조사에서 확보하지 못했다.

### 6.3 Salesforce: 기존 Flow·업무 로직을 도구로 제공

공식 2026년 5월 기술 글은 Claude와 Hosted MCP Server를 연결하는 과정을 설명한다. 리조트 예약 관리 장면과 사용자 정의 작업을 예시로 들며, 운영 환경에서는 대량 취소를 처리하는 전용 Flow를 고려하도록 한다. [S11]

이것은 **가상 업무를 사용한 공식 구현 예제**다. 실제 호텔 운영 실적이 아니다. 글에서는 ‘이미 있는 업무 로직을 AI가 호출할 수 있도록 제공한다’는 기술 설명에만 사용한다.

### 6.4 Oracle Integration: 기존 연동 자산 재사용

2026-02-28 발표는 기존 integration·automation을 MCP 서버로 노출하는 기능을 설명한다. 이미 구성한 업무 연동을 AI 도구로 재사용하는 방향을 보여준다. ‘한 번 클릭’은 기존 연결·업무 로직·권한 구성이 갖춰진 제품 맥락의 설명이지, 사내 시스템 통합 전체가 한 번에 끝난다는 뜻이 아니다. [S12]

2026-09-10 별도 Gateway 발표는 중앙 신원·정책·자격증명·관측 기능을 다루지만, Oracle Integration 26.10 릴리스에 제공할 예정이라고 적는다. **이번 조사 시점에 이미 전면 운영 중인 기능으로 쓰지 않는다.** [S13]

### 6.5 제외 또는 보조할 사례

- Dust의 Glittery Helmet 고객지원 예제는 가상 보안회사 데모다. 고객 조회 → 관련 지식 검색 → 티켓 생성의 교육 예시로는 유용하나 현장 실적이 아니다. [S14]
- 국내 제조·유통기업의 이름, MCP 사용, 쓰기 업무, 성과가 한 자료에서 확인되는 사례는 이번 조사에서 확보하지 못했다. 일반 AI 도입 사례에 MCP를 임의로 붙이지 않는다.
- 사례 본문 우선순위: Block → Atlassian 운영 패턴. NetSuite·Dust Salesforce는 ‘어떻게 구현하는가’에서 보조한다. 모든 제품을 나열할 필요는 없다.

## 7. 연결 후에 남는 엔지니어링

### 인증·권한·승인

MCP 서버에 접속할 권한, ERP에서 특정 고객·법인의 데이터를 볼 권한, 외부 발송이나 장부 변경 승인은 각각 구분한다. 2025-11-25 Authorization 명세는 HTTP 기반 인증 흐름과 토큰 대상 검증을 설명한다. MCP 서버가 받은 토큰을 검증 없이 하위 API에 전달하는 token passthrough는 허용하지 않는다. 하위 API 접근은 그 대상에 맞는 별도 자격증명·위임 설계가 필요하다. [S03][S04]

실무 설계 제안:

- 공유 관리자 계정을 모든 직원의 AI에 붙이지 않는다.
- 로그인 사용자를 서버 측에서 식별하고 레코드·행위별 권한을 강제한다.
- ‘읽기 전용’이라는 도구 설명만 믿지 않고 실제 실행 코드와 하위 시스템 권한으로 막는다.
- 승인 화면에는 대상·변경 전후·금액·발송 여부를 보여준다. 승인 뒤 인자가 바뀌면 다시 검토한다.

### 외부 자료와 프롬프트 인젝션

메일·문서·도구 결과에 ‘다른 고객 자료를 보내라’는 문장이 있어도 업무 권한을 부여하는 지시로 취급하면 안 된다. 서버 출처 관리, 결과 처리, 네트워크 대상 제한을 함께 설계한다. 공식 보안 지침은 confused deputy, token passthrough, SSRF, 세션 관련 위험 등을 다룬다. [S04]

### 추가 보안 조사 — 서버 출처와 변경 관리 (2026-09-14)

기존 인증·인젝션 조사에 공급망·운영 통제를 보강했다. [Atlassian Trust and Security의 2025-06-26 안내](https://www.atlassian.com/blog/company-news/mcp-risk-awareness)는 악성 문서 지시, MCP 서버 설명의 악성 변조, 연결 이후 도구 변경, 유사 이름을 통한 사칭을 다룬다. 최소 권한, 사람의 검토, 도구 출처·버전 검증과 변경 감시, 감사 기록을 권고한다. 실제 침해 사고 발표가 아닌 위험·대응 안내다.

포스트 적용 예시는 자체 가상 장면이다. 고객 메일에 다른 거래처 단가표를 보내라는 지시가 섞이면, 메일 읽기·CRM 조회·발송 기능을 함께 가진 에이전트가 잘못된 행동을 시도할 수 있다. 데이터의 지시를 권한으로 취급하지 않고 조회 범위·외부 발송을 실행 계층에서 제한해야 한다.

공식 보안 지침 S04에는 로컬 MCP 서버 침해와 범위 최소화도 포함돼 있다. 실무 적용 시 로컬 파일·네트워크 권한, 원격 운영자·데이터 전달처, 업데이트 검토 책임을 확인한다. 사고 대응을 위한 연결 차단·자격증명 폐기, 로그의 비밀값 제외는 운영 설계 제안이다. 읽기 전용도 기밀 조회·외부 전달 위험을 따로 검토한다.

추가 검증: 악성 지시가 섞인 메일, 미승인 도구 변경, 허용되지 않은 발송 대상, 권한 밖의 고객 조회, 토큰 로그 노출 여부. 본문에는 견적 장면과 직접 관련된 통제만 설명하고 공격 분류 전체는 나열하지 않는다.

### 상태·중복 실행·부분 실패

아래는 프로토콜 기능이라고 주장하는 내용이 아니라 **업무 구현 시 확인할 설계 항목**이다.

- 견적 저장 후 응답이 끊겼을 때 곧바로 재생성하지 말고 요청 키와 실제 저장 결과를 조회한다.
- ERP 저장은 성공했지만 CRM 기록은 실패했다면 두 결과를 따로 남기고 미완료 단계만 복구한다.
- 재고·가격·승인이 실행 전 바뀔 수 있으므로 버전 또는 갱신 시각을 확인한다.
- ‘조회 실패’를 ‘재고 없음’으로 바꾸지 않는다. 도구 오류와 업무 데이터의 빈 결과를 구분한다.
- 최종 안내는 모델의 자신감이 아니라 실제 시스템의 견적 ID·상태를 근거로 작성한다.

MCP Tools 명세는 프로토콜 오류와 `isError: true`인 도구 실행 오류를 구분한다. 도구가 오류 내용을 제공하는 것과 재실행이 안전한 것은 다른 문제다. [S02]

## 8. API 없는 프로그램, MCP를 쓰지 않아도 되는 업무

**설계 선택:** 기존 API·공식 커넥터가 있으면 먼저 적합성을 확인한다. 없는 경우에는 승인된 파일 교환, 사내 서비스 계층, RPA·화면 조작 등 다른 실행 통로가 필요하다. 그 기능을 MCP로 노출할 수는 있지만, MCP 서버를 설치한다고 구형 프로그램에 API가 생기지는 않는다.

| 상황 | 검토할 방향 |
|---|---|
| 같은 입력으로 정해진 처리를 반복 | 기존 배치·워크플로·API 자동화로 충분한지 확인 |
| 여러 AI 애플리케이션이 같은 기능을 사용 | MCP로 공통 접점 제공 검토 |
| 문서 검색과 답변만 필요 | 검색 품질·권한·최신성부터 확인 |
| 화면 외에 연결 통로가 없음 | UI 자동화의 안정성·로그인·복구 비용 확인 |
| 기존 iPaaS·업무 Flow가 있음 | 검증된 흐름을 도구로 재사용할 수 있는지 확인 |

## 9. 블로그용 가상 예시: 견적 초안에서 실제 기록까지

실제 고객 사례가 아닌 자체 기획 장면이다.

1. 고객이 제품 P-210을 20개 구매할 수 있는지 문의한다.
2. 기존 방식: AI가 답변을 작성하지만 직원이 고객 코드를 찾고 ERP 재고를 복사하고 가격을 계산한 뒤 CRM에 견적을 입력한다.
3. 연결 후: 고객 조회 도구로 거래처를 식별하고 재고 도구로 주문 가능한 수량·창고·조회 시각을 가져온다.
4. 가격·세액은 회사 업무 로직으로 계산한다. 거래처 할인과 납기 확약 권한을 확인한다.
5. AI가 견적 초안을 만들고 담당자가 필요한 항목을 검토한다.
6. 승인 조건에 맞춰 초안을 저장한다. 견적 ID와 저장 상태를 확인하고 CRM 기록을 연결한다.
7. 고객 발송은 별도 조건으로 실행한다. 중간 실패 시 무엇이 저장됐는지 먼저 확인한다.

**전달할 차이:** 사람이 복사·입력하던 과정을 도구 호출로 옮기되, 확인해야 할 판단까지 사라진다고 쓰지 않는다. AI가 만든 견적 문장과 ERP에 실제 저장한 견적은 다른 산출물이다.

## 10. 도입 순서와 성과 확인

다음은 앞선 자료를 종합한 자체 도입 제안이다.

1. 시스템 목록 대신 반복 업무 하나를 고른다. 누가 어느 화면에서 무엇을 복사하는지 기록한다.
2. 공식 커넥터·API·기존 연동과 필요한 권한을 확인한다.
3. 조회 기능부터 실제 고객·상품 ID와 단위가 맞는지 검증한다.
4. 쓰기는 테스트 환경의 초안 생성부터 시작한다. 운영 자료에 바로 쓰지 않는다.
5. 승인·실행 결과·부분 실패 복구를 붙인다.
6. 현업 검증 사례를 통과한 범위부터 확장한다. 도구 변경과 권한 변경 때 다시 시험한다.

### 검증 문제 후보

| 문제 | 기대할 동작 |
|---|---|
