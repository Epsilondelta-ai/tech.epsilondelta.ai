- 범위: 장애·재배포·장시간 대기에도 업무 진행을 보존하는 구조, 외부 시스템 실행 안전성, 실제 산업 적용.

## 1. 핵심 결론

**Durable Execution은 실행 상태와 단계별 결과를 영속적으로 남겨, 장애나 장시간 대기 뒤에도 업무를 복구·재개할 수 있도록 하는 실행 방식이다.** 프로세스 하나가 계속 살아 있어야만 작업이 이어지는 구조에서 벗어나도록 돕는다. Temporal과 Azure Durable Task는 실행 이력을 이용한 복원 방식을 설명한다. [S1][S2]

경영진에게는 ‘AI가 답을 잘 만드는가’에 더해 **‘내일도 이 업무가 어디까지 진행됐는지 알고 이어갈 수 있는가’**라는 질문으로 접근하면 좋다.

반드시 함께 설명할 경계가 있다. **실행 이력 복구와 외부 시스템의 중복 처리 방지는 별개의 설계 과제다.** 결제나 발주는 외부에서 성공했지만 성공 응답을 기록하기 전에 연결이 끊길 수 있다. 이 경우 안전한 재시도에는 외부 시스템의 멱등성 지원이나 거래 결과 대조가 필요하다. [S3][S4]

이 글은 Temporal 제품 소개로 한정하지 않는다. 실행 보존이라는 문제를 먼저 설명하고, Temporal·Azure·LangGraph를 구현 관점의 비교 대상으로 사용한다.

## 2. 기존 글과 이어지는 질문

| 앞선 주제 | 다뤘던 질문 | 이번 글의 질문 |
|---|---|---|
| 에이전트 메모리 | 이전 경험과 선호를 다음 작업에 어떻게 활용할까? | 지금 진행 중인 업무를 장애 뒤에 어떻게 이어갈까? |
| AI 결재선 | 어디까지 맡기고 언제 승인받을까? | 승인자가 다음 날 응답해도 올바른 업무를 재개할까? |
| MCP | 사내 시스템에 어떻게 연결할까? | 연결이 끊겼을 때 이미 실행한 일과 남은 일을 어떻게 구분할까? |
| 프로세스 마이닝 | 실제 업무가 어디서 지연되고 반복되는가? | 중단된 업무를 사람이 처음부터 재처리하지 않게 하려면? |

메모리와 실행 상태가 완전히 분리된 제품이라는 뜻은 아니다. LangGraph처럼 thread의 체크포인트를 대화 연속성과 장애 복구에 함께 쓰기도 한다. 이번 글에서는 기능의 목적을 구분한다. [S5]

## 3. 혼동하기 쉬운 개념

| 개념 | 맡는 역할 | 단독으로 해결하지 않는 문제 |
|---|---|---|
| 재시도 | 실패한 호출을 다시 시도 | 어떤 단계까지 끝났는지, 중복 발주 여부 |
| 메시지 큐 | 작업 전달·버퍼링·소비 | 여러 단계 전체의 상태·보상·사람 승인 정책 |
| 상태 머신 | 상태와 전이 규칙 표현 | 저장·원자적 전이·중복 이벤트 처리는 별도 구현 필요 |
| 체크포인트 | 정한 경계의 실행 상태 저장 | 경계 안의 외부 작업이 이미 성공했는지 여부 |
| 이벤트 소싱 | 사건 이력으로 상태 재구성 | 모든 제품의 저장·재생 방식이 같다는 보장 |
| Durable Execution | 실행의 영속화와 복구·재개를 구성 | 업무 판단의 정확성, 모든 외부 부작용의 자동 중복 방지 |
| 멱등성 | 같은 논리 작업의 반복 요청이 효과를 중복 생성하지 않도록 설계 | 여러 다른 업무의 전체 순서·대기 관리 |
| 보상 처리 | 앞서 수행한 업무의 효과를 후속 업무로 상쇄 | 이미 발송한 메일이나 배송을 물리적으로 없던 일로 만들기 |

비교표는 공식 문서들을 바탕으로 한 설계 관점의 정리다. 큐·DB·상태 머신으로 직접 구축할 수도 있다. 전용 엔진을 쓰는 이유는 이 조합의 복구·대기·이력 관리 부담을 공통 기반으로 옮기기 위해서다. [S1][S2][S3][S6]

## 4. 복구 원리: 코드를 다시 따라가도 업무를 전부 다시 하지는 않는다

### 4.1 Workflow와 Activity

Temporal의 대표적인 구성에서는 Workflow가 순서·분기·대기를 관리하고 Activity가 외부 API, 문서 추출, LLM 호출 같은 실제 작업을 수행한다. 같은 이력으로 복원할 때 Workflow가 같은 명령 순서를 만들도록 결정성을 지켜야 한다. LLM의 답이 매번 같아야 한다는 뜻은 아니며, 비결정적인 호출을 Activity 경계로 분리한다. [S7]

### 4.2 실행 이력과 replay

설명용 흐름:

1. 거래처 조회를 실행하고 결과를 기록한다.
2. AI가 만든 발주 초안의 결과를 기록한다.
3. 사람의 승인 요청과 대기 상태를 남긴다.
4. Worker가 종료되거나 새 버전으로 교체된다.
5. 저장한 이력을 사용해 실행 상태를 복원한다.
6. 승인 결과가 도착하면 검증 후 다음 작업을 진행한다.

이력 기반 엔진에서는 Workflow 코드가 처음부터 재생될 수 있지만, **완료 결과가 기록된 작업은 그 결과를 재사용**한다. ‘복구할 때 모든 외부 호출을 다시 실행한다’와 다르다. 메모리의 CPU 명령 위치를 그대로 저장했다가 이어 붙이는 방식으로 설명하지 않는다. [S1][S2]

### 4.3 재실행할 수 있는 구간은 여전히 존재한다

Activity 하나에 조회·결제·메일 발송을 한꺼번에 넣으면 마지막 단계 실패로 앞 단계까지 다시 실행할 위험이 커진다. 반대로 너무 잘게 나누면 이력과 운영 부담이 늘어난다. 외부 효과와 실패·재시도 단위를 보고 경계를 정한다. 완료 보고가 남지 않은 Activity는 다시 시도될 수 있다. [S3]

이는 기술적인 각주가 아니라 발주·환불 업무에서 직접 비용이 발생하는 지점이므로 본문에 쉬운 사례로 넣는 것이 좋다.

## 5. ‘다시 해보세요’가 위험해지는 순간

### 5.1 발주 성공 여부를 모르는 상황 — 가상 예시

| 시점 | 실제 상황 | 에이전트 시스템이 아는 것 |
|---|---|---|
| 1 | 발주 API 요청 전송 | 요청을 보냈음 |
| 2 | ERP가 발주를 생성 | 아직 성공 응답을 못 받음 |
| 3 | 네트워크 끊김 | 타임아웃 발생 |
| 4 | 같은 요청 재시도 | 새 발주인지 기존 발주 재시도인지 구분 필요 |

‘타임아웃=발주 실패’라고 처리하면 중복 발주가 생길 수 있다. 설계 시 안정적인 업무 키를 함께 보내고, 외부 시스템이 같은 키를 동일 작업으로 처리하도록 구성한다. 지원하지 않는 레거시 시스템은 거래 조회·대조, 중복 검사, 수동 확인 경로 등을 검토한다. 단순히 요청 전에 DB를 조회하는 것만으로 동시 요청까지 안전해지는 것은 아니다. [S3][S4]

### 5.2 멱등 키의 범위

다음은 적용 설계 제안이다.

- 예: `발주요청번호 + 승인된 문서버전 + 실행종류`를 논리 작업의 식별 기준으로 정한다.
- 같은 작업의 재시도에서는 같은 키를 유지한다. 새 시도마다 임의 UUID를 만들면 중복을 식별하지 못한다.
- 사용자가 실제로 새 주문을 의도했다면 별도 업무 키가 필요하다.
- 엔진의 실행 ID와 회사의 업무 ID를 연결한다. 재시작·새 실행·이력 분할 때도 같은 업무를 잘못 새 작업으로 취급하지 않도록 한다.
- 저장소의 고유 제약과 원자적 처리, 외부 API의 계약을 함께 확인한다. 로컬 완료 기록과 원격 효과 사이에는 실패 구간이 남을 수 있다.

Stripe의 공식 API는 같은 멱등 키로 최초 요청의 결과를 재사용하며, 키 보존·파라미터 검증 조건을 설명한다. 이는 중복 방지 인터페이스의 실제 예시이지 모든 ERP·메일 API가 같은 기능을 제공한다는 뜻은 아니다. [S4]

## 6. 내일 승인해도 이어지는 업무

### 6.1 대기 자체를 상태로 관리

사람의 승인을 기다리는 동안 LLM을 계속 호출하거나 Worker의 메모리에만 상태를 들고 있을 필요는 없다. 상태를 저장하고 외부 이벤트나 durable timer에 따라 다시 진행하도록 구성한다. Temporal에는 Signal·Update·Query가 있고, Azure도 외부 이벤트와 타이머를 사용하는 장기 오케스트레이션을 제공한다. [S2][S8]

### 6.2 승인과 재개를 연결할 때 필요한 항목 — 설계 제안

- 승인 대상 업무 ID와 문서·주문 버전.
- 승인자의 신원·권한과 승인 시각.
- 승인 또는 거절, 유효기간, 필요한 의견.
- 같은 승인 이벤트의 중복 수신 방지.
- 승인 후 실행 전 대상 내용이 바뀌었는지 확인.
- 기한 만료·취소·담당자 부재 시 인계할 사람.

복구된 이전 승인이 변경된 금액의 발주까지 허용하면 안 된다. Durable Execution은 승인을 기다리고 복구하는 기반을 제공하고, 무엇을 승인한 것으로 볼지는 업무 규칙으로 정한다.

## 7. 재시도·중단·보상·버전 변경

### 7.1 실패 유형을 나누기

Temporal의 Retry Policy에는 간격·증가 계수·최대 시도·재시도하지 않을 오류 등을 구성할 수 있다. 이를 업무의 시간 제한과 연결해야 한다. [S9]

| 실패·대기 | 처리 방향 — 설계 예시 |
|---|---|
| 일시적 네트워크 오류·호출 제한 | 간격을 두고 재시도, 총시간·비용 한도 설정 |
| 잘못된 입력·설정 | 원인 수정 또는 담당자 인계 |
| 승인 거절 | 같은 실행을 무한 재시도하지 않고 거절 경로로 종료 |
| 오래 걸리는 정상 처리 | 적절한 타임아웃과 진행 신호, 외부 상태 확인 |
| 외부 실행 성공 여부 불명 | 업무 키로 대조하고 중복 생성 방지 |
| 일부 단계만 완료 후 취소 | 완료한 단계에 맞는 보상·후속 처리 |

### 7.2 보상은 업무로 수행하는 취소·정정

재고를 예약한 뒤 결제가 실패했다면 예약 해제, 이미 결제했다면 환불처럼 앞 단계의 효과를 상쇄할 작업을 정한다. 모든 단계를 단일 DB 트랜잭션처럼 되돌릴 수는 없다. 보상 자체도 실패할 수 있어 이력·재시도·사람 인계가 필요하다. Microsoft의 보상 트랜잭션 패턴을 참고할 수 있다. [S6]

### 7.3 진행 중인 업무가 있는데 코드를 바꾼다면

장기 업무는 과거 이력과 새 코드가 충돌할 수 있다. Temporal은 Worker Versioning과 패칭 같은 방법을 제공한다. 배포 시 기존 실행을 어느 버전으로 마칠지, 새 실행부터 어떤 버전을 적용할지 정하고 기존 이력으로 replay 검증을 하는 구성을 검토한다. [S7][S10]

모델·프롬프트·도구 스키마도 변경 대상이다. 다음 단계에서 새 정책을 적용할지, 승인 당시 조건을 유지할지 기록해야 한다. 이 부분은 AI 운영 설계 제안이다.

## 8. 구현 선택지 비교

| 선택지 | 공식 자료에서 확인한 구성 | 검토할 업무 |
|---|---|---|
| Temporal | Workflow·Activity, 실행 이력, replay, 재시도, 메시지 전달, 버전 관리 | 여러 시스템·사람·장기 대기를 잇는 업무 |
| Azure Durable Functions / Durable Task | 이력 기반 오케스트레이션, 타이머·이벤트, 영속 저장소 | Azure 환경의 장기·서버리스 업무 흐름 |
| LangGraph | thread 체크포인터, 중단·재개, 장기 store | 에이전트 그래프의 상태와 사람 개입 |

이는 우열표가 아니라 구성 비교다. 운영 기반·지원 언어·팀 역량·기존 시스템·저장 정책과 함께 선택한다. [S1][S2][S5][S11]

LangGraph의 메모리 저장 체크포인터는 프로세스 재시작 후 상태를 보존하지 않는다. 운영에서는 영속 저장 체크포인터를 선택해야 한다. 또 interrupt 후에는 해당 노드의 처음부터 코드가 다시 실행되므로, 그 앞의 외부 변경 작업이 중복될 수 있는지 확인한다. [S5][S11]

모든 제품에 Temporal의 결정성 제약이나 같은 replay 경계를 그대로 적용해 설명하지 않는다. 현재 문서에서 실제 저장·재개 단위를 확인한다.

- **업무:** 보험 운영 AI. 이메일 접수 후 누락 문서를 요청하고, 며칠 뒤 PDF를 받아 추출·보험 시스템 확인·사람의 판단·회신을 잇는다.
- **구현:** 조정은 Workflow, 추출·API·발송은 Activity로 분리. 첨부 처리와 AI 추론을 Child Workflow로 나누고, 동일 고객 문맥이 겹치는 요청의 추론을 직렬화했다.
- **운영 설명:** 일부 첨부 실패 때문에 성공한 다른 추출을 전부 잃지 않도록 구성. 고객·사람 응답을 기다리는 동안 배포·Worker 재시작이 있어도 이력으로 재개한다고 설명한다.
- **글에서 맡길 역할:** ‘고객이 내일 답해도 업무를 이어가는 AI’의 중심 사례.
- **검증 메모:** 공개된 기술 설계와 운영 경험이다. 처리시간 절감률이나 전체 보험사의 도입 범위를 새로 추정하지 않는다. [C1]

### 9.2 Mews — 호텔 결제 관련 업무를 장애 뒤 복구

- **발행:** 2026-06-04.
- **업무:** 숙박 플랫폼의 청구 마감, 결제 webhook, 부분 환불, 분쟁·온보딩.
- **구현:** 청구 마감을 별도 Workflow로 분리하고 외부 이벤트로 장기 업무 상태를 갱신한다. 패칭과 replay 테스트도 사용했다.
- **공개 운영 규모:** 하루 약 6,000건의 bill closing을 Temporal로 처리한다고 설명한다.
- **장애 경험:** Kafka 장애로 멈춘 수천 개 Workflow가 Kafka 복구 후 재개됐고 수동 정리가 필요하지 않았다고 공개한다.
- **글에서 맡길 역할:** 장애 후 직원이 업무 건을 찾아 복구하는 부담을 줄이는 사례.
- **검증 메모:** 6,000은 결제 총건수나 신규 성과 증가분이 아니라 청구 마감 처리량이다. 이 사례의 결제 복구를 생성형 AI 성과로 바꾸지 않는다. [C2]

### 9.3 SMILe — 배송 예약부터 외부 파트너 응답까지

- **발행:** 2026-06-17.
- **업무:** 지역 서비스 가능 여부, 파트너·차량 가용성, SLA·비용 조건에 따라 배송 경로를 선택한다.
- **구현:** 예약별 Workflow가 내부 서비스·외부 파트너 API·추적 시스템을 연결한다. 외부 연동은 Activity, 파트너 상태 변경과 확인은 Signal·이벤트로 처리한다. Self-hosted 운영 사례다.
- **공개 결과:** 예약별 진행 추적과 재시도·상태 유지, 복구 코드 부담 감소를 정성적으로 설명한다.
- **글에서 맡길 역할:** 도구 호출 하나가 아니라 여러 회사·시스템의 응답을 기다리는 업무의 신뢰성.
- **검증 메모:** 정량 절감률 미제시. 생성형 AI 도입 사례로 단정하지 않는다. [C3]

### 9.4 Replit — 코딩 에이전트의 실행을 감독하는 제어 계층

- **발행:** 2025-09-15.
- **문제:** 에이전트와 실행 컨테이너의 상태 추적, 세션당 에이전트 프로세스 관리, 도구·모델 제공자 오류와 에이전트 중단 대응.
- **도입:** Replit Agent의 제어 계층 오케스트레이션에 Temporal을 적용했다.
- **글에서 맡길 역할:** AI 추론 능력과 별개로 장시간 실행을 감독·복구할 기반이 필요하다는 사례.
- **검증 메모:** 제품·사용자·매출 성장 전체를 Durable Execution의 단독 효과로 계산하지 않는다. 일반 사무 업무 독자에게는 보조 사례로 활용한다. [C4]

## 10. 우리 회사에 적용할 가상 업무 시나리오

다음은 실제 엡실론델타 고객 실적이 아닌 설계 예시다.

### 구매·발주

요청 접수→거래처·재고 조회→AI 초안→금액별 승인→승인 대상 버전 확인→발주 API→접수 결과 대조→통지.

담당자가 다음 날 승인하거나 ERP가 일시적으로 응답하지 않아도 같은 업무 건을 유지한다. 발주 API 재시도에는 동일 논리 작업의 키를 사용한다. 승인 이후 금액이 달라지면 재승인 경로로 보낸다.

### 계약·문서 검토

여러 문서 추출→조항 비교→추가 자료 요청→담당자 회신→검토 재개. 성공한 문서 추출 결과를 남겨 하나의 파일 실패 때문에 전체 문서를 다시 처리하지 않도록 한다. 자료가 바뀌면 해당 결과의 유효성을 다시 확인한다.

### 고객 환불

환불 가능 여부 확인→승인→환불 요청→결제사 완료 이벤트 대기→사내 장부 반영→고객 통지. 결제사 이벤트 중복과 환불 성공 후 응답 유실을 구분하고, 접수 상태와 실제 완료 상태를 고객 안내에서도 구분한다.

## 11. 도입·운영 체크리스트

아래는 기술 문서를 바탕으로 한 실무 제안이다.

- **업무 ID:** 재시도와 새로운 고객 요청을 구분할 수 있는가?
- **영속 저장:** 완료 결과·대기·기한·외부 이벤트가 재시작 후에도 남는가?
- **부작용 경계:** 조회·판단·발주·메일을 어떤 단위로 재시도하는가?
- **승인 결합:** 승인 대상 버전, 권한, 기한과 변경 여부를 검증하는가?
- **실패 정책:** 일시 오류와 입력 오류, 거절을 다른 경로로 처리하는가?
- **중복·경합:** 중복 webhook, 늦은 이벤트, 동시에 온 요청을 처리하는가?
- **비용 한도:** AI 재호출·툴 호출·실행 시간에 예산과 종료 조건이 있는가?
- **취소·보상:** 이미 실행한 외부 작업을 누가 어떻게 정정하는가?
- **배포:** 진행 중인 이전 실행과 새 코드가 호환되는가?
- **이력 관리:** 긴 이력의 크기·보관 기간·민감정보 접근을 관리하는가?
- **현업 화면:** 실행 중·승인 대기·외부 응답 대기·실패·완료를 구분해 보여주는가?
- **운영 기반:** 엔진·저장소·Worker 장애와 백업·복구 절차까지 담당자가 있는가?

AI가 잘못 판단하면 잘못된 결과도 안정적으로 실행할 수 있다. 업무 평가·승인 기준과 Durable Execution을 함께 설계한다. 복구 가능성이 무한 대기나 무한 재시도를 뜻하지는 않는다.

## 12. 도입 시험과 성과 지표

### 장애 주입 시험 제안

| 시험 | 확인할 결과 |
|---|---|
| 단계 완료 기록 후 Worker 종료 | 기록된 결과 재사용, 남은 단계 진행 |
| 외부 발주 성공 후 완료 보고 전 종료 | 중복 발주 없음, 원격 거래와 대조 가능 |
| 승인 대기 중 재배포 | 대기 상태·승인 대상 유지, 올바른 버전 실행 |
| 동일 승인·webhook 두 번 수신 | 업무 효과가 중복되지 않음 |
| 일부 문서만 추출 실패 | 성공 결과 보존, 실패 단위만 재처리 |
| 모델 API가 계속 실패 | 한도 도달 후 명시적 실패·인계, 비용 폭증 방지 |
| 승인 후 발주 내용 변경 | 기존 승인을 변경된 요청에 재사용하지 않음 |
| 보상 API도 실패 | 보상 진행 상태와 수동 처리 대상 확인 가능 |

### 경영진에게 보고할 지표 — 제안

완료율, 장기 미완료 건수, 자동 복구율, 직원의 수동 복구 시간, 중복 실행 건수, 불필요한 AI 재호출 비용, 대기 사유별 시간, 변경 배포 후 실패율을 본다. 일시적 실패 후 최종 성공과 영구 실패를 구분한다. ‘엔진이 실행 중’인 상태를 ‘고객 업무 완료’로 집계하지 않는다.

### 근거의 한계와 후속 확인

네 기업 사례는 독립 실험이 아닌 공급사 공개 자료다. 구체적 업무·구현·운영 경험을 활용하고, 미공개 비용 절감률이나 무장애 보장을 만들어내지 않는다. 국내 도입 사례는 이번 조사에서 검증해 채택하지 않았다. Restate도 조사 후보로 살펴봤으나 특정 고객의 상세 사례나 세부 보장 비교는 이번 문서에 포함하지 않았다. 단순 고객 로고만으로 사용 업무를 추정한 사례는 제외했다.
