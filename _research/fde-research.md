# [사전 조사] FDE란? AI 엔지니어가 고객 현장으로 들어가는 이유

- 조사·작성 기준일: 2026-09-07
- 목적: 기업 AX 테크블로그 포스트를 위한 개념·기술·산업 사례 조사
- 독자: AI·AX에 관심 있는 경영진, 사업·현업 책임자, CIO·CTO
- 우선순위: 실제 현업의 문제와 구현 과정 → 개념과 역할 → 필요한 기술과 운영 → 도입 판단
- 연결할 기존 글: 「AX는 암묵지를 자산화할 수 있어야 성공합니다」, 「AI 에이전트 엔지니어링 겉핥기」, 「Context Graph란?」
- 자료 원칙: 고객사·공급사의 공식 발표, 실무자 인터뷰, 채용공고, 공식 기술 문서를 우선한다. 직무 정의와 실제 도입 성과, 사업 계획은 구분한다.
- 문서 성격: 포스트 초안이 아닌 리서치 노트. ‘편집 제안’과 ‘가상 예시’는 조사자가 구성한 내용이다.

## 0. 먼저 읽을 결론

### 이 글에서 사용할 정의

> FDE(Forward Deployed Engineer)는 고객의 실제 업무와 기술 환경에 밀착해 문제를 구체화하고, 데이터·소프트웨어·AI를 연결해 운영 가능한 시스템을 구현하며, 현장의 피드백을 재사용 가능한 자산으로 남기는 엔지니어다.

Palantir는 FDSE(Forward Deployed Software Engineer)라는 명칭을 사용한다. 회사마다 배치 방식과 책임 범위가 다르므로 위 문장은 여러 공식 자료를 종합한 **이 글의 작업 정의**다. [Palantir 직무 설명][p2019], [OpenAI FDE 공고][oai-fde], [Anthropic FDE 공고][ant-fde]

### 조사에서 확인한 핵심

1. **생성형 AI 이전부터 있던 역할이다.** Palantir의 2019년 공식 글에 이미 제품 엔지니어와 FDSE의 책임 차이가 나온다. 당시에도 고객 업무와 데이터 시스템의 연결이 중요했다. [Palantir][p2019]
2. **고객사 상주가 정의의 전부는 아니다.** Palantir의 2020년 인터뷰에는 원격 근무 중인 FDSE가 등장한다. 중요한 것은 사용자·업무·피드백과의 거리다. [실무자 인터뷰][p2020]
3. **코드 작성과 현업 이해를 함께 요구한다.** 현재 FDE 공고에는 범위 정의, 구현, 평가, 운영 배포, 고객의 사용 정착과 재사용 자산 개발이 포함된다. [OpenAI][oai-fde], [Anthropic][ant-fde]
4. **암묵지·Context Graph 글과 직접 연결되는 근거가 있다.** AWS의 FDE 파트너 발표는 구축 지식을 온톨로지·평가·MCP 서버·운영 도구·Context Graph로 남기는 방식을 설명한다. [AWS Delivery Harness][aws-partner]
5. **직무 설명이나 투자 발표만으로 효과를 입증할 수는 없다.** 실제 고객 성과는 별도 사례로 확인해야 한다. 아래에서는 FDE 직접 사례, 인접 공동개발 사례, 신규 협업 계획을 구분했다.
6. **FDE는 혼자 모든 일을 떠맡는 사람이 아니다.** Anthropic은 기술 구현을 맡는 FDE와 범위·일정·관계·KPI 등을 조율하는 Technical Deployment Lead의 분업을 명시한다. [Anthropic TDL 공고][ant-tdl]

### 포스트의 중심 논지 후보

고객의 업무를 이해하고, 실제 시스템으로 구현하고, 사용 결과를 보며 고치고, 그 과정에서 얻은 지식을 남기는 책임을 이어주는 역할이 필요하다. FDE는 이 책임을 조직하는 한 가지 방식이다.

이것은 특정 직함을 도입하면 AX가 성공한다는 주장이 아니라, 아래 자료를 종합한 **편집적 결론**이다.

## 1. FDE의 개념과 계보

### 1-1. 일반 제품 개발과 책임 단위가 다르다

Palantir의 설명에서 제품 엔지니어는 여러 고객이 사용할 플랫폼 기능을 개발한다. FDSE는 특정 고객의 목표를 위해 여러 기능을 구성하고 연결한다. 필요한 개선을 제품팀에 전달하거나 제품 코드에 기여하기도 한다. 차이는 개발 실력의 높낮이보다 **무엇의 결과를 책임지는가**에 있다. [Dev versus Delta][p2019]

현장 업무는 요구사항이 처음부터 완성되어 있지 않은 경우가 있다. 사용자가 말하는 ‘재고’, ‘승인’, ‘완료’의 뜻을 확인하고, 시스템이 그 뜻대로 움직이게 만드는 과정이 필요하다. 이때 현업과 설계·구현·검증을 반복하는 방식으로 FDE를 설명할 수 있다. 이 설명은 직무 자료를 업무 상황으로 풀어낸 해석이다.

### 1-2. ‘현장으로 들어간다’는 말의 의미

- 사용자가 실제로 처리하는 사례를 함께 본다.
- 문서에 없는 예외와 시스템의 제약을 확인한다.
- 구현한 결과가 실제 업무에서 쓰이는지 관찰한다.
- 현업의 수정 요청을 코드·데이터·평가 기준으로 바꾼다.

위 네 항목은 이 포스트를 위한 설명 틀이다. 물리적 현장 방문이 필요할 수 있지만, 원격 협업도 가능하다. 또한 FDE는 역사적으로 데이터·소프트웨어 문제를 폭넓게 다뤘으므로 모두 LLM 전문가였다고 설명하면 안 된다. [Palantir 실무자 인터뷰][p2020]

### 1-4. 비슷한 직무와 무엇이 다른가

다음은 공식 직무 설명을 비교한 **종합 정리**다. 회사별 업무 경계는 겹치며, 직함으로 우열을 나누는 표가 아니다.

| 역할 | 주로 책임지는 것 | FDE와 비교해 확인할 점 |
|---|---|---|
| 제품 소프트웨어 엔지니어 | 여러 고객이 쓰는 제품 기능·품질 | 특정 고객의 업무 결과를 위해 시스템을 가로질러 구현하는 책임이 누구에게 있는가? |
| Solutions / Sales Engineer | 도입 전 기술 검토, 제품 적합성, 데모·프로토타입 | 운영용 구현과 출시 후 사용 정착까지 책임지는가? SE도 코드를 작성할 수 있다. |
| Solutions Architect | 시스템 설계, 기술 선택, 통합 구조 | 설계와 실제 구현·배포의 책임이 어떻게 나뉘는가? |
| 컨설턴트 | 문제 진단, 전략, 업무·조직 변화와 경우에 따른 구현 | 현장 반복 개발과 결과 검증을 누가 맡는가? 컨설팅 회사도 FDE 팀을 운영한다. |
| SI 수행 조직 | 여러 시스템의 구축·연동·이행 | 고객별 구축 결과를 운영하면서 개선하고 공통 자산으로 환류시키는가? |
| Customer Success Manager | 제품 채택, 활용 가치, 고객 관계와 운영 지원 | 직접 생산용 시스템을 구축하는 책임이 포함되는가? CSM도 기술적인 역할일 수 있다. |
| ML / AI Engineer | 모델·AI 시스템·데이터 파이프라인의 개발과 운영 | 고객 업무의 탐색·조율·수용 기준까지 맡는가? |
| FDE | 고객 환경 안에서 문제 발견부터 구현·사용 결과까지 연결 | 현장 지식, 소프트웨어 구현, 제품·운영 피드백의 책임을 어디까지 갖는가? |

비교 근거: [Palantir][p2019], [OpenAI FDE][oai-fde], [Anthropic TDL][ant-tdl], [AWS 파트너 모델][aws-partner], [Salesforce CSM 설명][csm], [Google ML Engineer 역량][ml-engineer].

Palantir·AWS 자료의 ‘기존 컨설팅과 다르다’는 표현은 해당 회사의 포지셔닝으로 읽는다. ‘컨설턴트는 보고서만 쓰고 FDE만 구현한다’거나 ‘SI를 FDE가 대체한다’는 일반화는 피한다.

## 2. 산업 현장 사례: 무엇이 실제로 확인되는가

### 2-1. 사례를 읽는 기준

FDE 참여 여부와 도입 단계를 별개로 본다. **FDE가 명시되어도 아직 계획일 수 있고, 운영 성과가 있어도 FDE라는 직함이 확인되지 않을 수 있다.**

| 사례 | 산업·업무 | FDE 참여 근거 | 도입 단계 | 본문에서 맡길 역할 |
|---|---|---|---|---|
| Airbus–Palantir | 항공기 생산 운영 | 직접 명시: 공식 발표의 담당 FDE 설명 | 운영·확장 | 데이터와 현장 판단을 연결하는 역할의 기원 |
| NFL–AWS | 스포츠 데이터 기반 팬 서비스 | 직접 명시: 고객 CIO의 FDE 공동개발 설명 | 운영 | 현대 AI FDE의 직접 사례 |
| Novo Nordisk–AWS | 제약 연구개발 | 직접 명시: 고객사 발표 | 공동개발·확대 계획 | 높은 도메인 전문성이 필요한 이유 |
| Jabil–AWS·Mendix | 제조 불량 원인 분석 | 현장 공동개발 확인, FDE 직함 미확인 | 운영·효과 보고 | 암묵지를 실제 업무 지식으로 남기는 과정 |
| Tampa General Hospital–Palantir | 병상·환자 흐름 관리 | 엔지니어와 현업 밀착협업 확인, FDE 직함 미확인 | 기존 운영 + 신규 AIP 확대 발표 | 조직의 여러 판단을 연결하는 작업 |
| Lyft–AWS·Anthropic | 기사·승객 고객 지원 | GenAI Innovation Center 선행 공동개발 | 운영 | 답변과 실제 업무 해결의 차이 |
| Virgin Atlantic–Tomoro | 여행 탐색·서비스 경험 | 현장 공동설계 확인, 개별 FDE 직함 미확인 | 웹 서비스 출시 | 기업 고유 서비스 방식을 제품에 담는 작업 |

### 2-2. Airbus: 생산 현장의 결정을 소프트웨어로 연결

**문제와 개입.** A350 생산 확대에는 부품·작업지시·일정·품질 정보와 팀 간 의존관계를 함께 보는 일이 필요했다. Palantir와 Airbus는 데이터와 운영 화면을 연결했다. 공식 Demo Day는 Airbus 계정을 초기부터 담당한 Bianca를 FDE로 소개하고, 현장 사용자와 운영 워크플로를 개발했다고 설명한다. [Palantir Demo Day p.3][p-demo], [파트너십 자료][p-airbus]

**기술과 단계.** Foundry 기반 데이터 통합과 운영 애플리케이션이 중심인 선행 사례다. Airbus의 2019년 발표는 Skywise가 항공사 생태계로 확장된 상태를 확인해 준다. LLM 도입 사례로 설명할 수는 없다. [Airbus 발표][airbus-skywise]

**수치와 한계.** 공급사 자료의 33%는 인도 증가·가속 맥락의 표현이며, 이를 ‘생산 리드타임 33% 감소’로 바꿀 근거가 없다. FDE 개인의 기여율·팀 규모·비용도 확인되지 않는다. 숫자보다 현장 판단과 시스템을 연결한 과정을 중심으로 쓰는 편이 좋다.

### 2-3. NFL: 기존 데이터를 팬이 직접 사용할 제품으로

**문제와 개입.** NFL은 데이터 기반 팬 경험을 만들기 위해 AWS FDE와 공동 개발했다. 고객 CIO는 엔지니어들이 NFL 팀과 함께 일해 수주 안에 운영 환경으로 출시했다고 밝혔다. 공개된 결과물은 NFL Fantasy AI와 NFL IQ다. [AWS 공식 발표의 고객 발언][aws-launch]

**기술.** NFL IQ의 엔지니어링 설명에서는 Amazon Quick 기반 대시보드와 AI 어시스턴트가 데이터 모델·구조화 데이터·맥락 메타데이터를 공유한다. 별도 챗봇을 만드는 것만으로 설명되지 않는 제품 통합 사례다. [NFL IQ 구현 설명][nfl-iq]

**성과와 한계.** ‘수주 내 production 출시’는 확인되지만 정확한 주수·개발비·매출·이용자 증가율은 없다. 팬과 방송사의 반응을 측정했다는 발언을 정량 성과로 바꾸면 안 된다.

### 2-4. Novo Nordisk: 과학자와 엔지니어의 공동 작업 공간

**개입과 기술.** Novo Nordisk는 런던 기존 시설의 공동혁신 허브에서 연구개발 인력과 AWS 전문가가 협업한다고 발표했다. 고객사 자료에 AWS FDE가 직접 등장한다. Bio Discovery·Bedrock과 향후 AgentCore 활용을 제시한다. [Novo Nordisk 공식 발표][novo]

**단계와 한계.** 공동 작업과 전략적 확대가 확인되는 사례다. 신약 개발 기간 단축은 목표이며 신규 FDE 허브의 실현 성과 수치는 없다. 발표에 함께 나오는 이전 임상 문서 업무·직원 생산성 지원 실적을 신규 허브의 성과로 합치지 않는다.

**편집 활용.** 엔지니어가 과학자의 전문 판단을 대신한다는 이야기가 아니라, 고유한 연구 데이터와 판단 맥락을 함께 시스템으로 만드는 이야기로 쓴다.

### 2-5. Jabil: 시리얼 번호와 숙련자의 진단 지식을 연결

**문제와 공동개발.** 제조 기술자가 제품 사양·고객별 디버깅 절차·고장 이력을 여러 곳에서 찾아야 했다. Jabil은 일선 기술자를 개발에 참여시키고 AWS·Siemens Mendix와 Debug Tool Assistant를 구축했다. 이 자료에서는 FDE 직함이 확인되지 않는다. [공동 저술 사례][jabil]

**작동 방식.** 시리얼 번호를 읽어 제품 맥락을 찾고, 출처가 있는 현지 언어 진단 안내를 제공한다. 승인된 기술자 의견은 지식 베이스로 돌아간다. Bedrock·S3·Mendix가 AI·문서·업무 앱을 연결한다.

**공개 수치.** 작동하는 솔루션까지 4주, 불량 분석 25% 가속, 폐기·재작업 15% 감소를 보고한다. 측정 기간·대상 공장·표본은 미공개다. ‘분석 가속’을 같은 비율의 시간 감소로 변환하지 않는다.

**편집 활용.** 기존 암묵지 글의 가장 구체적인 후속 사례다. 다만 Amazon Q Business 기반 Jabil의 다른 프로젝트와 기술·일정·성과를 섞지 않는다.

### 2-6. Tampa General Hospital: 병상 배정은 여러 사람의 판단을 잇는 일

**문제와 개입.** 병원은 Palantir 엔지니어가 운영·분석·임상 전문가와 밀접하게 협업한다고 밝혔다. 병상과 환자 흐름을 다루는 Foundry 활용은 2021년에 시작됐고, 2024년 발표는 AIP 기반 확대를 추가한다. 해당 발표에는 FDE 직함이 없다. [병원 공식 발표][tgh]

**공개 수치.** 병원은 병상 배정 소요시간 83% 감소, 마취후회복실의 환자 이동 지연을 뜻하는 PACU holds 지표 28% 감소 등을 보고한다. 후자를 대기시간 28% 감소로 바꾸어 쓰지 않는다. 대상 기간·표본·세부 산식·다른 운영 개선 요인의 기여율은 자세히 공개하지 않았다.

**중요한 시점 구분.** 기존 Foundry와 업무 개선의 성과를 이후 도입할 AIP나 LLM의 결과로 쓰면 안 된다. 환자 흐름·병상·인력의 실제 운영을 함께 이해해야 한다는 사례로 사용한다.

### 2-7. Lyft: 문의 분류에서 운행·정산 맥락을 확인하는 지원으로

**문제와 개입.** Lyft는 AWS Generative AI Innovation Center와 사업 목표를 정의하고 고객 의도를 파악하는 에이전트를 공동개발했다. 자연어 문의를 운행·결제 정보와 연결하고 필요한 조치와 사람 이관으로 이어간다. [Lyft–AWS 발표][lyft]

**기술과 성과.** Claude를 Bedrock으로 이용하는 구성이며, Lyft는 평균 해결시간 87% 감소를 보고한다. 비교 기간·문의 구성·전체 물량 중 AI 비율은 충분히 공개하지 않는다.

**분류.** 2026년 AWS FDE 신설 조직의 직접 실적이 아니라, 그 이전 전문 엔지니어 공동개발의 실제 운영 사례다. 답변 생성과 업무 시스템 연결의 차이를 설명하는 데 사용한다.

### 2-8. Virgin Atlantic: 항공사다운 서비스 경험을 구현

**문제와 개입.** Tomoro는 Virgin Atlantic 직원의 서비스 방식과 고객 경험을 이해하며 Concierge를 설계·구축했다. 항공사는 OpenAI 기반 텍스트·음성·이미지 대화와 개인화된 여행 탐색 서비스를 웹사이트에 출시했다고 밝혔다. [Virgin Atlantic 공식 발표][virgin]

**한계.** 예약 전환율·비용 절감·구체적인 평가 구조는 공개하지 않는다. 개별 프로젝트의 FDE 직함도 해당 발표에서 확인되지 않는다.

**시점 구분.** OpenAI의 2026년 Deployment Company 발표는 Tomoro의 기존 실적으로 이 고객을 언급한다. 과거 프로젝트를 신생 Deployment Company가 수행한 것으로 바꾸면 안 된다. 같은 자료에서 인수는 합의·종결 조건이 남은 상태다. [OpenAI 발표][openai-deploy]

### 2-9. 사례 선택 권고

**핵심 본문 3개:** Airbus → NFL → Jabil.

- Airbus: FDE 직접 근거와 현장 운영의 계보.
- NFL: 현대 AI 제품을 공동 개발한 직접 사례.
- Jabil: FDE 직함을 단정하지 않으면서 암묵지·업무 맥락·지식 환류를 보여주는 인접 사례.

병원 경영진이 주 독자라면 Jabil과 함께 TGH를 선택할 수 있다. Novo Nordisk는 성공 수치보다 협업 구조의 사례로 쓴다. 모든 사례를 본문에 넣기보다 업종과 설명 역할이 다른 것부터 선택하는 편이 읽기 좋다.

## 3. 기술적으로 FDE는 무엇을 만드는가

### 3-1. 특정 스택이 아니라 업무 요구에 따른 구성

OpenAI의 의료 FDE 공고는 발견·설계·구현·평가·운영화·정착·이관을 명시하고, 전자의무기록·보험청구·API·데이터 플랫폼 통합을 요구한다. 이는 직무 기대 사항이며 특정 병원의 도입 성과는 아니다. [공식 채용공고][oai-health]

아래 표는 직무 자료와 기술 문서를 조합한 **구현 설계 관점**이다. 모든 프로젝트에 모든 구성요소가 필요한 것은 아니다.

| 기술 영역 | 현장에서 생기는 질문 | 구현·검토할 산출물 | 기술 근거 |
|---|---|---|---|
| 업무·도메인 모델 | ‘주문 완료’, ‘가용 재고’, ‘승인됨’이 정확히 무엇인가? | 업무 객체·속성·관계·상태 전이·행동 정의 | [Palantir Ontology][ontology] |
| 데이터·레거시 연결 | 어떤 시스템이 실제 상태를 갖고 있는가? | API·파이프라인·식별자 매핑·오류 처리·데이터 책임자 | [의료 FDE 직무][oai-health] |
| 결정론적 코드와 AI의 분담 | 고정 규칙과 상황별 판단을 어디서 나눌까? | 규칙·계산·워크플로와 모델 호출의 경계 | [Building effective agents][agents] |
| Tool | AI가 업무 시스템에 무엇을 요청할 수 있는가? | 명확한 입력·결과·오류·조회 및 쓰기 권한을 가진 도구 | [Tool 설계][tools] |
| MCP | 도구를 에이전트에 어떤 인터페이스로 제공할까? | 업무 도구를 노출하는 서버·연결 설정·인증 구조 | [Anthropic FDE 직무][ant-fde] |
| Context·검색 | 이번 판단에 필요한 근거는 무엇인가? | 자료 선별·실행 중 검색·압축·출처 연결 | [Context Engineering][context] |
| Memory·진행 상태 | 다음 세션에 무엇을 기억해야 하는가? | 진행 중인 일·확정 사실·미해결 문제의 외부 기록 | [Context Engineering][context] |
| Skill | 반복 업무의 수행 방법을 어떻게 배포할까? | 지침·스크립트·참고자료와 검증·갱신 절차 | [Agent Skills][skills] |
| 평가·검증기 | 실제로 일을 끝냈다고 어떻게 확인할까? | 현업 평가세트·예외 사례·최종 시스템 상태 검사 | [에이전트 평가][evals] |
| 사람의 검토·승인 | 누가 어떤 정보를 보고 결정해야 하는가? | 제안과 실행의 분리·앱 검증·승인 결과 처리 | [AWS 확인·제어 반환 예제][human-approval] |
| 실행 환경·복구 | 실행 중 서버가 죽으면 어떻게 이어갈까? | 세션 기록·상태 보존·격리·자격증명 경계·복구 | [Managed Agents 구현][managed] |
| 관측·운영 | 왜 틀렸고 왜 느렸는지 알 수 있는가? | 오류 분석·실행 기록·배포·모니터링·운영 문서 | [의료 FDE 직무][oai-health] |

### 3-2. Ontology와 Context Graph를 넣는 이유와 범위

Ontology는 데이터의 표·컬럼을 주문·설비·고객 같은 업무 대상으로 맞추고, 관계와 수행 가능한 행동을 정의하는 데 도움을 준다. Palantir의 제품 문서는 객체와 관계뿐 아니라 행동·함수·보안도 함께 다룬다. [Ontology 문서][ontology]

이전 글의 Context Graph는 판단의 근거·정책·승인·실행·결과를 이어서 보존하는 관점이다. FDE가 반복적으로 마주치는 판단을 이런 구조로 남길 수 있다. 다만 이 연결은 **기존 포스트와 FDE 자료를 종합한 설계 제안**이며, 모든 FDE에게 Graph DB 설치가 필수라는 뜻은 아니다.

단순 업무는 기존 관계형 데이터베이스, API, 이벤트 기록과 평가세트만으로 시작할 수 있다. 그래프 도입 여부는 관계 탐색·이력 재사용의 필요와 기존 시스템을 보고 판단한다.

### 3-3. Tool·Skill·Memory를 구분해서 설명하기

- **Tool:** 고객 정보 조회, 재고 확인, 주문 초안 생성처럼 외부 기능을 호출하는 인터페이스.
- **Skill:** 어떤 순서와 기준으로 일을 수행할지 정리한 지침·스크립트·참고자료 묶음.
- **Memory:** 현재 작업 상태와 다음 작업에서도 필요한 정보를 유지하는 장치.
- **평가:** 위 요소가 함께 작동했을 때 업무를 정확하게 수행했는지 확인하는 장치.

이 구분은 [도구 설계][tools], [Skills][skills], [Context Engineering][context], [평가 문서][evals]를 바탕으로 한 설명이다. Skill에 ‘승인 후 실행’이라고 쓰는 것과 API·업무 시스템이 실제 승인권을 검사하는 것은 다르다.

### 3-4. 사람의 ‘확인’과 회사의 ‘승인’은 다르다

AWS 예제는 도구 실행 전 사용자 확인과 애플리케이션으로 제어를 돌려주는 방식을 설명한다. 신청자가 내용을 확인하는 버튼만으로 회사의 결재선이 구현되지는 않는다. 실제 승인권자, 승인 대상 값, 변경 시 재승인 여부는 업무 시스템과 함께 설계해야 한다. [AWS 기술 예제][human-approval]

예를 들어 승인받은 것은 100만 원 발주인데 실행 입력이 150만 원으로 바뀌었다면 같은 승인을 재사용해서는 안 된다. 이는 기업 업무에 적용한 **설명용 예시**다.

### 3-5. AI로 FDE의 개발 업무도 바뀐다

AWS는 FDE 전달 방식에 AI-Driven Development Life Cycle(AI-DLC)을 연결한다. AI-DLC는 기획·구축·운영 단계에서 AI가 작업을 지원하고 사람이 검토하며, 요구사항·계획·설계 자료를 유지하는 방식을 설명한다. [AWS AI-DLC][ai-dlc]

포스트에서는 ‘FDE가 고객을 위해 에이전트를 만든다’와 ‘FDE 자신도 코딩·문서·평가에 AI를 쓴다’를 나누면 좋다. 개발 속도가 빨라져도 업무 정의와 실제 결과를 검증하는 책임이 사라지는 것은 아니다.

## 4. 현업 발견부터 운영 이관까지: 산출물 중심의 실행 흐름

이 절의 단계와 산출물은 **여러 직무 자료를 종합한 편집·실무 제안**이다. 특정 공급자의 공식 방법론이나 계약상 보장사항이 아니다. 평가는 첫 단계부터 함께 설계하고, 사용 결과에 따라 앞 단계로 돌아간다.

| 단계 | 함께 풀 질문 | 검토 가능한 산출물 |
|---|---|---|
| 1. 목표와 기준점 | 어느 업무의 어떤 결과를 개선할까? | 업무 책임자, 현재 처리시간·대기·오류, 범위와 제외 범위 |
| 2. 실제 업무 관찰 | 담당자는 어떤 자료를 보고 어디서 예외를 판단하는가? | 실제 사례, 화면·시스템 이동, 예외와 암묵적 기준 목록 |
| 3. 의미·데이터·권한 정리 | 시스템마다 같은 용어가 같은 뜻인가? | 객체·상태 정의, 원천 시스템, 접근·수정 권한 지도 |
| 4. 작은 업무 구현 | AI 판단과 고정 코드를 어디서 나눌까? | 업무 흐름, Tool, 필요한 Skill·검색·Memory, 사용 화면 |
| 5. 실제 사례 평가 | 정상·예외·정보 부족에서 어떻게 행동해야 하는가? | 현업 평가세트, 실패 분류, 승인 및 운영 전환 기준 |
| 6. 운영 연결 | 오류·재시도·취소·중복 요청을 어떻게 다룰까? | 실행 검증, 배포·복구 절차, 로그·알림·담당자 |
| 7. 공동 운영과 이관 | 고객팀이 규칙 변경과 장애를 처리할 수 있는가? | 코드·설정·평가·런북, 교육, 운영 접근권한, 이관 점검 |
| 8. 재사용과 제품 환류 | 무엇이 고객 고유이고 무엇이 공통 패턴인가? | 재사용 가능한 연결·검증 모듈, 제품 개선안, 지식 소유 범위 |

직무 범위의 근거: [OpenAI 의료 FDE][oai-health], [Anthropic TDL][ant-tdl], [AWS 고객 자립 운영 설명][aws-launch].

## 5. 모든 기술을 한 업무로 설명하는 가상 예시

### 납기 지연 대응: ‘재고가 있다’는 말부터 확인한다

**아래는 실제 고객 사례가 아닌 설명용 가상 상황이다.**

영업팀은 고객에게 납기를 답해야 한다. ERP에는 재고가 있다고 나오지만, 창고 담당자는 그중 일부가 품질검사 대기라고 말한다. 협력사 메일에는 다음 입고 일정이 바뀌었다고 적혀 있다. 대체품은 존재하지만 고객 승인이 필요하다.

이 상황에서 FDE와 고객팀이 함께 정할 항목은 다음과 같다.

| 관찰한 사실 | 설계할 것 | 남길 자산 |
|---|---|---|
| ERP의 재고와 출하 가능한 재고가 다르다 | 가용 재고의 계산·상태 정의 | 업무 용어와 데이터 규칙 |
| 여러 시스템을 확인해야 한다 | 재고·공급 일정·대체품 조회 Tool | 입출력·오류·권한이 명확한 인터페이스 |
| 담당자마다 확인 순서가 다르다 | 검증된 납기 답변 절차 Skill | 지침과 사례, 갱신 담당자 |
| 고객·제품에 따라 조건이 다르다 | 이번 주문에 필요한 Context 조회 | 근거·시점·예외 조건 |
| 승인권자가 다음 날 답할 수 있다 | 진행 상태 저장과 재개 | 승인 대기·미해결 항목 기록 |
| 가격·계약 변경은 별도 승인 대상이다 | 지정 승인권자와 실행 API 검증 | 승인 대상 값과 실제 실행 결과 |
| 과거 예외가 다음 판단에 도움이 된다 | 필요할 때 판단 이력의 관계화 | 근거·승인·실행·결과를 잇는 기록 |

핵심은 개발자가 숨은 업무 규칙을 추측하는 것이 아니라 **현업과 확인하고 검증 가능한 형태로 만드는 과정**이다. 원천 API가 정보 부족을 반환하면 에이전트가 날짜를 지어내지 않고 확인이 필요한 항목을 보여주도록 평가한다.

짧게 도식화하면 다음과 같다.

```text
실제 업무와 예외 관찰
        ↓
업무 의미·데이터·권한 정의
        ↓
코드 + Tool + 필요한 Skill·Context·Memory
        ↓
실제 사례 평가 → 사람의 검토·승인 → 실행 결과 확인
        ↑                                 ↓
        └────── 현업의 수정·운영 피드백 ──────┘
```

## 6. FDE가 떠난 뒤 무엇이 남아야 하는가

### 6-1. 두 종류의 학습을 구분한다

| 구분 | 고객 조직의 업무 자산 | 구축 조직의 전달·개발 자산 |
|---|---|---|
| 무엇을 기억하는가? | 업무 기준, 승인된 예외, 실제 수행 결과, 현업의 교정 | 아키텍처 선택, 통합 패턴, 평가 방법, 일반화된 코드 |
| 왜 필요한가? | 다음 직원·에이전트가 같은 일을 다시 이해하는 비용을 줄이기 위해 | 다음 구축에서 검증된 방법을 활용하기 위해 |
| 예시 | 고객별 납기 예외의 근거와 결과 | 승인 상태를 안전하게 처리하는 재사용 모듈 |
| 확인할 권리 | 고객 데이터·계약·접근권한·보관 규칙 | 코드·템플릿·플랫폼의 소유와 재사용 허용 범위 |

AWS APN의 Delivery Harness는 특히 오른쪽의 구축 지식 축적을 설명한다. 기존 포스트의 Context Graph는 왼쪽의 업무 의사결정 기억에 무게를 두었다. 서로 연결할 수 있지만 같은 범위라고 단정하지 않는다. [AWS 파트너 발표][aws-partner]

고객 자료를 다른 고객에게 옮겨도 된다는 의미로 재사용을 설명해서는 안 된다. 계약·비밀·개인정보를 포함한 자료와 일반화된 구현 패턴의 경계를 따로 정해야 한다. 이는 위 모델을 도입할 때의 운영·계약 검토 제안이다.

### 6-2. 이관할 산출물 제안

- 업무 목적, 범위, 예외와 책임자.
- 코드·설정·배포 절차, 필요한 라이선스와 접근권한.
- 데이터 원천, 식별자·용어 매핑, 변경·오류 처리 방법.
- Tool·Skill·정책의 검증 및 갱신 절차.
- 현업 평가세트와 모델·프롬프트 변경 시 회귀 평가 방법.
- 실행 기록, 알림, 장애 대응·복구 런북.
- 개인정보·고객 자료의 보관·정정·삭제 책임.
- 고객팀이 직접 변경·복구를 수행해 보는 이관 점검.

AWS는 고객 자립성을 목표로, 관찰자에서 공동 구축자·운영자로 전환하는 방식을 설명한다. 위 목록의 상세 형식과 철수 조건은 이 문서의 제안이다. 모든 공급사가 동일한 수준의 자립 운영을 보장하는 것은 아니다. [AWS 발표][aws-launch]

### 6-3. 재사용이 가능한 제품과 고객별 커스텀의 균형

고객별 규칙·데이터 연결은 필요하지만 모든 변경을 별도 코드 복사본으로 만들면 유지보수가 어려워질 수 있다. 반대로 공통 제품의 기능만 고집하면 현업의 중요한 예외를 놓칠 수 있다.

편집 제안으로 다음 세 층을 나누어 설명할 수 있다.

1. 여러 고객에게 재사용하는 플랫폼·연결·검증 기능.
2. 고객별 설정과 업무 규칙.
3. 특정 고객의 운영 데이터·판단 기록.

어떤 것을 제품 개선으로 돌리고 무엇을 고객 고유 설정으로 둘지 결정하는 과정 자체가 중요하다. 제품 환류의 직무 근거는 Palantir와 Anthropic 설명에서 확인된다. [Palantir][p2020], [Anthropic][ant-fde]

## 7. FDE는 누구와 일하는가

다음 조직 구성은 **프로젝트 설계 제안**이다. 실제로 한 사람이 여러 역할을 맡을 수도 있고, 역할이 더 나뉠 수도 있다.

| 역할 | 결정하거나 책임질 것 |
|---|---|
| 고객 측 경영·사업 책임자 | 목표, 예산, 부서 간 우선순위 |
| 현업 책임자·숙련자 | 업무 의미, 정상·예외 기준, 결과 수용 |
| FDE | 데이터와 기술 제약을 반영한 설계·구현·검증 |
| 고객 IT·데이터 담당자 | 원천 시스템, 접근권한, 운영 환경과 이관 |
| 보안·법무·준법 담당자 | 데이터·외부 연결·권한·계약상 제약 |
| 배포·프로젝트 책임자 | 범위, 일정, 의존관계, 조직 정착과 성과 확인 |
| 공급사 제품·연구팀 | 공통 제품 개선과 모델·플랫폼 피드백 수용 |

Anthropic TDL 공고는 기술 구현과 전달·조율 역할을 나누는 실제 조직 설계의 근거다. OpenAI 의료 FDE 공고도 기술 구현 책임과 상업적 관계 책임을 구분한다. FDE를 영업·법무·현업·개발·운영의 만능 1인으로 묘사하지 않는다. [Anthropic][ant-tdl], [OpenAI][oai-health]

## 8. 경영진이 검토할 도입 조건과 한계

### 8-1. FDE 방식이 유용할 수 있는 조건

아래는 자료에서 확인한 역할을 바탕으로 한 **선택 기준 제안**이다.

- 중요한 업무가 여러 시스템과 부서를 오간다.
- 숙련자가 판단하는 예외가 많고 문서만으로 요구를 확정하기 어렵다.
- 작은 구현을 현업과 반복 검증할 수 있다.
- 기존 제품·플랫폼을 활용하되 고객별 통합과 조정이 필요하다.
- 실제 사용할 현업 책임자와 고객 측 기술 담당자를 확보할 수 있다.
- 구축 결과를 운영하고 개선할 예산·책임·권한을 함께 정할 수 있다.

표준 제품의 설정만으로 충분한 업무는 제품 도입과 교육으로 해결할 수 있다. 업무 규칙이 안정적이고 AI 판단이 필요하지 않은 단계는 기존 코드·자동화가 적절할 수 있다. 에이전트의 복잡성도 업무 요구에 맞춰 선택한다. [에이전트 구성 원칙][agents]

### 8-2. 실패하거나 비용이 커질 수 있는 지점

| 문제 | 확인할 신호 | 검토할 대응 |
|---|---|---|
| 현업 책임자가 없다 | 기능은 완성됐는데 업무에서 쓰지 않는다 | 사용자·수용 기준·운영 책임자를 초기부터 지정 |
| 접근권한 확보가 늦다 | 실제 데이터와 다른 샘플로만 시연한다 | 데이터·보안 담당자를 범위 정의에 참여 |
| 고객별 수정이 계속 쌓인다 | 비슷한 기능이 고객마다 별도 코드로 존재한다 | 공통 모듈·설정·고객 데이터의 경계 관리 |
| 평가가 데모에 머문다 | 정상 사례는 잘하지만 예외를 측정하지 않는다 | 현업 실패 사례와 실행 결과를 회귀 평가에 포함 |
| 승인 버튼을 통제로 착각한다 | 승인 대상 값과 실제 실행 값이 다르다 | API의 권한·값 검증과 재승인 규칙 구현 |
| 특정 엔지니어에게 지식이 갇힌다 | 담당자가 없으면 규칙 변경·복구를 못 한다 | 공동 운영과 고객 주도 이관 점검 |
| 플랫폼·인력 비용이 가려진다 | 구축비만 보고 운영·검토·재작업을 계산하지 않는다 | 전체 수행 비용과 업무 성과를 같은 단위로 비교 |
| 재사용의 권리 범위가 모호하다 | 고객 자료와 공통 패턴의 경계가 없다 | 소유·접근·반출·재사용 범위를 문서화 |

이 표는 관찰 가능한 위험을 정리한 제안이며, FDE 프로젝트에서의 발생률을 입증하는 통계는 아니다.

### 8-3. 공급자 관점과 고객 관점의 이해관계

공급자는 고객 도입 확대와 플랫폼 활용, 공통 제품 개선에서 이익을 얻는다. 고객은 업무 성과와 운영 가능성을 원한다. 두 목표가 항상 자동으로 일치하지는 않으므로, 사용할 제품·독자 개발 범위·운영 지원·전환 시 자산 접근을 합의하는 것이 중요하다.

AWS는 파트너가 소유하는 전달 자산을, Microsoft는 고객 고유 지식과 IP 보호를 강조한다. 이는 각 회사의 제공 모델 설명이며, 실제 프로젝트의 권리와 책임은 계약에서 확인할 사항이다. [AWS][aws-partner], [Microsoft][ms-frontier]

## 9. 성과를 무엇으로 측정할까

다음 지표는 **고객·FDE가 함께 고를 수 있는 예시**다. 채용공고가 요구하는 기준점·수용 기준·KPI 설정을 구체화한 것이며, 업계 공통 점수표가 아니다. [Anthropic TDL][ant-tdl]

| 관점 | 측정 후보 | 같이 봐야 할 것 |
|---|---|---|
| 첫 운영 적용 | 실제 업무가 처음 처리될 때까지 걸린 시간 | 데모·시험·제한 운영·정식 운영의 단계 차이 |
| 업무 효율 | 전체 처리시간, 부서 간 대기, 재작업 | AI 생성 이후 사람의 검토 시간 |
| 품질 | 정상·예외별 완료율, 반려·오류 | 업무 난이도와 문의 구성 변화 |
| 실제 실행 | 원천 시스템의 결과와 요청의 일치 | 제안만 했는지, 승인·실행까지 했는지 |
| 통제 | 잘못된 쓰기·권한 위반, 적절한 이관 | 차단 때문에 생기는 지연·운영 부담 |
| 경제성 | 완료 업무 한 건당 전체 비용 | 모델·도구·플랫폼·사람 검토·운영 지원 |
| 정착 | 목표 업무의 실제 사용·재사용 | 계정 수·로그인 수와의 차이 |
| 유지보수 | 업무 규칙 변경과 오류 복구 시간 | 특정 개인·공급사 의존 정도 |
| 고객 운영 역량 | 고객팀이 직접 수정·배포·복구한 범위 | 이관 이후에도 유지되는지 |
| 제품·지식 환류 | 재사용 자산, 회귀 평가와 개선안 | 자산 수보다 실제 사용과 수정 비용 |

시간 절약을 곧바로 같은 액수의 인건비 감소로 환산하지 않는다. 처리 여력·초과근무·서비스 수준·추가 매출 중 어떤 변화로 이어졌는지 별도로 확인한다. FDE 투입 자체의 순효과를 주장하려면 제품·데이터 정비·현업 참여 등 다른 요인을 분리할 추가 근거가 필요하다.

|---|---|---|
| Airbus | 항공기 한 대에 남은 작업과 부품을 여러 팀이 따로 보고 있다 | FDE가 데이터와 실제 판단을 잇는 역할임을 구체화 |
| Jabil | 기술자가 같은 제품을 앞에 두고도 필요한 고장 지식을 찾지 못한다 | 기존 암묵지 글과 바로 연결. FDE 직접 사례가 아님을 설명 |
| 가상 납기 대응 | 화면에는 재고가 있지만 출하할 수 없는 물량이다 | 우리 회사에도 있을 법한 업무 의미의 차이를 보여줌 |

권장안은 **Airbus로 시작하고, 정의 이후 NFL, 기술 설명에서 Jabil을 사용하는 구성**이다. 첫 문단부터 직함·약어를 나열하기보다 독자가 알아볼 업무 문제를 보여준다.

### 본문 순서 제안

1. 들어가며: 제품을 도입한 뒤에도 남는 현장의 문제와 글의 결론.
2. FDE란: 고객 업무 결과를 중심으로 일하는 엔지니어, Palantir 계보.
3. 실제로 무엇을 했나: Airbus·NFL, 필요하면 Jabil 인접 사례.
4. 현장에서 발견하는 것: 데이터의 의미, 예외, 도구·권한·평가.
5. 누가 함께 일하나: 현업·IT·보안·배포 책임자와의 분업.
6. 무엇을 남겨야 하나: 업무 지식, 운영 역량, 재사용 가능한 구축 자산.
7. 나가며: 조직에 필요한 책임과 지원을 확인하는 질문, 상담 연결.

### 기존 글과 이어지는 질문

- 암묵지 글: 숙련자가 아는 판단 기준을 어떻게 드러낼 것인가?
- Context Graph 글: 그 기준과 판단의 이력을 어떻게 남기고 다시 사용할 것인가?
- 이번 FDE 글: 누가 현업과 함께 그것을 구현·검증·운영 가능한 상태로 만들 것인가?

### CTA로 연결할 내용

엡실론델타의 지원을 설명할 때는 FDE라는 이름보다 제공할 일을 구체적으로 말하는 것이 좋다. 현업 관찰과 과제 선정, 데이터·도구·권한 연결, 실제 사례 평가, 운영 인계와 지속 개선을 함께 설계한다는 방향으로 연결할 수 있다.

고객 내부에서 맡아야 할 업무 결정과 외부에서 도울 수 있는 기술·운영을 구분한다. 현재 확인하지 않은 자체 고객 성과, 해외 FDE 프로그램 인증·파트너 자격, 보장된 기간·절감률을 회사 실적으로 추가하지 않는다.
