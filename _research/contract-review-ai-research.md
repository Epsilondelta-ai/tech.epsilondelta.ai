## 1. 핵심 결론과 글의 관점

계약서의 위험 조항을 찾는 것과 우리 회사가 받아들일 조건을 판단하는 것은 다른 업무다. 계약 검토 AI를 현업에 적용하려면 계약 문장뿐 아니라 거래의 목적, 우리 회사의 입장, 선호 조건, 양보할 수 있는 범위, 예외를 승인할 사람을 함께 다뤄야 한다.

이번 글의 중심은 ‘AI가 법률을 얼마나 잘 아는가’보다 **숙련자가 하던 협상 판단을 어떻게 회사의 검토 기준으로 정리하고 실제 업무에 연결하는가**에 둔다. 법무만의 일이 아니다. 대금 지급 조건은 재무, 이행 가능성은 운영, 고객과의 거래 조건은 영업의 판단이 필요하다.

후킹 제목 후보: **계약서는 AI가 읽었는데, 왜 협상은 다시 해야 할까?**

도입 장면 후보 — 실제 사례가 아닌 설명용 가상 상황:

> 영업 담당자가 AI에게 계약서 검토를 맡겼다. 수정 의견은 스무 개나 나왔다. 법무 담당자가 묻는다. “이 중 꼭 고쳐야 하는 건 뭔가요? 상대가 거절하면 어디까지 받아줄 수 있죠?” AI는 문서를 읽었지만 담당자는 협상안을 다시 만들어야 한다.

이 장면 이후 표준 계약서와 협상 플레이북의 차이, 도입 사례, 기술 구성, 첫 적용 범위로 이어가면 좋다.

## 2. 개념: 무엇을 AI에 가르친다는 것인가

### 2.1 기본 용어

| 개념 | 의미 | 현업에서 답하려는 질문 |
|---|---|---|
| 계약 요약 | 당사자·기간·대금·의무 등 주요 내용 정리 | 무슨 계약인가? |
| 조항 추출·분류 | 관련 문구의 위치와 유형 식별 | 해지 조건이 어디에 있는가? |
| 계약 검토 | 문구와 관계 조항을 읽고 기준에 비춰 문제 확인 | 우리 기준에서 무엇을 바꿔야 하나? |
| 협상 플레이북 | 선호 조건·대안·금지 조건·적용 상황·승인 경로를 정리한 내부 지침 | 상대가 거절하면 어떻게 대응하나? |
| 조항 라이브러리 | 승인된 문구와 사용 조건의 모음 | 어떤 문구로 고칠까? |
| 레드라인 | 삭제·삽입 등 변경 사항을 드러낸 수정안 | 원문에서 정확히 무엇이 달라졌나? |
| CLM | 작성·검토·협상·승인·서명·보관·이행을 관리하는 계약 생애주기 관리 | 계약이 지금 어디까지 진행됐나? |

Ironclad는 플레이북에서 선호 문구와 대안 문구를 제시하고, 비표준 조항을 관련 부서의 승인으로 연결하는 기능을 설명한다. 플레이북을 읽고 수정할 권한도 구분한다. ‘회사 기준’이 설명문에만 머무르지 않고 검토·승인 흐름에 들어가는 예다. [S1]

### 2.2 표준 계약서만 넣으면 충분하지 않은 이유

표준 계약서는 회사가 처음 제안하고 싶은 문구를 담을 수 있지만, 상대방이 수정했을 때의 모든 대응까지 설명하지는 않는다. 과거 체결본도 그 거래에서 최종 합의한 결과이지 현재의 일반 정책과 같지는 않다.

따라서 자료를 다음처럼 나누는 구성이 유용하다. 아래는 본 문서의 설계 제안이다.

- **공식 기준:** 현재 유효한 정책, 표준 조항, 승인된 협상 지침.
- **조건부 대안:** 특정 거래 조건에서 허용하는 변경과 승인 요건.
- **사례:** 과거 제안·수정·최종 합의 및 당시 판단 이유.
- **일회성 예외:** 특정 거래에서만 승인한 양보. 일반 기준으로 자동 승격하지 않는다.
- **폐기 자료:** 더 이상 적용하지 않을 문구와 그 시점.

### 2.3 ‘가르친다’와 ‘모델을 재학습한다’는 같은 말이 아니다

| 방법 | 담당 역할 | 적용 시 판단 |
|---|---|---|
| 지시·템플릿 | 검토 순서와 결과 형식을 정함 | 반복 절차를 명확히 할 때 |
| 검색·컨텍스트 제공 | 현재 정책과 관련 선례를 찾아 제시 | 근거의 최신성·접근권한이 중요할 때 |
| 구조화된 규칙 | 거래 조건에 따른 분기와 승인 요건 표현 | 누가 언제 무엇을 허용하는지 명확할 때 |
| 도구·업무 연결 | 문서 비교, 수정안 작성, 결재 요청, 결과 기록 | 검토를 실제 협상 업무로 연결할 때 |
| 모델 튜닝 | 특정 분류·추출·표현 과업의 성능 개선 | 평가 데이터로 필요성과 개선 효과를 확인한 경우 |

위 표는 구성 선택을 위한 정리다. 특정 공급사가 이 방법을 전부 쓰거나 같은 방식으로 구현한다는 뜻은 아니다. 제품에서 말하는 ‘학습’도 지침 갱신, 예시 추가, 검색 자료 보강, 모델 파라미터 변경 중 무엇인지 확인해야 한다.

## 3. 플레이북을 만드는 실무 방법

아래는 공개 기능 설명을 참고해 구성한 **도입 설계 제안**이다. 실제 기업의 정책이나 보편적인 법률 기준이 아니다.

### 3.1 계약 유형 하나부터 고른다

계약 건수가 충분하고 반복되는 쟁점이 있는 유형을 고른다. NDA, 소프트웨어 구매, 용역 계약 등이 후보지만 단순히 짧은 문서라는 이유로 저위험이라고 판단하지 않는다. 우리 회사가 구매자인지 공급자인지도 함께 구분한다.

### 3.2 자료와 판단 이유를 함께 모은다

최신 표준서, 상대방 수정본, 최종 체결본, 협상 이메일, 예외 승인 기록을 같은 거래 단위로 연결한다. 담당자에게는 “이 조항이 왜 나쁜가요?”만 묻지 말고 다음을 확인한다.

- 처음 제안한 조건과 실제 합의한 조건은 무엇이 달랐는가?
- 무엇을 얻는 대신 무엇을 양보했는가?
- 이번 거래에만 적용한 예외는 무엇인가?
- 누가 어떤 근거로 승인했는가?
- 비슷해 보여도 같은 기준을 쓰면 안 되는 거래는 무엇인가?

Harvey의 2026-08-04 Playbook Builder 발표는 기존 문서와 지침에서 규칙 초안을 만들고, 확인 질문을 통해 기준을 정리하는 기능을 소개한다. 과거 계약에서 벗어난 조건을 찾아 확인하도록 하는 설명도 있다. 이는 기준 작성 지원 기능이지, 담당자 확인 없이 과거 체결본을 정책으로 확정한다는 뜻이 아니다. [S2]

### 3.3 규칙 한 개에 담을 항목

| 항목 | 기록할 내용 |
|---|---|
| 적용 대상 | 계약 유형, 우리 측 역할, 사업부, 언어, 적용 지역 |
| 확인 쟁점 | 어떤 조항 또는 의무를 확인할 것인가 |
| 기본 입장 | 우선 제안할 조건과 승인된 문구 |
| 대안 | 어떤 전제에서 어느 조건까지 검토할 수 있는가 |
| 예외·금지 | 자동 통과시키면 안 되는 조건 |
| 누락 처리 | 반드시 있어야 하는 조항인지, 없으면 질문할지 |
| 판단 근거 | 정책 문서, 관련 조항, 승인된 선례 |
| 담당자 | 기준 소유자와 예외 승인자 |
| 변경 관리 | 버전, 시행일, 종료일, 변경 사유 |

### 3.4 가상 예시: 대금 지급 조건

사내 기준을 ‘지급기일이 길면 위험’이라고만 쓰면 AI는 무엇을 제안해야 할지 알기 어렵다. 대신 ‘어떤 사건을 지급기일의 시작으로 보는가’, ‘검수 지연 시 어떻게 처리하는가’, ‘예외를 어느 부서에서 승인하는가’를 따로 정리한다.

예시 결과 형식:

> 검토 쟁점: 지급기일의 시작 조건이 불명확함.  
> 근거: 본문 지급 조항과 별첨 검수 절차.  
> 필요한 확인: 검수 완료 시점을 누가 확정하는가?  
> 제안: 승인된 기준 문구를 바탕으로 시작 조건을 명확히 하는 수정안 작성.  
> 후속 처리: 재무·사업 담당자가 조건과 이행 가능성을 확인한 뒤 외부 전달.

구체적인 일수나 책임 한도를 일반 정답처럼 제시하지 않는다. 독자에게 보여줄 핵심은 숫자가 아니라 **조건·근거·승인자를 빠뜨리지 않는 규칙의 형태**다.

## 4. 기술: 검토 AI의 실제 구성

### 4.1 참고 구현 흐름

아래는 특정 제품의 내부 구조를 단정한 것이 아닌 권장 설계안이다.

`접수·버전 확정 → 문서 구조 추출 → 거래 맥락 확인 → 적용 플레이북 선택 → 조항·별첨 검토 → 수정안 생성 → 일관성 검사 → 담당자 승인 → 전달·이력 저장`

1. **접수:** 계약 ID와 문서 버전을 부여하고 본문·별첨·변경계약을 묶는다. 상대방이 새 버전을 보내면 이전 승인과의 관계를 확인한다.
2. **파싱:** 조항 번호, 정의, 표, 각주, 참조 관계, 문서상의 위치를 보존한다. 스캔본은 OCR 품질도 확인한다. Microsoft의 Layout 모델은 문단·표·제목 등 구조 추출을 지원하지만, 추출 지원 자체가 계약 의미의 정확성을 보장하지는 않는다. [S3]
3. **맥락 입력:** 구매/판매 입장, 거래 대상, 관련 서비스, 중요 조건 등을 확인한다. 확인되지 않은 정보를 AI가 임의로 채우지 않게 한다.
4. **자료 검색:** 현재 정책을 먼저 식별하고 권한 내 선례를 찾는다. 문자열이 비슷한 계약만 찾지 말고 계약 유형과 거래 조건으로 범위를 좁힌다.
5. **검토:** 조항 존재 여부, 기준 부합 여부, 예외 적용 여부를 구분한다. 정의와 별첨 때문에 의미가 달라지면 해당 구간까지 확인한다.
6. **수정:** 원문의 어느 부분을 어떤 이유로 바꾸는지 연결한다. 전체 조항을 무조건 다시 쓰기보다 필요한 수정 범위를 통제한다.
7. **통합 검증:** 서로 다른 쟁점의 수정안이 충돌하는지, 정의가 깨졌는지, 다른 문서 버전에 수정했는지 검사한다.
8. **승인·전달:** 내부 검토 완료와 상대방에게 보내도 되는 상태를 구분한다. 서명 권한은 별도로 둔다.

### 4.2 공개된 실제 아키텍처: Harvey Playbook Review

2026-09-02 기술 글에서 Harvey는 규칙별 검토를 여러 에이전트에 나누고 총괄 에이전트가 결과를 조정하는 구조를 설명한다. 각 에이전트는 필요하면 관련 별첨을 읽으며, 문서 요소의 ID를 이용해 근거와 수정 위치를 지정한다. 별도 문서 분기에서 만든 수정안을 병합하고 충돌을 해결한다. [S4]

같은 글에서 공개한 기존 방식의 문제는 과도한 수정, 누락, 잘못된 수정 위치, 규칙별 수정안 충돌이었다. 평가에서는 위험 분류와 수정안 품질을 나누고 법무팀의 기준을 사용했다. 운영상으로는 동시 실행 수 제한, 부분 재시도, 캐싱 등을 적용했다. 이는 공급사의 구현 설명이며 독립적인 성능 검증 결과는 아니다. [S4]

경영진에게 전달할 기술적 의미: **AI를 여러 개 붙이는 것보다, 같은 문서를 고치는 작업들의 충돌을 통제하고 결과를 평가하는 설계가 중요하다.** 작은 실증은 단순한 순차 검토로 시작하고 실제 품질·지연·비용을 보고 복잡도를 늘릴 수 있다.

### 4.3 구현 데이터의 최소 형태 — 제안

```text
review_id / contract_id / document_version
playbook_id / playbook_version / effective_date
represented_party / contract_type / deal_context
rule_id / clause_ids / evidence_locations
status: compliant | deviation | missing | needs_information
proposed_change / business_reason / policy_reference
required_approver / approval_state
reviewer_decision / rejection_reason / final_outcome
```

이 구조는 모델이 쓰는 장문의 내부 추론을 저장하자는 제안이 아니다. 사람이 검증할 수 있는 원문 위치, 적용 규칙, 판단 요약, 수정 내용과 승인 이력을 남기자는 뜻이다.

## 5. 산업 현장 도입 사례

### 5.1 Carvana — 개별 변호사의 작성·검토 방식을 플레이북으로

- **출처 성격:** Harvey가 공개한 고객 사례. 고객 발언과 공급사 정리이며 독립 실험은 아니다. 페이지 게시일은 명시적으로 확인하지 못했으며 조사일에 열람했다.
- **문제:** 사업 확장과 함께 계약·금융·제품 관련 법무 업무가 늘고, 문서와 지식이 분산돼 있었다.
- **적용:** 법무팀 내 여러 역할이 참여해 도입했다. 19명 파일럿에서 법무 및 관련 조직 70명 이상으로 확장했으며, 26개 템플릿을 플레이북으로 바꿨다고 설명한다.
- **공개 성과:** 한 플레이북에서 시작한 작성·검토 시간 80% 감소를 소개한다. 업무별 표에서는 작성 시간으로 표현하므로 집필 시 측정 범위를 함께 적거나 숫자를 생략한다.
- **포스트 활용:** 과거 문서와 검토 논리를 재사용 가능한 기준으로 묶은 사례. 80%를 계약 체결 전체 기간이나 법무 인력 감소로 바꾸어 쓰지 않는다. [S5]

### 5.2 Benjamin Moore — 법무·구매·영업이 같은 계약 흐름에서 일하도록

- **출처 성격:** Ironclad 고객 사례, 실제 담당자 인터뷰. 게시일은 명시적으로 확인하지 못했다.
- **문제:** 부서별 시스템과 공유 드라이브가 흩어져 계약 만료·자동 갱신·승인 경로를 파악하기 어려웠다.
- **도입 순서:** NDA에서 시작해 간접구매, 판매 계약으로 넓혔다. 계약 규모에 따라 승인 흐름을 다르게 구성했다.
- **확인되는 활용:** 승인 경로와 판단 이력을 모으고 AI 플레이북, 조항 라이브러리, Jurist를 사용한다. 영어·프랑스어 번역 결과를 기존 번역 서비스의 결과와 대조한 설명도 있다.
- **포스트 활용:** AI 검토 결과가 실제 승인·협업으로 이어져야 한다는 사례. 시스템 통합 효과를 모두 생성형 AI 단독 성과로 돌리지 않는다. [S6]

### 5.3 Allen & Overy의 ContractMatrix — 전문 판단을 Word 업무 안에 연결

- **날짜·맥락:** 2023-12-21 당시 Allen & Overy 발표. 현재 A&O Shearman 사이트에 보존돼 있다.
- **적용:** Microsoft·Harvey와 만든 계약 작성·협상 도구로, 웹 또는 Word 추가 기능 형태와 Azure 기반 구성을 설명했다.
- **당시 상태:** 내부 변호사 1,000명 이상이 사용 중이라고 밝혔다. 대형 고객 5곳의 다음 해 1월 출시 합의는 당시 계획으로 구분한다.
- **공개 수치:** 일부 계약 협상에서 약 7시간을 아꼈다고 발표했다. 평균이나 보장 성과로 사용하지 않는다.
- **포스트 활용:** 전문가가 도구의 시험·개선에 참여하고 검증된 선례를 활용한 사례. 최신 이용자 수로 인용하지 않는다. [S7]

### 5.4 국내 참고: BHSN의 기업 리걸 솔루션

2024-02-21 BHSN 공식 보도자료는 CJ제일제당·SK텔레콤에 자체 AI 리걸 솔루션을 제공했다고 밝히고, 당시 Allibee를 CLM·ELM으로 소개한다. 국내 기업의 계약·법무 업무 적용이 존재한다는 근거로 활용할 수 있다. [S8]

다만 이 발표만으로 해당 고객이 현재의 협상 플레이북이나 자동 수정 기능을 어떻게 썼는지, 어떤 성과를 냈는지는 확인할 수 없다. 국내 사례를 억지로 중심에 놓지 말고 짧은 참고로 쓰거나 본문에서는 생략한다. 추가 인터뷰에서 도입 범위, 한국어 문서 처리, 승인 연결, 운영 성과를 확보하면 보강한다.

## 6. 최신 제품 방향과 실제 사례의 구분

Harvey는 2026-09-10 Contract Review Agents를 발표했다. 과거 계약·지침을 활용하고 인터뷰로 문서에 없는 판단을 확인하며, 최근 합의와 기존 기준의 차이를 찾아 기준 갱신을 제안하는 방향이다. 발표문은 **early access 대기 명단**을 안내한다. 따라서 Carvana의 기존 도입 성과를 이 신제품의 성과로 연결하지 않는다. [S9]

Icertis의 Playbook Review 자료는 Harvey를 이용한 기준 대조, 수용 가능·추가 검토·수용 불가 분류, 조항 참조와 검토 기록 저장을 설명한다. 이는 구성 요소를 설명할 제품 기능 근거이며 별도의 고객 실적은 아니다. [S10]

집필 우선순위: Carvana의 기준 재사용 → Benjamin Moore의 부서 간 운영 → 필요한 곳에 기술 설명. 최신 제품은 변화 방향을 보여줄 때만 짧게 넣는다.

## 7. 실패할 수 있는 지점과 검증 항목

아래는 실제 사건 목록이 아니라 **설계·시험용 실패 시나리오**다. 제품팀이 공개한 문제는 4.2절에서 별도 표시했다.

| 실패 시나리오 | 업무상 문제 | 확인·개선 방법 |
|---|---|---|
| 공급자용 기준으로 구매 계약 검토 | 상대편에 유리한 수정안 | 당사자 역할을 필수 입력·검증 |
| 예전의 일회성 양보를 기본값으로 사용 | 승인되지 않은 조건 반복 | 선례와 현행 정책, 예외를 구분 |
| 본문만 읽고 별첨·정의 누락 | 잘못된 위험 판단 | 참조 문서 존재와 확인 여부 검사 |
| 필요한 조항이 없는데 통과 | 검색에 잡힌 문구만 검사한 오류 | 필수 항목의 누락을 별도 평가 |
| 모든 문장을 표준서대로 변경 | 불필요한 협상 왕복 증가 | 필수 수정과 표현 선호 구분 |
| 여러 수정안이 같은 문구를 덮어씀 | 모순·정의 불일치 | 수정안 병합 후 전체 재검증 |
| 내부 협상 하한을 외부 댓글에 포함 | 협상 정보 유출 | 내부 사유와 상대방 전달 문안 분리 |
| 담당자가 고친 내용을 즉시 정책화 | 잘못된 피드백의 전사 확산 | 수정 사유 수집 후 기준 소유자 승인 |
| 승인 후 다른 버전 전달 | 승인하지 않은 계약이 상대방에게 감 | 문서 버전과 승인 대상 묶기 |

### 7.1 공개 연구에서 가져올 평가 관점

- **CUAD, 2021:** 전문가가 계약의 중요한 검토 구간을 표시한 13,000개 이상의 주석을 제공한다. 관련 문구를 찾는 과업의 평가 출발점이다. 회사의 양보 기준이나 협상 완료까지 평가하는 자료는 아니다. [S11]
- **ContractNLI, 2021:** 607개 계약에 대해 주어진 명제가 계약에서 성립하는지, 모순되는지, 언급되지 않는지를 분류하고 근거 구간을 찾는 과업이다. 단서·예외와 긴 문서의 어려움을 다룬다. [S12]

두 연구의 과거 모델 성능을 현재 상용 모델의 성능처럼 쓰지 않는다. 한국어 계약과 자사 정책 검증은 별도로 필요하다.

### 7.2 자사 평가 세트 — 제안

정상 계약뿐 아니라 누락 조항, 서로 다른 정의, 수정된 별첨, 폐기 정책, 일회성 예외, 양 당사자 역할 전환, 한영 병기 불일치, OCR 오류를 넣는다. 정답 문구 하나만 만들기보다 허용 가능한 수정 범위와 반드시 승인받을 조건을 기록한다.

성과 지표는 다음처럼 나눈다.

- **탐지:** 중요한 이탈을 놓친 비율, 문제없는 조항을 잘못 표시한 비율.
- **근거:** 실제 원문·현재 정책을 올바르게 연결했는가.
- **수정:** 취지를 보존하면서 필요한 변경을 정확한 위치에 했는가.
- **운영:** 검토자 재작업 시간, 불필요한 수정 제안, 승인 대기, 협상 왕복.
- **통제:** 승인 누락, 버전 불일치, 권한 밖 정보 노출.

시간 절감은 AI 응답 시간과 사람의 검토 시간을 나눠 잰다. 계약 체결 기간은 상대방의 응답 등에도 영향을 받으므로 내부 검토 시간과 별도로 기록한다.

## 8. 보안과 권한: 계약 검토에 직접 필요한 내용

상대방 계약서는 검토 대상 데이터이지 시스템 명령이 아니다. 문서 속에 AI를 조종하는 지시가 들어갈 가능성을 고려해야 한다. OWASP의 프롬프트 인젝션 예방 지침과 과도한 권한 위험을 참고하면, 문서 분석과 외부 실행 권한을 분리할 필요가 있다. [S13][S14]

실무 적용 제안:

- 계약별 열람권한을 검색 단계에서 적용하고 사업부·고객 간 자료 접근을 통제한다.
- 협상 하한, 내부 법무 의견, 상대방 전달용 설명을 따로 관리한다.
- 계약서 내 지시로 검색 범위나 발송 대상이 바뀌지 않도록 도구 권한을 제한한다.
- 수정안 작성, 이메일 발송, 전자서명을 서로 다른 권한과 승인 단계로 둔다.
- 외부 서비스의 보관·삭제·학습 이용 조건, 처리 지역과 재위탁 범위를 계약으로 확인한다.
- 로그·검색 색인·백업에도 민감한 문구가 남을 수 있으므로 동일한 보관 정책을 적용한다.
- 한국 법률에 관한 구체 판단은 담당 법무 전문가가 확인한다. 이번 글은 특정 조항의 효력이나 합법성을 판정하는 법률 해설로 확장하지 않는다.

## 9. 도입 방식과 첫 실증 범위 — 편집·구현 제안

| 방식 | 장점 | 확인할 부담 |
|---|---|---|
| 기존 CLM의 AI 기능 | 승인·계약 이력과 연결하기 쉬움 | 현재 제품·요금에서 지원하는 범위, 기존 데이터 품질 |
| 법무 특화 AI | 계약 검토 UI와 전문 업무 기능 활용 | 자사 기준 표현력, 문서 수정 정확성, 다른 시스템 연동 |
| 범용 에이전트 기반 구성 | 사내 절차·도구에 맞춰 구성 가능 | 파싱·수정·평가·권한·버전 통제를 직접 설계 |

첫 실증은 계약 유형 하나와 담당 부서를 정하고, 실제 검토본을 이용해 사람과 AI 결과를 비교한다. 외부 발송은 자동화하지 않은 채 시작할 수 있다. 실증 통과 뒤에도 어떤 유형과 조건까지 맡길지 범위를 명시한다.

역할 분담: 법무는 기준과 해석, 영업·구매는 거래 맥락과 협상 가능성, 재무·보안·운영은 소관 예외, 개발·AX팀은 연결·평가·권한·운영 기록을 맡는다. 기준의 최종 소유자를 분명히 해야 업데이트가 멈추지 않는다.

## 10. 집필안 및 기존 포스트와의 연결

1. **들어가며:** 수정 의견은 많지만 협상은 다시 시작하는 가상 장면. 읽고 나면 우리 회사가 먼저 정리할 기준과 도입 범위를 알 수 있다고 안내.
2. **AI가 계약을 읽는 것과 우리 편에서 검토하는 것:** 당사자 역할·사업 조건·플레이북을 설명.
3. **계약서를 모으기 전에, 양보한 이유부터:** 가상 지급 조건 예시로 기준 구조 소개.
4. **실제 기업은 무엇을 바꿨나:** Carvana와 Benjamin Moore를 서로 다른 도입 문제의 사례로 사용.
5. **수정안 뒤에서 필요한 기술:** 별첨 검색·근거 위치·수정 충돌·승인을 설명. 아키텍처 이름 나열보다 현업 오류와 연결.
6. **어떤 계약부터 맡길까:** 한 유형의 실증, 중요한 누락과 재작업을 보는 평가.
7. **나가며:** 숙련자의 협상 판단을 기준·사례·검증으로 남기는 일이 암묵지 자산화임을 정리하고 도입 지원으로 연결.

연결할 기존 주제: 암묵지 자산화, Agent Skills, AI Evals, AI 결재선, MCP. 모두 길게 재설명하지 않고 해당 문맥에서 필요한 링크만 사용한다.

CTA 방향: ‘법률 판단을 대신해준다’가 아니라 **현업·법무와 함께 검토 기준을 정리하고 계약 문서·승인 시스템·평가를 연결하는 구현과 운영을 돕는다**로 잡는다. 연락처는 `contact@epsilondelta.ai`.
