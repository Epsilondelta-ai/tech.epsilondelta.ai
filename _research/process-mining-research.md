## 1. 핵심 결론과 포스팅 관점

**AI가 한 작업을 빨리 끝내더라도, 고객이 기다리는 전체 시간은 다른 단계의 대기·반려·인계 때문에 그대로일 수 있다.** 프로세스 마이닝은 시스템에 남은 사건 기록으로 실제 업무 경로와 소요 시간을 분석해, 어디부터 바꿀지 판단하는 데 쓰인다. 학술적으로는 프로세스 발견·적합성 검사·개선이 주요 축이다. [S1][S2]

이 글의 핵심 질문은 “AI를 어디에 더 넣을까?”보다 “고객 건이 어디에서 멈추고, 그 이유를 어떤 기록으로 확인할 수 있을까?”다. 프로세스 마이닝은 생성형 AI의 다른 이름이 아니다. 로그 분석으로 개선 지점을 찾고, 필요에 따라 규칙 변경·기준정보 수정·자동화·AI 에이전트를 적용한다.

편집상 가장 적합한 조합:

1. **Hexion:** 고객이 기다리는 출하 지연을 설명하는 주 사례.
2. **Cosentino:** 발견한 병목에 AI 에이전트를 적용한 연결 사례.
3. **Microsoft MCAPS 또는 GWF:** 제조·물류 밖의 검토·재무 업무로 확장하는 보조 사례.

Siemens·DSM까지 모두 본문에 나열할 필요는 없다. 사례마다 다른 논점을 맡기고, 같은 신용 보류 이야기를 반복하는 사례는 선택해 사용한다.

## 2. 개념: 매뉴얼에 적힌 순서와 실제로 거친 순서

### 2.1 기본 용어

| 용어 | 의미 | 가상의 견적 업무 예시 |
|---|---|---|
| Case / 프로세스 인스턴스 | 분석할 업무 한 건 | 견적 요청 Q-101 |
| Event / 이벤트 | 기록된 사건 하나 | Q-101의 승인 요청 접수 |
| Activity / 활동 | 사건이 나타내는 업무 단계 | 견적 작성, 검토, 승인, 발송 |
| Trace / 실행 이력 | 한 건에서 기록된 사건의 순서 | 접수→작성→검토→수정→검토→승인→발송 |
| Variant / 경로 유형 | 같은 활동 순서를 가진 이력의 묶음 | 한 번에 승인된 경로, 두 번 반려된 경로 |
| Process model / 프로세스 모델 | 업무의 순서·분기 등을 표현한 모델 | 승인 후 발송하도록 설계한 흐름 |

정의 근거: IEEE 자료와 Microsoft 로그 문서. 예시는 설명용 구성이다. [S1][S2][S3]

### 2.2 세 가지 주요 기능

- **발견(Discovery):** 실제 기록에서 업무 경로를 찾는다.
- **적합성 검사(Conformance checking):** 정해진 모델·규칙과 실제 이력을 비교한다. 승인 전 발송, 필수 검사 누락 같은 일탈을 확인하는 용도로 설계할 수 있다.
- **개선(Enhancement):** 기록을 이용해 모델을 보완하거나 시간·자원 등의 정보를 덧붙여 개선을 돕는다. [S2]

### 2.3 주변 기술과의 차이

| 구분 | 주요 질문 | 이 글에서의 역할 |
|---|---|---|
| 업무 인터뷰·매뉴얼 | 원래 어떻게 해야 하고 왜 그렇게 하는가? | 기준과 현장 맥락 확인 |
| BI·성과 대시보드 | 얼마를 처리했고 성과가 어떠한가? | 집계와 경영지표 공유 |
| 프로세스 마이닝 | 각 건이 어떤 경로를 거쳐 어디서 지연됐는가? | 순서·반복·대기 경로 분석 |
| 태스크 마이닝 | 개인이 화면과 앱에서 어떤 작업을 수행하는가? | 시스템 로그 밖의 세부 행동 보완 |
| RPA·워크플로 | 정한 절차를 어떻게 실행할 것인가? | 반복 처리·인계 자동화 |
| AI 에이전트 | 자료 해석·판단·도구 실행을 어떻게 맡길 것인가? | 선택한 업무 단계의 수행 |

태스크 마이닝은 데스크톱 행동을 기록·분석하는 방식이다. 프로세스 마이닝을 하려면 모든 직원의 화면을 녹화해야 한다는 설명은 피한다. [S4] 위 표는 주된 관점의 비교이며, 실제 제품의 기능은 겹칠 수 있다.

## 3. ‘처리 시간’과 ‘고객이 기다린 시간’을 구분하는 방법

### 3.1 도입부용 가상 예시

견적 작성은 30분에서 3분으로 줄었지만, 요청부터 고객 발송까지는 약 사흘이 걸린다. 검토함에서 오래 기다렸거나, 조건 누락으로 반려됐거나, 승인 후 발송이 다음 날로 밀렸을 수 있다.

이 수치는 실제 회사 사례나 평균치가 아니다. **아직 어느 단계가 원인인지 모르는 상태에서 기록을 확인하러 들어가는 장면**으로 사용한다. 처음부터 직원이 늦게 처리했다고 단정하지 않는다.

### 3.2 지표 설계

다음은 현업 적용을 위한 측정 제안이다. SAP 문서의 cycle time도 선택한 사건 사이의 기간을 뜻하므로, 이름보다 시작·끝 정의가 중요하다. [S5]

| 지표 | 정의할 내용 | 주의할 해석 |
|---|---|---|
| 전체 소요 시간 | 고객 요청 접수부터 고객에게 전달할 결과의 완료까지 | 내부 승인 완료와 고객 수신을 구분 |
| 활동 처리 구간 | 해당 활동의 시작부터 종료까지 | 열어둔 작업 시간이 순수 노동 시간과 같지는 않음 |
| 단계 사이 간격 | 앞 활동 종료부터 뒤 활동 시작까지 | 큐 대기·영업시간 밖·고객 회신 대기 등을 구분 |
| 재작업률 | 재검토·재작성 경로를 거친 건의 비율 | 정상적인 반복 협의와 불필요한 반려 구분 |
| 최초 정상 완료율 | 정의한 수정·반려 없이 끝난 건의 비율 | 업무별 제외 조건 명시 |
| SLA 준수율 | 약속한 기한 내 완료한 비율 | 취소·미완료 건 처리 기준 고정 |
| 지연 분포 | 중앙값·P90·장기 미완료 건 | 평균만으로 일부 고객의 긴 지연을 숨기지 않음 |

**이벤트 발생 시각 하나만 있으면 순수 처리 시간과 대기 시간을 정확히 분리하기 어렵다.** 시작·종료 기록, 영업일 달력, 보류 사유와 담당 변경 등을 추가로 확인한다. Microsoft는 단일 시각의 이벤트 로그와 시작·종료 시각을 가진 활동 로그를 구분한다. [S3]

병렬 작업에서는 활동별 시간을 단순 합산하면 전체 경과 시간을 넘을 수 있다. 따라서 ‘전체 시간=모든 처리 시간+모든 대기 시간’이라는 식은 겹치지 않는 순차 구간으로 분해했을 때만 설명용으로 쓴다. 이는 측정 설계상의 판단이다.

대기 원인을 분해하는 연구도 있다. Lashkevich 외 연구는 활동 전환 사이의 대기를 직접적인 원인들로 나누어 분석하는 접근을 제안한다. 단순한 간격 표시에서 원인 분석으로 나아가는 참고 자료이며, 이번 조사에서는 초록 수준의 주장만 활용한다. [S6]

## 4. 기술: 사내 기록을 실제 업무 흐름으로 바꾸는 과정

### 4.1 데이터 준비

전형적인 case-centric 분석에는 **업무 건 식별자, 활동명, 시각**이 필요하다. 담당 부서·보류 사유·금액·채널 등의 속성을 추가하면 경로별 비교가 가능하다. 현재 상태만 담긴 테이블과 상태 변경 이력은 다르므로 감사 로그·이력 테이블을 확인해야 한다. [S3]

아래는 직접 만든 예시이며 실제 고객 데이터가 아니다. 시각은 모두 같은 날짜의 KST이다.

| case_id | activity | timestamp | 부서 |
|---|---|---|---|
| Q-101 | 요청 접수 | 09:00 | 영업 |
| Q-101 | 초안 작성 시작 | 09:02 | 영업 |
| Q-101 | 초안 작성 완료 | 09:05 | 영업 |
| Q-101 | 검토 시작 | 14:00 | 영업관리 |
| Q-101 | 수정 요청 | 14:15 | 영업관리 |
| Q-101 | 수정 완료 | 14:25 | 영업 |
| Q-101 | 승인 완료 | 15:00 | 영업관리 |
| Q-101 | 고객 발송 | 16:00 | 영업 |

이 표에서 초안 작성 구간은 3분, 요청 접수부터 발송까지는 7시간이다. 초안 완료부터 검토 시작까지 4시간 55분의 간격을 확인할 수 있다. 하지만 이 기록만으로 검토자의 실제 근무 상황이나 지연 이유까지 알 수는 없다.

### 4.2 구현 파이프라인 — 설계 제안

1. **분석 단위 결정:** 고객 요청, 주문, 주문 품목, 상담 건 중 무엇을 한 건으로 볼지 정한다.
2. **원천 추출:** ERP·CRM·티켓·승인 시스템의 이력 테이블이나 API에서 필요한 사건을 가져온다.
3. **연결·정규화:** 시스템 간 ID를 맞추고 중복 사건, 재전송, 시간대, 활동 명칭을 정리한다.
4. **기준선 생성:** 정상 경로·반려 경로·미완료 건과 소요 시간 분포를 계산한다.
5. **모델·분석:** 경로 발견, 규칙 적합성, 시간·반복·조건별 차이를 확인한다.
6. **현업 검증:** 표본 업무 건을 원자료와 대조하고, 왜 그런 경로가 생겼는지 담당자와 확인한다.
7. **개선 실행:** 규칙·데이터·권한·담당 배정·알림·AI 적용 중 맞는 수단을 선택한다.
8. **재측정:** 같은 지표 정의로 고객 완료 시간과 오류·재작업을 함께 비교한다.

### 4.3 알고리즘을 어느 정도 설명할 것인가

PM4Py의 공식 저장소와 구현에는 프로세스 발견 및 적합성 검사 기능이 있다. 기술 조사 출발점으로 사용할 수 있다. [S7][S8][S9]

| 기술 | 하는 일 | 경영진에게 설명할 핵심 |
|---|---|---|
| Directly-Follows Graph | 어떤 활동 다음에 어떤 활동이 기록됐는지 연결 | 자주 거치는 경로와 오래 걸리는 연결을 찾는 출발점 |
| Inductive Miner | 이벤트 이력에서 구조화된 프로세스 모델 발견 | 화면에 선을 그리는 것을 넘어 실행 흐름을 모델링 |
| Token replay / Alignments | 관측 이력과 모델의 실행 가능성·차이 비교 | 정한 업무 규칙에서 벗어난 건을 찾아 확인 |

DFG의 화살표는 시간상 인접 관계이지 인과관계의 증명이 아니다. ‘반려 경로가 느리다’와 ‘반려 자체가 지연의 유일한 원인이다’도 다른 판단이다. 난도가 높은 건이 더 자주 반려될 수 있으므로 조건별 비교가 필요하다. 이 문단은 분석 설계 해석이다.

### 4.4 Object-Centric Process Mining과 OCEL 2.0

실무에서는 주문 하나가 여러 배송으로 나뉘고, 청구서 하나가 여러 주문을 포함할 수 있다. 하나의 case ID로 모든 관계를 억지로 펼치면 같은 사건의 중복 집계나 관계 손실이 생길 수 있다. 이런 구조를 다룰 때 객체 중심 분석을 검토한다.

OCEL 2.0은 이벤트와 객체, 객체 간 관계, 관계의 역할, 시간에 따른 객체 속성 변화를 표현하는 로그 형식이다. 주문·배송·청구서를 별도 객체로 유지하고 관련 사건을 연결하는 식으로 설명할 수 있다. **OCEL은 데이터 형식이고, 그 자체가 분석 알고리즘이나 그래프 DB 제품은 아니다.** [S10]

이 주제는 본문 기술 섹션에서 짧게 소개하기 좋다. 모든 프로젝트에 객체 중심 구성이 필요한 것은 아니므로, 견적 한 건처럼 관계가 단순한 예시에는 기본 로그부터 설명한다.

## 5. 실제 기업 도입 사례

아래 수치는 연결한 공급사·기업의 공개 설명이다. 발표에서 확인한 운영 성과와 목표를 구분했다. 각 사례는 이번 주제에 필요한 내용만 추렸다.

### 5.1 Hexion — 주문을 처리했어도 출하까지 오래 걸렸던 이유

- **업무·문제:** 화학 제조업의 주문부터 대금 회수까지 흐름. 주문 변경이 다른 업무에 미치는 영향을 파악하기 어려웠다.
- **분석·조치:** 잘못된 경로 기준정보를 고치고, 출하 지연 위험이 있는 주문의 보류를 알림으로 확인해 선제 대응했다.
- **공개 성과:** 경로 변경 45% 감소. **신용 보류 해제부터 출하까지 약 11일→5일.**
- **글에서 맡길 논점:** 개별 부서의 처리 완료 이후에도 고객을 기다리게 하는 시간이 있다. 해결책에 기준정보 수정과 업무 알림이 포함된다.
- **근거 경계:** 위 6일 단축은 전체 주문 리드타임이나 AI 작성 속도의 수치가 아니다. 생성형 AI 에이전트 성과로 소개하지 않는다.
- **시점:** 페이지에 명확한 발행일 표시는 확인하지 못함. 본문에 2020·2021년 공급망 상황 언급. [S11]

### 5.2 Cosentino — 병목을 찾고 신용 보류 주문에 AI를 적용

- **업무·문제:** 건축용 표면재 주문의 신용 보류. 담당자가 고객 관계·지급 이력·위험을 확인하며 주문이 길게 지연됐다.
- **분석·구현:** 초기 프로세스 발견 후 병목을 선택하고 여러 IT 시스템 데이터를 연결해 AI 에이전트를 배포했다.
- **AI 역할:** 주문별 해제 또는 추가 조사 권고와 근거 제공. 일부는 자동 해제하며, 다른 건은 담당자가 수락·거절한다.
- **공개 성과:** 하루 약 180건 분석, 담당자의 처리량 최소 5배. 페이지 요약에는 주문 사이클 시간 **최대 28일 단축**을 제시한다.
- **글에서 맡길 논점:** 프로세스 분석→AI 적용 과제 선정→업무 데이터 연결→실행·검토라는 AX 흐름.
- **근거 경계:** 최대 28일은 평균이 아니다. 전 주문 완전자율 처리가 아니다. 7주 구축 설명을 일반 도입 기간으로 제시하지 않는다.
- **시점:** 정확한 발행일 미표시. 향후 에이전트 확대 계획과 배포된 신용 보류 업무를 구분한다. [S12]

### 5.3 Microsoft MCAPS — 콘텐츠를 빨리 만들어도 검토가 막히면

- **업무:** 마케팅 수요 창출 과정 분석.
- **방법:** 이벤트 로그 수집, Power Query 변환, 속성 매핑, 프로세스 맵 분석에 Copilot 활용, Power Automate 흐름 구성.
- **관측:** 분석한 구성요소의 평균 기간 약 60일, 경로 5종·활동 33개. 20%의 건에 재작업이 있었으며 검토 반복이 주요 병목이었다.
- **상태:** 전체 일정 **12주→8주**는 발표 당시의 예상 개선 결과다. 실제 달성 수치로 쓰지 않는다.
- **글에서 맡길 논점:** 문서 생성 자체보다 요청 접수·검토·반려 흐름에 개선 여지가 있을 수 있다.
- **발행일:** 2024-04-18. 60일과 12주를 같은 단위·동일 범위의 기준선으로 임의 결합하지 않는다. [S13]

### 5.4 GWF — 구매·재무가 함께 오래된 주문을 정리

- **업무·문제:** 입고됐지만 청구되지 않은 항목(GRNI)과 구매 주문 대사. 스프레드시트 중심으로 분산 관리했다.
- **방법:** SAP Signavio Process Insights를 활용해 가시성을 확보하고 구매·재무·운영의 공동 책임 아래 승인 보류·오래된 해제 전략 등을 조사했다.
- **공개 성과:** 12주간 운전자본 A$850,000 해제, clearing process cycle time 70% 감소. A$53.4m은 식별한 GRNI 가치·개선 기회이지 모두 실현한 절감액이 아니다.
- **글에서 맡길 논점:** 도구의 화면보다 부서 공동 책임과 실제 정리가 중요하다.
- **근거 경계:** 생성형 AI 도입 성과로 표현하지 않는다. 제품은 공개 자료대로 Process Insights라고 쓴다.
- **시점:** URL 경로는 2025/08, 본문에 정확한 날짜 미표시. [S14]

### 5.5 Siemens — 승인 자체를 다시 설계한 보조 사례

- **업무:** 구매·물류 등 여러 업무의 프로세스 분석.
- **조치·성과:** 직접 자재 주문의 불필요한 승인을 찾아 **승인자 수를 절반으로 줄였다**고 공개한다.
- **글에서 맡길 논점:** 결재 요청 문구를 AI로 빨리 쓰는 것 외에, 승인 구조 자체를 개선할 수 있다.
- **근거 경계:** 승인 시간 50% 단축이나 비용 50% 절감으로 바꾸지 않는다. [S15]

### 5.6 DSM — 출하 보류와 주문 수정의 반복을 줄임

- **업무:** Order-to-Cash 개선. 수작업 주문 변경과 신용·출하 보류가 납기에 영향을 줬다.
- **방법:** 회피 가능한 보류를 분석하고 지연 위험 알림과 업무 개선을 적용했다.
- **공개 성과:** 출하 보류 10% 감소, 보류 주문의 기간 수일 단축. 북미 OTIF는 6개월 내 84%→90%, APAC 최초 정상 완료율은 18%→42%로 설명한다.
- **글에서 맡길 논점:** 발송 속도뿐 아니라 재작업 감소와 납기 지표로 확인한다.
- **시점·경계:** 2020년 시작, 본문에 2022년 향후 계획이 등장하는 과거 사례다. 북미·APAC 수치를 전사 성과로 합치지 않는다. [S16]

## 6. 프로세스 마이닝과 AI는 어디에서 결합하는가

### 6.1 공개 자료에서 확인한 결합

- **분석 지원:** Microsoft MCAPS는 Copilot으로 프로세스 맵과 병목을 분석하고 자동화 구성을 연결했다. [S13]
- **업무 실행 지원:** Cosentino는 신용 보류 주문의 분석·권고와 일부 해제에 에이전트를 사용했다. [S12]

### 6.2 우리 조직에 적용할 수 있는 구성 — 설계 제안

| 발견한 현상 | 먼저 확인할 내용 | 가능한 개선 수단 |
|---|---|---|
| 입력 누락으로 반복 반려 | 필수 정보와 누락 시점 | 접수 폼 검증, AI 문서 추출·검사 |
| 담당 배정 전 장기 대기 | 업무 분류·배정 규칙 | 규칙 라우팅, AI 분류, 예외 담당 지정 |
| 여러 시스템을 보며 판단 | 필요한 근거와 최신 상태 | 조회 도구 연결, 근거 요약 에이전트 |
| 단순 건도 여러 단계 승인 | 위험별 승인 필요성 | 승인 기준 재설계, 저위험 건 자동 처리 |
| 승인 후 실행 누락 | 실행 트리거·오류·재시도 | 워크플로 연결, 완료 확인, 중복 실행 방지 |
| 기준정보 오류로 경로 변경 | 원천 정보 소유자와 갱신 방식 | 기준정보 정정과 검증 |

AI가 필요 없는 원인에는 AI를 억지로 넣지 않는다. 자동화 후에는 agent run ID를 업무 건 ID와 연결하고, 도구 호출 성공뿐 아니라 실제 시스템 상태 변경과 고객 완료 사건까지 남기는 구성을 권장한다.

개선 이후 지연이 다른 단계로 옮겨갔는지도 확인한다. 예를 들어 자동 작성량만 증가하고 검토 용량은 그대로라면, 작성 시간 단축과 전체 리드타임 개선은 다르게 나타날 수 있다. 이는 설계상 가설이며 위 기업 사례의 관측 결과로 가장하지 않는다.

## 7. 도입 실패를 줄이기 위한 확인 항목 — 실무 설계 메모

1. **잘못된 분석 단위:** 고객 ID 하나에 여러 주문을 합치지 않았는가? 주문 품목과 주문 전체의 완료 기준은 같은가?
2. **이력 부족:** 현재 상태와 최종 수정 시각만으로 중간 경로를 추정하고 있지 않은가?
3. **시각 오류:** 원천 발생 시각과 수집 시각, 시간대, 일괄 입력, 같은 시각의 사건 순서를 구분했는가?
4. **미완료 건 누락:** 빨리 끝난 건만 집계해 장기 대기 중인 고객을 분석에서 빼지 않았는가?
5. **업무일 기준:** 야간·주말·고객 회신 대기를 내부 처리 지연으로 혼동하지 않았는가?
6. **맵 단순화:** 드문 경로를 숨기면서 중요한 오류·위험 건까지 제외하지 않았는가?
7. **원인 확인:** 통계적 차이를 확인한 뒤 업무 건 표본과 담당자의 설명을 대조했는가?
8. **실행 책임:** 분석 결과를 실제 정책·업무 시스템에 반영할 책임자가 있는가?
9. **전체 성과:** 시간과 함께 오류·반려·고객 불만·수작업 복구·운영비를 보고 있는가?
10. **정보 접근:** 분석 목적에 불필요한 고객·직원 식별정보를 제거하고 열람 범위를 제한했는가?

특히 태스크 마이닝을 추가한다면 화면·행동 수집 범위와 직원 안내, 민감정보 처리 방식부터 별도로 설계해야 한다. 법률 준수 여부를 본 자료만으로 판정하지 않는다.

## 8. 첫 프로젝트를 작게 시작하는 방법

아래는 기업 실적이 아닌 제안이다.

- **질문 하나:** “견적 요청부터 고객 발송까지 왜 오래 걸리는가?”처럼 시작·끝이 명확한 업무를 고른다.
- **표본 대조:** 정상·반려·취소·장기 미완료 건을 포함해 시스템 이력과 현업 설명을 맞춘다.
- **기준선:** 분석 기간, 건수, 계절성, 업무 복잡도, 평균·중앙값·P90, SLA와 재작업을 기록한다.
- **개선 하나:** 가장 영향이 크고 실행 가능한 병목 하나를 선택한다.
- **시험:** 가능하면 비교 집단 또는 단계적 적용을 두고, 적용 전후 주문량·인력·정책 변화도 함께 기록한다.
- **운영:** 담당자, 데이터 갱신 주기, 예외 처리와 변경 이력을 남긴다.

필요한 산출물은 화려한 프로세스 맵 한 장이 아니라, 이벤트 정의서·검증된 기준선·우선순위가 있는 개선 과제·실행 책임·재측정 결과다.

## 9. 포스팅 구성 제안

5. AI를 넣을 곳과 절차부터 고칠 곳 — 원인별 개선 수단.
6. 빨라졌는지는 고객의 시계로 확인한다 — 재작업·SLA·장기 대기와 재측정.
