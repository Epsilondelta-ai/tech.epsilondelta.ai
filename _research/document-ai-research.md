조사일: 2026-09-23 (KST)

- 주제: 견적서는 제대로 줬는데, AI는 왜 다른 금액을 보고할까?
- 백로그: `_research/ax-topic-backlog-100.md` 023번.
- 독자: AI·AX에 관심 있는 경영진, 구매·재무·보험·운영 책임자.
- 범위: 문서의 문자·구조·의미 추출, 업무 데이터로의 변환, 검증·사람 검토·시스템 반영, 실제 도입 사례.
- 공개 공식 문서·기업 사례·연구 자료를 조사했다. 제품 실행, 고객 인터뷰, 벤치마크 재현은 수행하지 않았다.

## 1. 핵심 결론

**문서에 적힌 숫자를 읽는 것과 그 숫자가 어떤 품목·단위·조건에 해당하는지 판단하는 것은 서로 다른 과제다.** 문서 이해 AI를 도입할 때는 글자 인식에서 끝내지 않고 표의 행·열, 머리글, 각주, 원문 위치를 보존한 채 업무 항목을 추출하고 검증해야 한다.

Document AI는 특정 회사 제품만을 가리키지 않는다. Microsoft Research는 업무 문서를 자동으로 읽고 이해·분석하는 기술 영역으로 설명한다. Google Cloud의 Document AI는 같은 표현을 제품명으로도 사용한다. [S1][S2]

이번 글의 추천 관점은 ‘더 똑똑한 AI를 고르는 법’보다 **‘우리 회사가 받은 문서를 실제 판단과 입력에 쓸 수 있는 데이터로 만드는 법’**이다. 구매 협상 글의 앞 단계와 연결되지만 재무·보험 등 다른 업무 사례로 독자층을 넓힐 수 있다.

## 2. 개념 구분

| 개념 | 하는 일 | 확인할 질문 |
|---|---|---|
| OCR | 이미지 속 글자를 기계가 읽을 수 있는 텍스트로 인식 | 8과 3, 소수점, 음수 기호를 제대로 읽었나? |
| 레이아웃 분석 | 본문·제목·표·그림·읽기 순서 등 구조 파악 | 어떤 머리글이 어떤 셀에 적용되나? |
| 표 구조 인식 | 행·열·병합 셀·표 머리글의 관계 복원 | 단가와 수량을 같은 품목 행에 연결했나? |
| 항목 추출 | 문서 내용을 공급사·금액·통화·납기 같은 필드로 변환 | 공급가액과 청구 총액을 구분했나? |
| 정규화 | 날짜·통화·단위 등의 표현을 일정한 형식으로 변환 | 원문과 변환값을 함께 보존했나? |
| 업무 검증 | 계산, 기준정보, 계약·발주 내역과 대조 | 숫자를 읽었더라도 이 거래에 적용할 수 있나? |
| IDP | 분류·추출·검토·업무 반영까지 포함하는 지능형 문서 처리 | 사람이 어디에서 개입하고 무엇으로 완료를 판단하나? |
| 문서 RAG | 필요한 문서 구간을 검색해 답변 생성에 사용 | 답변에 필요한 표·단위·각주를 함께 가져왔나? |

기능을 설명하기 위한 구분이다. 실제 제품에서는 OCR·레이아웃·항목 추출을 함께 제공하기도 한다. Azure의 Layout 모델은 텍스트·표·선택 표시·문서 구조를 추출한다. [S3]

## 3. 견적서에서 벌어질 수 있는 오류

### 3.1 도입부로 쓸 가상 예시

같은 규격의 포장재를 비교하며 운송비·세금 등 다른 조건은 같다고 가정한다.

| 공급사 | 견적서 표시 가격 | 표시 단위 | 개당 환산 가격 |
|---|---:|---|---:|
| A | 9,800원 | 개 | 9,800원 |
| B | 90,000원 | 박스, 10개입 | 9,000원 |

AI가 9,800과 90,000을 정확하게 읽고도 단위를 놓치면 A가 저렴하다고 보고할 수 있다. 실제로는 B의 개당 가격이 낮다. ‘숫자를 잘못 읽었다’와 ‘비교 기준을 잘못 잡았다’를 같은 예시 안에서 구분할 수 있다.

10개입이라는 정보가 별도 각주에 있다면 가격 셀만 추출해서는 환산할 수 없다. 원문에도 포장 수량이 없다면 추측하지 않고 확인 요청을 해야 한다. 이 예시는 특정 제품의 실제 실패 사례가 아니다.

### 3.2 실패 유형과 확인할 방법 — 자체 테스트 설계

| 유형 | 가상 상황 | 확인 방법 |
|---|---|---|
| 문자 인식 | 8,000을 3,000으로 인식 | 원문 영역 확대·재인식·검토 |
| 열 연결 | 단가와 공급가액 열을 뒤바꿈 | 머리글·열 위치·행 관계 검증 |
| 단위 누락 | 박스 가격을 개당 가격으로 비교 | 포장 수량과 가격 기준 단위 확인 |
| 머리글 범위 | ‘단위: 천원’을 누락 | 표·페이지 단위 메타데이터 연결 |
| 각주 누락 | ‘운송비 별도’ 조건을 제외 | 각주를 해당 품목·가격에 연결 |
| 페이지 경계 | 다음 페이지의 표를 새 표로 잘못 처리 | 이어지는 머리글·품목·소계 검증 |
| 병합 셀 | 공통 품목명을 일부 행에만 적용 | 셀의 적용 범위 복원 |
| 소계 중복 | 상세 금액과 소계를 모두 더함 | 행 유형 분리, 계산 대상으로 쓸 행 지정 |
| 문서 유형 | 감액 문서를 일반 청구로 처리 | 송장·크레딧 메모 분류 |
| 수정 이력 | 취소선의 옛 금액을 채택 | 수정표시와 최신 문서 버전 확인 |
| 데이터 연결 | 이름이 비슷한 다른 공급사에 입력 | 승인된 공급사 기준정보와 대조 |

위 항목은 발생 가능한 오류를 시험하기 위한 제안이다. 제품별 발생률이나 우열을 측정한 결과가 아니다.

## 4. 산업 현장의 실제 도입 사례

### 4.1 FibroGen — 송장 추출을 SAP 업무에 연결

Google Cloud와 FibroGen 담당자가 공동 작성한 2024-03-13 사례에 따르면, FibroGen은 월 약 1,000건의 송장을 받았고 2명의 매입채무 담당자가 건당 평균 5분씩 처리했다. Document AI Invoice Parser와 Cloud Functions, SAP Cloud Integration을 연결하고 기준에 미달하는 송장은 사람이 검토하도록 구성했다. 설계부터 운영 배포까지 3개월 미만이 걸렸다고 설명한다. [S4]

초기에는 직원이 이메일의 송장을 저장소에 올렸으며 이 부분의 자동화는 후속 계획이었다. 월 150달러 운영비와 40배 ROI는 해당 글의 추정치다. 업무 전체 무인화나 검증된 일반 ROI로 소개하지 않는다.

**편집 포인트:** AI가 필드를 추출한 뒤 업무 규칙으로 검사하고 SAP에 넣는 과정까지 보여줄 수 있다. 작은 현업 팀과 외부 구축 파트너의 협업도 이번 블로그의 상담 주제와 연결하기 좋다.

### 4.2 Anthem — 보험 청구 서류를 처리 가능한 데이터로

AWS가 공개한 Anthem 사례에서는 청구 한 건에서 정보를 수작업으로 추출하는 데 평균 20분이 걸렸다고 한다. 의료기관이 포털에 제출한 문서를 저장하고 Textract 기반 처리 과정에서 정보를 추출·분류한 뒤 담당자가 사용할 수 있도록 했다. 공개 성과는 청구 처리 워크플로의 80% 자동화이며, 90% 이상은 목표로 제시한다. [S5]

80%를 문자 인식 정확도나 지급 심사 자동 승인율로 바꾸어 쓰지 않는다. 사례 페이지의 게시일은 명확히 확인하지 못했다. 당시 자료의 기업명인 Anthem으로 표기하고, 현재 AWS 고객 페이지에는 Elevance Health 이름으로 유사한 흐름이 소개됨을 집필 메모로 남긴다. [S6]

**편집 포인트:** 문서를 사람이 읽을 수 있다는 사실과 시스템이 업무 데이터로 활용할 수 있다는 사실의 차이를 설명한다. 의학적 판단이나 지급 결정의 자동화 성과로 확대하지 않는다.

### 4.3 Symbeo — 입력·처리 시간을 줄이는 문서 자동화

AWS 고객 페이지에 실린 Symbeo 담당자의 설명은 청구 처리의 데이터 수집 자동화를 다룬다. 누적 1,600만 페이지 이상을 처리했으며 문서 처리 시간은 3분에서 1분 미만으로 감소했고 자동화율은 68%라고 밝힌다. [S6]

이는 공급사 페이지에 게시된 고객 진술이며 집계 기간과 자동화율의 상세 산식은 공개 문구에서 확인하지 못했다. 처리 시간 감소를 고객의 전체 청구 해결 시간 감소로 바꾸지 않는다.

**편집 포인트:** 도입 효과를 OCR 점수보다 현업의 입력 부담과 처리 시간으로 설명할 수 있다. 본문 분량이 길다면 보험 사례 둘 중 하나만 사용해도 충분하다.

### 사례 선택 원칙

실제 업무 연결을 보여주는 FibroGen을 중심 사례로 추천한다. 보험 사례는 산업 범위를 넓히는 보조 사례로 적합하다. 이번에 확보한 정량 자료는 플랫폼 공급사가 공개한 사례이므로 독립 감사 성과로 표현하지 않는다. 물류·국내 사례는 확인되지 않은 숫자를 채워 넣지 않는다.

## 5. 기술 구성과 선택

### 5.1 모든 파일을 같은 방식으로 읽지 않는다

아래는 구현 시 권장하는 입력 분기다.

- **텍스트 PDF:** 내장 텍스트와 좌표를 먼저 확인한다. 텍스트가 있다고 표의 행·열 관계까지 올바르게 추출된다고 가정하지 않는다.
- **스캔·사진:** 회전·흐림·잘림을 확인한 뒤 OCR이나 이미지 기반 모델을 적용한다.
- **디지털·스캔 혼합 PDF:** 페이지별로 방식을 선택하고 동일 텍스트가 중복 추출되는지 확인한다.
- **원본 스프레드시트:** 가능한 경우 셀·시트·수식 등 원래 구조를 활용한다. 화면 이미지로 바꾸면서 정보를 잃지 않도록 한다.

Azure는 Office 입력과 PDF·이미지의 처리 지원 범위에 차이가 있음을 문서화한다. 제품명만 보고 모든 형식을 같은 수준으로 지원한다고 판단하지 말고 사용할 API 버전과 파일 형식을 확인한다. [S3]

### 5.2 단계별 모델과 멀티모달 모델

| 접근 | 구성 | 검토할 점 |
|---|---|---|
| 단계별 처리 | OCR → 레이아웃·표 → 필드 추출 | 오류가 어느 단계에서 생겼는지 추적하기 쉬우나 앞 단계 오류가 전파될 수 있음 |
| 이미지 기반 추출 | 시각·언어 모델이 페이지를 보고 구조·항목 생성 | 복잡한 화면 관계를 활용하지만 누락·추정·근거 위치를 별도로 평가 |
| 혼합 | 일반 문서는 기존 파서, 어려운 구간은 시각 모델 등으로 처리 | 라우팅 기준, 결과 불일치, 비용·지연·검토 부담 관리 |

이는 설계 비교이며 모든 문서에 우수한 단일 방식이 있다는 의미는 아니다. 오픈소스 Docling은 PDF 구조·표·읽기 순서·OCR 등 문서 변환 기능과 시각·언어 모델 기반 처리를 제공하고 로컬 실행도 지원한다. [S7] 기업 내부 배포에서는 모델 가중치·라이선스·외부 연결·운영 자원을 별도로 확인해야 한다.

Amazon Textract의 표 출력은 셀과 병합 셀, 머리글·제목·푸터 등의 관계를 표현한다. 표를 한 줄의 문자열로 만드는 것보다 이런 구조를 보존해야 후속 처리가 쉬워진다. [S8]

### 5.3 원문 값·정규화 값·계산값을 분리한다

Google Document AI는 추출된 원문과 별도로 지원 필드의 `normalizedValue`를 제공한다. 텍스트 위치를 가리키는 `textAnchor`와 원문 연결도 API에서 확인할 수 있다. [S9][S10]

다음은 제품의 실제 응답이 아니라 **권장 저장 항목**이다.

| 항목 | 견적서 예시에서 남길 내용 |
|---|---|
| 문서 식별 | 파일 ID·해시·버전·공급사·견적 날짜 |
| 원문 근거 | 페이지, 표·행·셀, 좌표 또는 텍스트 위치 |
| 원문 값 | 90,000원/박스, 10개입 |
| 정규화 값 | 통화 KRW, 박스 가격 90000, 박스당 수량 10 |
| 계산값 | 개당 9000원, 계산식 90000÷10 |
| 검증 상태 | 포장 수량 확인 여부, 다른 견적과 사양 일치 여부 |
| 변경 이력 | 추출기 버전, 수정자, 수정 이유, 승인 상태 |

단위 환산 결과를 원문에 직접 적혀 있던 숫자처럼 표시하지 않는다. 원문에 없는 필수 값은 null 또는 확인 필요 상태로 남기고, 0으로 채우거나 임의 추정하지 않도록 한다.

### 5.4 검색·답변에 넘길 때도 구조를 유지한다

자체 설계 제안:

- 표를 나눌 때는 각 조각에 머리글·단위·문서 ID를 함께 연결한다.
- 각주의 적용 범위를 보존하고, 여러 페이지에 걸친 표는 이어지는 관계를 확인한다.
- 견적 합계와 단가 환산은 검증된 구조화 데이터와 계산 코드로 처리한다.
- 답변에서 원문 페이지를 열고 해당 셀·각주를 확인할 수 있도록 한다.
- Markdown 출력만 저장하지 말고 필요하면 셀 관계와 좌표를 담은 구조화 결과도 보존한다.

검색이 관련 페이지를 잘 찾았더라도 표를 잘못 복원했다면 답변이 틀릴 수 있다. 검색 품질과 문서 추출 품질을 따로 평가해야 원인을 찾을 수 있다.

## 6. 검증·사람 검토·시스템 반영

권장 업무 흐름:

`수신·문서 식별 → 유형 분류 → 문자·구조·필드 추출 → 단위·형식 정규화 → 업무 규칙 검증 → 예외 검토 → 승인된 데이터 반영`

자동 검증 예시:

1. 필수 항목의 존재, 숫자·날짜 형식, 단위·통화 여부.
2. 수량×단가와 행 금액, 상세 합계와 문서 합계의 일치. 할인·세금·반올림 규칙을 먼저 반영한다.
3. 품목·공급사 기준정보와 실제 발주·입고 내역의 일치.
4. 같은 문서의 중복 수신과 이전 버전 여부.
5. 허용하지 않은 계좌·거래처 정보 변경이나 큰 금액 차이.

사람 검토 화면에는 원문 해당 영역, 추출값, 계산값, 검토 사유를 함께 보여주는 편이 좋다. ‘확인’ 버튼만 제공하면 담당자가 문서 전체를 다시 읽어야 한다.

**신뢰도 점수와 실제 정답률을 혼동하지 않는다.** AWS는 용도의 민감도와 점수를 함께 고려하도록 안내하며, 별도 기술 글에서도 점수를 정확도 자체와 구분한다. [S11][S12] 검토를 줄일 임계값은 우리 문서의 실측 결과와 오류 비용에 맞춰 정한다. LLM이 스스로 적은 ‘확신도 99%’도 검증된 정답률로 취급하지 않는다.

## 7. 무엇을 평가해야 하나?

Google의 평가 문서는 정답 라벨과 예측값을 비교한 precision·recall·F1을 제공하며 필드별 결과를 확인할 수 있다고 설명한다. 지원하지 않거나 테스트셋에 없는 라벨은 집계에서 빠질 수 있다. [S13]

평가 설계 제안:

| 수준 | 평가 대상 |
|---|---|
| 문자 | 중요한 금액·날짜·기호의 인식 오류 |
| 구조 | 행·열·병합·머리글·읽기 순서의 보존 |
| 필드 | 단가·통화·단위·포장 수량·납기의 정답 여부 |
| 문서 | 업무에 필요한 핵심 필드가 모두 맞는 비율 |
| 업무 | 잘못된 견적 비교·전표 입력·지급 요청 발생 여부 |
| 운영 | 검토 시간, 자동 처리율, 재작업, 문서 한 건의 총비용 |

필드가 대부분 맞아도 금액 하나를 틀리면 업무 결과가 달라진다. 평균 점수 외에 고위험 필드와 잘못 자동 통과한 문서를 별도로 본다. 자동 처리율은 ‘사람이 만지지 않은 비율’과 ‘검증까지 통과해 실제 반영한 비율’ 중 무엇인지 명시한다.

OmniDocBench는 다양한 PDF의 텍스트·표·수식·읽기 순서 등을 평가하기 위한 공개 벤치마크다. [S14] 평가 항목을 설계할 참고자료로 쓰되 공개 순위를 한국어 견적서의 정답률로 옮기지 않는다. 이번 조사에서 벤치마크를 실행하지 않았다.

테스트셋에는 실제 공급사 양식, 신규 양식, 다중 페이지, 낮은 화질, 한글·영문 혼합, 수정 문서, 각주, 병합 셀을 포함하도록 제안한다. 같은 양식의 거의 동일한 문서가 학습·테스트에 섞이지 않도록 공급사·양식·시점을 고려해 분리한다.

## 8. 운영과 보안에서 빠뜨리기 쉬운 일

아래는 구현 검토 항목이며 특정 제품의 보안 인증을 의미하지 않는다.

- 원문·추출값·검색 인덱스·로그에도 같은 접근 권한과 보관·삭제 정책을 적용한다.
- 외부 문서 안의 명령형 문구는 업무 지시가 아닌 처리 대상 데이터로 취급한다.
- 파싱 프로세스와 ERP 수정 권한을 분리하고, 검증을 통과한 데이터만 다음 단계에 보낸다.
- 파일 크기·페이지 수·손상 파일을 관리하고 문서 처리 도구를 격리한다.
- 사람의 교정은 즉시 모델 학습이 되는 것이 아니다. 정답 데이터, 추출 규칙, 공급사별 매핑, 평가 사례 중 무엇을 고칠지 분류한다.
- 모델·파서 버전이 바뀌면 기존 문서의 결과가 달라지는지 회귀 시험한다.
- ‘API 호출 완료’와 ‘모든 페이지·항목 처리 완료’를 구분하고 부분 실패를 기록한다.

## 9. 파일럿과 포스팅 방향

### 파일럿 제안

반복되는 견적서 또는 송장 한 종류를 고르고 담당자가 실제로 입력·비교하는 필드부터 정한다. 원문 근거가 연결된 추출 결과를 기존 수작업 결과와 비교한다. 어려운 문서도 포함해 자동 통과·사람 검토 기준을 조정한 뒤 시스템 입력을 연결한다.

비용은 페이지 처리비만 계산하지 않는다. 시각 모델 호출, 재시도, 원문 저장, 검토 인력, 연동·운영 비용을 더하고 기존 업무 시간과 비교한다. 특정 공급사의 과거 추정 운영비를 우리 회사 예산으로 그대로 쓰지 않는다.

### 포스트 전개 제안

1. **들어가며:** 개당 가격과 박스당 가격을 비교한 가상 보고서로 시작.
2. **문서를 읽었다는 말의 차이:** OCR·표·항목·검증을 같은 견적서로 설명.
3. **실제 현업 도입:** FibroGen의 SAP 연동, 보험 서류 처리 사례.
4. **원문부터 업무 데이터까지:** 단위·각주·페이지 관계와 근거 저장.
5. **자동 처리할 문서와 사람이 볼 문서:** 검증·신뢰도·테스트셋.
6. **나가며:** 현업이 알고 있는 문서 해석 기준을 자산화하고 업무 시스템에 연결하는 과제.

향후 CTA는 ‘최근 견적서·송장과 실제 수정한 항목을 함께 보며 자동화 범위를 찾자’는 방향이 적합하다. EpsilonDelta의 확인되지 않은 실적이나 정확도 보장은 추가하지 않는다. 연락처: `contact@epsilondelta.ai`.
