# AI FinOps — 개념·기술·기업 적용 사례 리서치

조사일: 2026-09-28 (KST)

- 백로그: `_research/ax-topic-backlog-100.md` 048번, 업무 한 건당 AI 비용.
- 독자: AI·AX에 관심 있는 경영진, CFO·CTO, 현업·운영 책임자.
- 범위: AI 비용의 가시화·배분·예측·최적화, 업무 단가와 품질, 기술 구성과 기업 사례.
- 자료 구분: 공식 프레임워크·제품 문서, 기업 엔지니어링 발표, 행사 주최 측 요약, 공급사 고객 사례, 자체 설계 제안.
- 공개 자료조사이며 기업 청구서 열람, 제품 실험, 고객 인터뷰, 절감 효과 재현은 수행하지 않았다.

## 1. 핵심 결론

**AI FinOps는 AI 비용을 무조건 줄이는 활동보다, 지출과 업무 가치를 연결해 기술·현업·재무가 함께 판단하는 운영 방식이다.** FinOps Foundation은 기술의 사업 가치를 높이고 재무적 책임을 공유하는 협업 체계로 FinOps를 설명하며 AI를 별도의 기술 지출 범주로 다룬다. AI 지출에는 API뿐 아니라 자체 인프라·SaaS·계약 지출도 포함된다. [S1][S2]

이번 포스트의 중심 질문:

> 모델 호출료는 낮췄는데 재시도와 직원 검토가 늘었다면, 정말 더 싸게 일하고 있는 걸까?

토큰 단가는 자원 사용을 비교할 지표다. 경영 판단에는 품질 기준을 만족한 업무 완료 건수와 그 과정의 비용을 연결해야 한다. FinOps Foundation의 Unit Economics도 토큰에서 지원·에이전트 행동·업무 결과 단위로 평가 범위를 확장하는 접근을 설명한다. [S3]

## 2. 개념과 경계

| 개념 | 이번 글에서의 의미 |
|---|---|
| FinOps for AI | AI에 쓰는 비용과 가치를 관리 |
| AI for FinOps | 비용 분석·이상 탐지 등 FinOps 업무에 AI를 활용 |
| 토큰 단가 | 특정 모델·요금 조건의 자원 가격 |
| 요청당 비용 | 모델 호출 또는 애플리케이션 요청 한 번의 비용 |
| 업무당 비용 | 같은 업무 ID에 속한 호출·도구·검토 등을 합친 비용 |
| 성공 업무당 비용 | 실패·재시도 비용까지 포함한 총비용을 정해진 성공 건수로 나눈 값 |
| TCO | 구축·운영·유지보수·인프라·인력 등을 포함한 전체 보유 비용 |
| ROI | 비용뿐 아니라 실현한 편익을 함께 계산하는 투자 평가 |

위 구분은 집필용 정리다. 성공 업무당 비용을 낮췄다고 곧바로 ROI가 양수라는 뜻은 아니다. 시간 확보, 매출 기여, 고객 경험과 실제 현금 절감도 구분한다.

Workslop 글은 받는 사람에게 넘어가는 재작업을 다뤘다. 이번에는 **모델·검색·캐시·반복·예산 정책을 어떻게 구성해야 업무 원가가 달라지는가**에 집중한다.

## 3. 계산 예시 — 저렴한 호출이 비싼 업무가 되는 경우

아래는 실제 가격이나 도입 성과가 아닌 가상 수치다. 같은 난도의 요청 100건을 처리하고, 필요한 수정까지 거쳐 모두 같은 합격 기준을 충족했다고 가정한다. 직원 시간은 분당 500원의 내부 평가 단가로 환산한다.

| 항목 | 구성 A | 저렴한 모델로 바꾼 구성 B |
|---|---:|---:|
| 모델·도구 사용료 합계, 재시도 포함 | 10,000원 | 5,000원 |
| 직원 검토·수정 시간 합계 | 100분 | 200분 |
| 시간 환산 비용 | 50,000원 | 100,000원 |
| 비교 대상 운영비 합계 | 60,000원 | 105,000원 |
| 합격한 업무 | 100건 | 100건 |
| 합격 업무 한 건당 비용 | 600원 | 1,050원 |

API 지출은 절반이지만 비교 대상 업무 단가는 높아진다. 여기에는 구축비·공통 인프라비를 넣지 않았다. 비교 시 같은 비용 범위를 적용해야 하며 시간 환산 비용 감소를 곧바로 급여 지출 감소로 계산하지 않는다.

권장 식:

`성공 업무당 운영비 = 해당 업무군의 총 운영비 / 같은 집계 범위에서 합격·완료한 업무 수`

실패한 시도의 비용을 분자에서 빼지 않는다. 재시도를 새 업무로 세지 않으며, 사람이 마무리한 업무를 성공에 포함하면 그 인력 비용도 포함한다. 자동 완료와 사람 보완 완료를 별도로 보고하면 변화의 원인이 보인다. 장기 업무는 발생 기간과 완료 기간이 어긋나므로 요청 코호트 또는 미완료 건 처리 기준을 명시한다.

## 4. 실제 기업 사례와 활용 우선순위

### 4.1 Notion — 생성 모델 밖에도 비용이 있었다

Notion은 2026-02-19 자사 기술 블로그에서 벡터 검색 인프라를 10배 규모로 확장하면서 비용을 90% 줄인 과정을 소개했다. 이 수치는 **벡터 검색 인프라 범위**이며 Notion 전체 AI 비용 절감률이 아니다. [S4]

특히 문서가 조금만 바뀌어도 전체 구간을 다시 임베딩하던 방식에서, 텍스트와 메타데이터의 해시를 비교해 필요한 부분만 갱신하도록 바꿨다. 권한 같은 메타데이터만 바뀌면 임베딩 계산을 생략하고 해당 정보만 수정했다. 이 변경으로 데이터 처리량을 70% 줄여 임베딩 API와 벡터 DB 쓰기 비용을 낮췄다고 설명한다.

**편집 포인트:** 비싼 모델을 싼 모델로 바꾸는 방법만 있는 것이 아니다. 이미 계산한 것을 다시 계산하지 않는 구성도 비용을 줄인다. 문서 이해·사내 검색 글과 연결하기 좋다.

집필 메모: 같은 글의 Ray 이전에 따른 임베딩 인프라 비용 90% 이상 감소는 당시 진행 중인 작업의 예상치다. 이미 달성한 비용 절감과 섞지 않는다. 여러 단계의 절감률을 더하지 않는다.

### 4.2 SAP — AI 지출을 조직의 관리 대상으로

FinOps Foundation의 FinOps X 2026 행사 요약은 SAP의 FinOps·AI 담당자가 글로벌 규모의 AI FinOps 지표·거버넌스·운영 경험을 발표했다고 기록한다. SAP 발표 세션 소개는 경영진의 권한 부여와 업무 결과 중심의 단위 경제성을 강조한다. [S5][S6]

**편집 포인트:** 개발팀의 모델 사용량 표만으로 끝내지 않고 현업과 재무가 같은 지표를 보는 운영 문제로 설명한다. 이번 조사에서는 행사 요약과 세션 소개를 확인했으며 영상 전체·내부 원가표는 확인하지 않았다. SAP의 구체 절감률이나 내부 시스템 구조를 만들어 쓰지 않는다.

### 4.3 Lonely Planet — 비교 기준을 확인해야 하는 비용 절감 사례

AWS는 Lonely Planet이 기존 여행 콘텐츠를 활용해 개인화 여행 일정을 생성하는 서비스를 구축했다고 소개한다. AWS의 일부 자료는 생성형 AI 워크로드 비용을 다른 모델·서비스 대비 80% 줄였다고 설명한다. 반면 AWS 영상 소개에는 수작업 대비 80%, 다른 모델 대비 78%라는 표현이 함께 나온다. [S7][S8]

**활용 판단:** 모델·구성 선택을 실제 서비스 비용과 연결한 사례로는 쓸 수 있다. 다만 본문에서 단일 ‘80%’를 강조하려면 비교 대상과 측정 범위를 추가 확인해야 한다. 현재는 수치를 빼고 모델 선택의 사례로 쓰거나 Notion·SAP 중심으로 구성하는 편이 안전하다.

### 보류 후보: Robinhood

검색 결과의 AWS CDN 페이지에는 하루 토큰량 증가와 80% 비용 감소가 표시됐지만, 직접 확인한 정식 사례 페이지 본문은 금융범죄 조사 지원 에이전트 설명 위주이며 해당 수치를 확인하지 못했다. 정량 비용 사례로 채택하지 않는다. [S9]

이번 조사에서 확보한 사례를 모두 ‘기업이 공식적으로 AI FinOps 프로그램을 운영했다’고 부르지 않는다. SAP는 운영 체계 사례, Notion은 실제 비용 최적화 사례, Lonely Planet은 공급사 발표 사례다.

## 5. 무엇을 비용으로 모을 것인가?

아래는 기업 구축을 위한 자체 분류안이다.

| 비용 층 | 항목 예시 | 놓치기 쉬운 부분 |
|---|---|---|
| 모델 | 입력·출력·캐시 읽기·쓰기·과금 대상 추론 | 입력 토큰만 계산하거나 추론 토큰 중복 합산 |
| 데이터 | 임베딩·검색·재순위화·문서 파싱·저장 | 문서 수정 때 재처리, 유휴 인덱스 |
| 도구 | 검색 API·음성·브라우저·외부 서비스 | 실패한 호출도 비용 발생 가능 |
| 실행 | 워커·DB·큐·네트워크·로그 | 에이전트 대기·반복·장시간 세션 |
| 사람 | 검토·수정·인계·운영·평가 | 작성자가 아낀 시간만 보고 검토 시간 누락 |
| 공통·고정 | SaaS 좌석·예약 용량·GPU·플랫폼팀 | 사용하지 않는 좌석·낮은 가동률·미소진 약정 |
| 도입·변경 | 구축·데이터 준비·학습·마이그레이션 | 초기 투자를 누락하거나 월 운영비와 혼합 |

실시간 비용 추정, 공급사 청구액, 내부 인력 환산 비용은 서로 다른 장부로 유지한 뒤 목적에 맞게 합친다. 개발·실험·운영 지출도 분리한다. 정확하지 않은 공통비를 모든 요청에 억지로 배분하기보다 배분 기준과 미배분 금액을 표시한다.

## 6. 기술 구성으로 비용을 바꾸는 방법

### 6.1 모델 라우팅과 단계적 승격

간단한 분류·추출과 복잡한 판단을 구분해 모델을 선택하거나, 검사에 실패한 요청을 더 강한 모델로 넘기는 설계를 검토한다. 라우터와 추가 검증 호출도 비용에 포함한다.

AWS의 Intelligent Prompt Routing 설명은 품질 차이 설정과 개발 데이터셋에서의 비용·지연 평가를 다룬다. 공개된 절감률은 내부·공개 평가 데이터에서 나온 결과이며 기업 도입 성과와 구분한다. [S10]

자체 적용 기준: 어려운 요청을 싼 모델에 여러 번 재시도하는 경로와 강한 모델 한 번으로 처리하는 경로를 같은 정답셋에서 비교한다. 모델의 자체 확신만으로 승격을 결정하기보다 규칙 검사·실행 결과·현업 평가를 활용한다.

### 6.2 프롬프트 캐시와 답변 캐시는 다르다

프롬프트 캐시는 반복되는 입력 부분의 계산을 재사용하는 기능이다. Bedrock 문서는 고정 내용을 앞에, 변하는 내용을 뒤에 배치하는 방식을 설명한다. 캐시 적중은 보장되지 않으며 유효기간·최소 길이·읽기와 쓰기 과금은 모델별로 확인해야 한다. [S11]

답변 캐시는 이전 결과 자체를 재사용한다. 유사한 질문이라도 사용자 권한·고객·정책 버전·가격 시점이 다르면 같은 답을 돌려주면 안 된다. 이는 자체 운영 설계 주의점이다.

캐시 적용 후에는 적중률뿐 아니라 쓰기 비용과 실제 청구 감소를 확인한다. 정답률이나 접근 통제를 희생하면서 캐시 적중률만 높이지 않는다. 반복 입력을 캐시해도 새 출력과 도구 실행 비용이 사라지는 것은 아니다.

### 6.3 비동기 배치 처리

지금 답해야 하는 상담과 내일까지 처리하면 되는 문서 분류를 나누어 본다. Bedrock은 여러 프롬프트를 비동기 배치로 처리하는 기능을 제공한다. [S12] 지원 모델·완료 시간·할인은 해당 서비스 조건에 따라 확인한다.

업무 설계에서는 부분 실패의 재처리, 마감 시간, 중복 결과 반영을 관리한다. 단가가 낮아도 승인 마감을 놓치면 적합한 선택이 아니다.

### 6.4 컨텍스트·도구·반복 횟수

자체 최적화 제안:

- 관련 문서와 필요한 도구 정의만 제공하고 중복된 결과를 줄인다.
- 대화 요약 시 승인 조건·예외·근거가 사라지지 않는지 평가한다.
- 합계·단위 환산처럼 명확한 계산은 검증된 코드로 처리한다.
- 실패 원인이 권한·입력 오류라면 같은 호출을 반복하지 않는다.
- 총 도구 호출 수, 반복 횟수, 실행 시간, 출력량의 상한과 사람 인계 기준을 둔다.
- 병렬 하위 에이전트의 비용을 부모 업무 ID로 합산한다.

### 6.5 증류·자체 호스팅은 별도 투자 판단

모델 증류는 큰 모델의 출력을 활용해 작은 모델을 특정 업무에 맞추는 방식이다. AWS는 학습 데이터 생성·미세조정·배포를 연결하는 기능을 제공한다. [S13] 일반 제품의 최대 절감률을 우리 업무의 예상 성과로 쓰지 않는다.

검토할 전체 비용에는 교사 모델 호출, 학습·평가, 모델 저장·서빙, 재학습을 포함한다. 자체 호스팅은 GPU 가격 외에 가동률·피크 용량·장애 대응·업데이트 인력도 계산한다. 사용량이 불규칙하면 저렴한 시간당 장비가 낮은 업무 단가를 보장하지 않는다.

## 7. 관측·배분·청구 대조 구조

권장 연결:

`업무 ID → 실행·재시도·하위 작업 → 모델·도구 사용량 → 가격표·계약 조건 → 추정 비용 → 실제 청구 대조 → 품질·완료 결과`

OpenTelemetry의 GenAI 자료는 모델 호출·토큰 사용량 등의 관측 항목을 제공한다. [S14] 공급사 사용량 필드와 SDK 버전별 의미를 확인하고, 캐시·추론 토큰이 전체 토큰에 포함되는지 확인해 중복 합산을 막는다.

자체 최소 기록안:

- 업무 ID·부서·제품·환경·소유자.
- 실행 ID·부모 작업·재시도·요청 시각.
- 모델·공급사·버전, 입력·출력·캐시 사용량, 적용 요금표 시점.
- 도구 사용량·지연·오류·중단 사유.
- 품질 판정·완료 여부·사람 검토 시간.

개인정보가 담긴 원문 프롬프트를 전부 저장해야 비용을 계산할 수 있는 것은 아니다. 사용량 메타데이터와 제한된 평가 자료를 분리한다.

FOCUS는 여러 공급사의 비용·사용량 데이터를 공통 형식으로 정규화하려는 공개 명세다. [S15] 우리 회사의 ‘업무 완료’를 자동으로 정의해주지는 않으므로 업무 결과 데이터와 별도로 연결한다.

Showback은 부서에 비용을 보여주는 것, Chargeback은 정한 기준으로 비용을 배부·청구하는 것이다. 초기에는 부서별 사용과 공통비를 보여주고 책임자를 정한 뒤 실제 배부 범위를 합의하도록 제안한다.

## 8. 예산 알림과 실행 차단은 별개

Google Cloud는 alerts-only budget이 사용량·지출을 자동 제한하지 않는다고 명시한다. 지원 서비스에는 별도 spend cap 예산의 preview도 안내한다. [S16] ‘예산을 설정했으니 더 이상 과금되지 않는다’고 가정해서는 안 된다.

자체 실행 통제 제안:

1. 실행 전 예상 최대 사용량을 확인하고 업무 예산 일부를 예약한다.
2. 각 모델·도구 호출 뒤 실제 사용량을 누적한다.
3. 병렬 실행은 공통 한도를 원자적으로 확인해 동시에 초과 승인하지 않게 한다.
4. 한도 근처에서는 새 작업을 막거나 적절한 모델·비동기 처리·사람 인계로 전환한다.
5. 실패·취소 후 남은 예산을 정산하고 청구 지연·가격 변경의 차이를 대조한다.

진행 중인 결제·발주를 무조건 끊지 않는다. 이미 실행한 거래의 결과를 확인하고 안전하게 마무리하거나 인계할 비용도 고려한다. 예산 때문에 보안 검사나 필수 승인을 생략하는 경로는 만들지 않는다.

## 9. 운영 지표와 파일럿

| 경영진 질문 | 볼 지표 |
|---|---|
| 더 많이 써서 비싸졌나, 비효율이 늘었나? | 전체 지출·처리량·업무 단가를 함께 비교 |
| 싸게 바꾼 뒤 품질은 유지됐나? | 합격률·중요 오류·재시도·사람 수정 시간 |
| 어떤 업무가 비용을 쓰나? | 업무군·부서·환경·모델별 비용 및 미배분액 |
| 평균에 가려진 비싼 작업은? | 비용 분포·상위 고비용 건·p95 지연 |
| 예산 초과는 막을 수 있나? | 예측 대비 실제, 알림·차단·인계 결과 |

파일럿은 업무 한 종류의 현재 비용·정답 기준을 먼저 기록한 뒤 구성 하나씩 바꾸도록 제안한다. 모델 교체·캐시·검색 범위를 한꺼번에 바꾸면 원인을 분리하기 어렵다. 같은 요청군에서 품질·지연·비용을 비교하고 실제 운영에서 제한된 범위로 검증한 뒤 확대한다.

역할은 현업이 완료·품질 기준, 개발팀이 관측·실행 제어, 재무가 비용 범위·배분·실현 편익, 구매가 계약 조건을 맡는 방식으로 나눌 수 있다. 비용을 보는 담당자만 있고 구성 변경 책임자가 없으면 개선하기 어렵다.
