고객센터 AI는 언제 사람을 불러야 할까요? 반복 설명 없는 상담 인계의 조건

Geoff Yoon ㆍ
2026. 11. 23

들어가며

온라인 서비스에서 결제 문제가 생겨 고객센터 채팅창을 열었을 때를 떠올려 보겠습니다. 도움말 버튼을 몇 번 누르다 해결이 안 되어 ‘상담원 연결’을 입력했는데 비슷한 안내문만 반복되는 경우가 있습니다. 어렵게 상담원과 연결되더라도 “어떤 일로 문의하셨을까요? 주문번호부터 다시 말씀해 주시겠어요?“라는 첫마디를 듣는 순간 피로감은 커집니다.

서울시는 2025년 10월 2일부터 14일까지 온라인쇼핑 소비자 1,000명을 조사해 2026년 2월 27일 온라인쇼핑 소비자 조사 결과 를 발표했습니다. 피해 발생 시 가장 큰 불편으로 응답자의 41.1%가 ‘고객센터 연결이 안 되거나 자동 응답 등으로 연락이 원활하지 않음’을 꼽았습니다. AI 챗봇 개선 요구 사항으로도 ‘AI 챗봇과 직원 1:1 상담 동시 운영’(40.4%)과 ‘복잡한 문의 시 상담원 즉시 연결’(27.0%)이 나란히 상위권에 올랐습니다. 온라인쇼핑 이용자를 조사한 이 결과에서도 자동 응답 기능 못지않게 사람 상담원에게 이어지는 통로가 중요하다는 점이 드러납니다.

많은 기업이 고객센터 AI를 도입할 때 전체 문의 중 몇 퍼센트를 스스로 답변했는지에 집중합니다. 정작 고객 경험과 운영 안전성을 좌우하는 기준은 자동 응답의 경계선에 있습니다. 응급실 분류(triage) 데스크가 경증과 전문의 진료 대상을 가려내고 활력 징후 차트를 담당 의사에게 넘기듯, 고객센터 AI도 언제 멈추고 사람을 부를지(호출 기준), 무엇을 전달해 반복 설명을 막을지(맥락 인계), 대화를 실제로 받아줄 담당자와 여력이 있는지(인수 관리)를 한 묶음으로 설계해야 합니다.

문의의 이름보다 무엇을 바꾸는 일인지 살펴야 합니다

고객센터 문의를 ‘계정’, ‘결제’, ‘환불’처럼 큰 제목으로만 나누면 어디까지 자동화하고 어디서부터 사람을 부를지 정하기 어렵습니다. 같은 결제 문의라도 단순 승인 조회와 이중 청구 이의 제기는 회사가 질 책임이 다르기 때문입니다. 흔히 답변 확신도(confidence score)가 낮으면 사람에게 넘긴다고 말합니다. 그런데 이번에 확인한 주요 플랫폼 기술 문서들에서도 모든 기업에 그대로 적용할 보편적인 확신도 임계값을 따로 정해 두고 있지는 않습니다. 운영 경계는 문의 제목보다 그 작업이 시스템 데이터와 고객의 권리 관계에서 무엇을 바꾸는가를 기준으로 정해야 합니다.

출판·교육 기업 Wiley의 학기 초 초기 실사용 파일럿이 역할 분담의 출발점을 보여줍니다. Salesforce의 고객 사례 와 2024년 9월 12일 보도자료 가 이 파일럿을 다뤘습니다. Wiley는 개학 시즌 파일럿에서 계정 접근과 비밀번호 재설정은 AI가 자동으로 해결하고 등록·결제 문제는 분류(triage)하여 적절한 자료나 경로로 안내하도록 구분했습니다. Salesforce와 고객사는 파일럿 첫 몇 주 동안 기존 챗봇 대비 케이스 해결이 40% 이상 개선됐다고 발표했습니다. 공급사와 고객사가 공개한 초기 파일럿의 기존 챗봇 대비 상대적 개선 폭이므로 장기 운영의 절대 해결률로 일반화할 수는 없습니다. 다만 자동 해결 업무와 분류해 넘길 업무를 처음부터 나눈 점은 참고할 만합니다.

1. 비밀번호 재설정: 사람의 개입이 본인 확인 생략을 뜻해서는 안 됩니다

비밀번호 재설정은 본인 확인과 복구 절차가 정해져 있어 자동화하기 좋습니다. 다만 등록된 인증 수단을 쓸 수 없어 AI 단계에서 본인 확인에 실패했을 때 상담원이 대신 잠금을 풀어주도록 설계하면 보안 위험이 커집니다. Okta의 2023년 8월 보안 공지 와 미국 CISA·FBI 합동 권고문(AA23-320A) 은 공격자가 서비스데스크 직원에게 전화를 걸어 설득한 뒤 고권한 사용자의 비밀번호나 다중인증(MFA) 요소를 재설정하게 만든 사회공학 공격을 경고합니다. 둘 다 기업 내부 IT 헬프데스크 맥락의 1차 자료입니다. 내부 IT 헬프데스크 사례를 소비자 고객센터에 그대로 대입할 수는 없지만 운영상 유추해 볼 때 원칙은 분명합니다. 자동 인증 실패로 사람을 부를 때는 상담원이 임의로 예외 처리를 하는 대신, 회사가 별도로 정해 둔 더 엄격한 2차 본인 확인 및 계정 복구 절차로 안내하는 역할을 맡겨야 합니다.

2. 결제 문의: 단순 상태 조회와 청구 오류 조사를 분리합니다

결제일이나 승인 여부를 확인하는 조회는 시스템 기록만 읽어오면 되므로 AI가 즉시 응답하기에 적합합니다. 반면 “취소했는데 돈이 빠져나갔다"거나 “같은 금액이 두 번 청구됐다"처럼 조회 기록과 고객 주장이 충돌할 때는 분쟁 조사와 정정이 필요합니다. 이때는 AI가 대화를 끝내려 하지 않고 접수 번호를 생성한 뒤 담당자에게 넘기도록 설계하는 편이 안전합니다.

3. 환불 요청: 정책 안내·자격 판정·지급 요청·예외 복구를 나눕니다

환불을 모두 사람이 승인해야 한다거나 AI가 모든 예외를 처리할 수 있다고 단정할 필요는 없습니다. Klarna는 2024년 2월 27일 첫 달 글로벌 운영 발표 에서 환불·반품·결제 문의를 AI 지원 범위로 소개하면서도 고객이 원하면 사람 상담사와 대화할 수 있는 선택권을 명시했습니다. 한편 Stripe의 환불 기술 문서 에 따르면 환불 요청 접수와 최종 완료는 서로 다른 단계이며 잔액이나 결제 수단 조건에 따라 환불이 보류(pending)되거나 실패할 수 있습니다. 따라서 약관과 시스템 조건이 들어맞는 환불 요청까지는 자동화하되, 정책 밖의 예외 요구나 결제 시스템의 환불 보류·실패가 발생했을 때는 사람 담당자를 호출해 복구와 안내를 맡기는 운영 설계를 제안합니다.

현장에서 사람을 부르는 네 가지 호출 신호

업무별 책임 경계를 정했다면 대화 도중 어떤 신호가 왔을 때 사람을 호출할지 규칙을 세워야 합니다. 상용 에이전트 플랫폼 문서를 종합하면 호출 신호는 네 가지로 나뉩니다.

첫째는 고객의 명시적 연결 요청입니다. Microsoft Copilot Studio의 상담원 인계 문서 와 Intercom의 Fin 에스컬레이션 규칙 도움말 은 고객이 직접 상담원 연결을 요구하거나 AI가 의도를 파악하지 못했을 때를 기본 이관 조건으로 다룹니다. 고객이 사람을 찾는데도 AI가 질문을 다시 입력하라며 가로막으면 불만만 커집니다.

둘째는 사전에 지정한 주제나 고객 조건에 도달했을 때입니다. Copilot Studio는 특정 토픽에 대화 이전(Transfer conversation) 단계를 직접 배치하는 방식을 지원합니다. Intercom도 자연어 지침과 별도로 고객·대화 속성 기반의 규칙 설정을 제공합니다. 분쟁 소지가 크거나 예외 판단이 필요한 주제는 확정된 규칙으로 담당 팀에 넘기는 것이 안전합니다.

셋째는 해결 진전이 없는 반복 대화와 강한 불만 신호입니다. 같은 안내가 반복되거나 고객이 같은 질문을 되풀이하는 현상은 대화가 제자리를 맴돌고 있다는 운영 신호입니다. Intercom 문서는 반복 대화와 강한 불만 감지를 다루면서도, 불만이 감지됐다고 해서 항상 즉시 연결하는 대신 연결을 먼저 제안하거나 조직의 워크플로 설정에 따르도록 설명합니다. 감정 표현은 보조 신호로 삼고 해결 진전이 멈췄는지를 중심 기준으로 두는 설계를 권장합니다.

넷째는 외부 업무 시스템의 처리 보류나 불일치입니다. 앞서 본 Stripe 환불 문서 의 보류·실패 사례처럼 결제나 주문 시스템에서 보류 상태가 돌아오거나 고객 주장과 조회 기록이 어긋날 때입니다. 이런 조건은 AI의 문맥 추측에 맡기지 않고 시스템 규칙으로 이관 신호를 발생시켜야 운영 오류를 줄이는 데 도움이 됩니다.

상담원에게 연결됐는데 왜 처음부터 다시 설명해야 할까요?

구독형 온라인 교육 서비스를 이용하는 고객이 카드 명세서를 보다가 같은 달에 동일한 수강료가 두 번 청구된 것 같아 채팅창을 열었다고 가정해봅시다. 고객은 AI에게 주문번호를 알려주며 한 건을 취소해 달라고 요청합니다. AI가 조회해 보니 한 건은 본과목이고 다른 한 건은 실습 키트 별도 결제 건으로 확인됩니다. 이때 고객이 “키트를 신청한 적이 없으니 환불해 달라"고 이의를 제기한다면 담당자가 이어받아야 합니다.

만약 상담원에게 ‘결제 문의’ 알림과 긴 채팅 원문만 넘어가면 상담원은 기록을 읽느라 응답이 늦어지거나 주문번호와 사연을 다시 묻게 됩니다. 이를 막기 위해 상용 플랫폼들은 대화 전문, 라우팅과 조회를 위한 변수, 상담원이 빠르게 읽을 요약 메모를 함께 전달하는 기능을 제공합니다.

Microsoft Copilot Studio 문서 에 따르면 연결된 상담 허브로 대화를 넘길 때 전체 대화 이력과 관련 변수, 상담원에게만 보이는 비공개 메시지를 전달할 수 있습니다. 또한 Intercom의 Fin Agent API 문서 를 보면 외부 시스템이 이관을 호출할 때 Fin이 대화를 요약해 새 헬프데스크 대화의 내부 메모로 붙이고 선택적인 배경 정보(context)를 함께 넘길 수 있습니다. 이 문서는 현재 Preview 상태이며 별도 접근 신청이 필요합니다.

도입 시 구분해 확인할 점도 있습니다. Salesforce의 2024년 9월 보도자료 는 Agentforce가 상호작용 요약과 고객 정보 개요, 다음 행동 권고를 사람에게 전달한다고 설명합니다. 반면 Wiley 고객 사례 페이지 의 요약 설명은 케이스가 완료될 때 다음 담당자나 관리자가 파악하도록 돕는 사후 요약입니다. 검토 중인 도구가 실시간 이관 시점에 요약을 전달하는지 확인해야 합니다. 아울러 Intercom의 Preview API 문서 는 내부 메모와 배경 정보가 고객에게는 보이지 않아도 대화 접근권이 있는 팀원에게는 보이므로, 비밀번호·인증코드 같은 자격증명이나 불필요한 개인정보를 넣지 말라고 경고합니다.

이러한 기능을 바탕으로 5대 인계 메모 항목을 운영 제안으로 정리했습니다. 상담원이 대화를 맡은 뒤 빠르게 맥락을 파악하도록 돕는 항목입니다.

  1. 고객이 원하는 조치: 고객이 바라는 최종 결과 (예: 중복 청구 의심 건 취소 요청)
  2. 확인된 사실과 식별자: 본인 확인 여부, 조회한 주문·결제 번호와 조회 시각, 원문 위치
  3. AI의 실행 이력과 상태: 실행한 조치와 성공·보류·실패 상태 (‘요청 접수’와 ‘최종 완료’ 구분)
  4. 아직 약속하지 않은 사항: 정책 예외 승인이나 보상처럼 AI가 확답을 보류한 내용
  5. 이관 사유와 남은 쟁점: 사람을 호출한 이유와 상담원이 바로 확인해야 할 불일치 지점

‘이관 요청’과 ‘상담원 인수’는 서로 다른 사건입니다

인계 메모를 잘 꾸렸더라도 실제 상담원의 인수(acceptance)와 대기열 운영이 뒷받침되지 않으면 고객은 빈 대기열에 머물게 됩니다. 경영진 보고서에서는 ‘AI 이관 건수(Escalated)‘를 곧 ‘사람이 응대한 건수’로 여기는 착시가 흔히 나타납니다.

Microsoft Copilot Studio 문서 에 따르면 분석 화면의 Escalated 표시는 대화가 Transfer conversation 노드에 도달한 세션을 집계합니다. 새로 만든 에이전트에는 이 노드가 기본으로 들어 있지 않습니다. 실시간 상담을 넘기려면 참여 허브와의 연결 설정(표준 하네스 범위 기준)이 필요합니다. 또한 Microsoft의 Bot Framework SDK v4 사람 인계 설계 문서 (2024년 10월 갱신 기준)는 인계 요청과 상담원이 대화를 실제로 맡은 상태(accepted), 인계 실패(failed), 처리 완료(completed)를 별개의 상태로 구분합니다.

받는 팀 설정과 업무시간도 중요합니다. Intercom 에스컬레이션 규칙 문서 는 대화를 받을 사람 팀이 지정되지 않은 봇 단독(bot only) 구성에서는 사람 연결을 제안하지 않는다고 설명합니다. 업무시간과 예상 응답 시간을 안내하려면 Intercom 예상 응답 시간 도움말 처럼 워크플로에 표시 단계를 따로 넣어야 합니다. Intercom 업무시간 리포팅 문서 를 보면 첫 응답 시간의 기본 시작점은 AI 이관 시각이 아니라 고객의 첫 메시지 시각입니다.

따라서 운영 책임자는 세 가지 원칙을 함께 세워야 합니다. 우선 상담원이 대화를 실제로 인수(accepted)하기 전에는 “상담원이 확인했습니다"라고 안내하지 말고 접수·대기·인수 상태를 정확히 알립니다. 다음으로 사람에게 대화 소유권이 넘어간 뒤에는 AI의 자동 답변과 도구 재시도를 멈춰 중복 실행이나 혼선 메시지를 막습니다. 마지막으로 영업시간 밖이거나 대기열이 찼을 때는 인계 메모를 티켓으로 접수하고 회신 경로와 예상 시점을 안내합니다.

자동화 비중이 높아질수록 사람에게 닿는 통로가 중요해집니다

고객센터 AI 운영이 성숙할수록 자동화 처리량과 사람의 뒷받침을 함께 유지하는 일이 핵심 과제가 됩니다. Klarna는 2024년 2월 첫 달 운영 발표 에서 고객서비스 채팅의 3분의 2를 AI가 처리했다고 밝혔습니다. 2026년 2월 26일 서명된 2025년 연차보고서(Form 20-F) 에서는 자체 로그를 기준으로 2025년 고객서비스 채팅의 80%를 AI가 처리했다고 보고했습니다. AI 처리 비중을 80%로 보고하는 이 연차보고서에서도 모든 고객에게 사람 상담원을 선택할 수 있는 권리를 계속 제공한다고 명시했습니다.

경영진은 매월 ‘AI 자동 처리율’ 하나만 보고받기보다 상담 인계가 건강하게 작동하는지 보여주는 다섯 가지 운영 지표를 함께 점검할 필요가 있습니다.

  • 필요한 이관의 누락률과 불필요한 이관률: 사람이 필요했던 예외 건을 AI가 붙잡아 둔 비율과 단순 조회를 성급히 넘긴 비율을 표본 검수합니다.
  • 이관 인수율과 실질 인수 대기시간: 이관 요청 건수 중 상담원이 실제 인수한 비율과 요청부터 인수까지의 대기시간을 봅니다.
  • 반복 설명률: 필수 본인 확인을 제외하고 고객이 AI에게 이미 말한 주문번호나 사연을 상담원이 다시 질문한 비율을 측정합니다.
  • 동일 사안 재문의율: 상담 종료 후 일정 기간 안에 같은 문제로 다시 연락한 비율을 추적합니다.
  • 업무 결과 일치율: 고객에게 안내한 처리 상태와 실제 결제·계정 시스템의 최종 결과가 일치하는지 확인합니다.
